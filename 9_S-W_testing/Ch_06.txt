1. WHAT IS SOFTWARE TESTING?
====================================================================

Software Testing is the process of evaluating software to determine
whether it behaves as expected and satisfies specified requirements.

In simple words:

    SOFTWARE TESTING = CHECKING SOFTWARE QUALITY AND BEHAVIOR

A tester compares:

    EXPECTED RESULT
            VS
    ACTUAL RESULT


Example:

Requirement:

    User should be able to log in using valid username and password.


Tester performs:

    1. Open login page.
    2. Enter valid username.
    3. Enter valid password.
    4. Click Login.
    5. Observe result.


Expected:

    User successfully logs in.


Actual:

    User successfully logs in.


Result:

    PASS


If the application shows:

    "Invalid password"

when valid credentials were entered:

    Expected ≠ Actual

Therefore:

    FAIL


====================================================================
2. WHY IS SOFTWARE TESTING REQUIRED?
====================================================================

Software is developed by humans, and human beings can make mistakes.

Mistakes during:

    - Requirement analysis
    - Design
    - Coding
    - Configuration
    - Integration
    - Deployment

can introduce defects into software.


Software testing helps identify problems before they affect users.


Example:

Suppose an e-commerce application has a payment defect.

Expected:

    ₹1,000 should be deducted from the customer account.


Actual:

    ₹10,000 is deducted.


This could cause:

    - Financial loss
    - Customer complaints
    - Business reputation damage
    - Legal/compliance problems
    - Loss of customer trust


Therefore, testing is an important part of software development.


====================================================================
3. MAIN OBJECTIVES OF SOFTWARE TESTING
====================================================================

Important objectives include:

1. Find defects.

2. Verify that requirements are implemented.

3. Validate that the software meets user/business needs.

4. Reduce the risk of software failure.

5. Provide information about software quality.

6. Verify expected behavior.

7. Detect problems early.

8. Improve confidence in the software.

9. Help prevent defects from reaching production.

10. Support delivery of reliable software.


IMPORTANT:

Testing is not only about finding bugs.

Testing also provides INFORMATION about the quality and risks
associated with the software.


====================================================================
4. WHAT DOES A SOFTWARE TESTER ACTUALLY DO?
====================================================================

A QA/Test Engineer may:

    - Understand requirements
    - Review user stories
    - Analyze acceptance criteria
    - Design test scenarios
    - Write test cases
    - Prepare test data
    - Execute tests
    - Compare expected and actual results
    - Report defects
    - Retest fixes
    - Perform regression testing
    - Test APIs
    - Test databases
    - Test web/mobile applications
    - Perform automation
    - Analyze logs
    - Communicate quality risks


Typical flow:

    REQUIREMENT
        ↓
    TEST DESIGN
        ↓
    TEST EXECUTION
        ↓
    RESULT
       / \
    PASS  FAIL
          ↓
       DEFECT
          ↓
        FIX
          ↓
       RETEST
          ↓
      REGRESSION
          ↓
        CLOSE


====================================================================
5. TESTING IS NOT JUST "FINDING BUGS"
====================================================================

A common beginner misconception is:

    "The job of a tester is to find bugs."

This is incomplete.

A professional QA engineer focuses on:

    - Finding defects
    - Preventing defects
    - Understanding risks
    - Verifying requirements
    - Validating behavior
    - Providing feedback
    - Improving product quality
    - Supporting reliable releases


Example:

During requirement review, QA notices:

    "User can transfer money."

But the requirement does not specify:

    - Maximum transfer amount
    - Minimum amount
    - Insufficient balance behavior
    - Invalid account behavior

QA asks these questions BEFORE development.

This can prevent defects from being introduced.


====================================================================
6. VERIFICATION
====================================================================

Verification means checking whether work products are being created
according to specified requirements, specifications, or expectations.

Simple question:

    "Are we building the product correctly?"


Verification is commonly associated with activities such as:

    - Requirement reviews
    - Design reviews
    - Code reviews
    - Documentation reviews
    - Inspections
    - Walkthroughs


Example:

Requirement says:

    Password must contain at least 8 characters.


During requirement/design/code review, the team checks whether the
implementation design supports this rule.


Verification focuses strongly on correctness of work products and
whether specified requirements are being followed.


====================================================================
7. VALIDATION
====================================================================

Validation means evaluating the actual software to determine whether
it satisfies user needs and intended use.

Simple question:

    "Are we building the right product?"


Example:

Requirement:

    User should be able to reset password.


Tester uses the actual application:

    1. Open Forgot Password.
    2. Enter registered email.
    3. Request reset.
    4. Open reset link.
    5. Set new password.
    6. Log in using new password.


If the functionality satisfies the intended requirement:

    VALIDATION SUCCESS


Validation is strongly associated with executing and evaluating the
software.


====================================================================
8. VERIFICATION VS VALIDATION
====================================================================

Very important interview topic.


VERIFICATION:

    "Are we building the product correctly?"

Focus:

    - Specifications
    - Requirements
    - Design
    - Code
    - Documents
    - Reviews


VALIDATION:

    "Are we building the right product?"

Focus:

    - Actual software
    - User needs
    - Expected behavior
    - Real-world usage
    - Testing


Simple memory trick:

    VERIFICATION → PRODUCT CORRECTLY
    VALIDATION   → RIGHT PRODUCT


Example:

Suppose the business needs a login system.

Verification:

    Does the design/code correctly implement the specified
    login requirements?


Validation:

    Does the actual login system satisfy the user's need to
    securely access the application?


====================================================================
9. QUALITY ASSURANCE — QA
====================================================================

Quality Assurance is a process-oriented approach focused on
preventing quality problems and improving the processes used to
develop software.

Simple idea:

    QA focuses on PROCESS IMPROVEMENT AND DEFECT PREVENTION.


Examples:

    - Define testing processes
    - Establish standards
    - Review development practices
    - Improve workflows
    - Define quality procedures
    - Promote preventive activities
    - Analyze recurring problems


QA asks:

    "How can we improve the process so that fewer defects are
     introduced?"


Example:

If a team repeatedly receives incomplete requirements, QA may
recommend:

    - Requirement review process
    - Acceptance criteria standards
    - Review checklist
    - Better communication process


====================================================================
10. QUALITY CONTROL — QC
====================================================================

Quality Control is focused on evaluating the actual product or
output to identify defects.

Simple idea:

    QC focuses on PRODUCT EVALUATION.


Examples:

    - Test execution
    - Product inspection
    - Defect identification
    - Checking actual output against expected output


Example:

Tester checks whether the login function works correctly.

That is a quality control activity.


====================================================================
11. QA VS QC
====================================================================

QA:

    Process-oriented
    Preventive
    Focuses on improving process
    Asks: "How can we prevent problems?"


QC:

    Product-oriented
    Detective
    Focuses on identifying problems in the product
    Asks: "Does the product have problems?"


Comparison:

+----------------------+-----------------------------+
| QA                   | QC                          |
+----------------------+-----------------------------+
| Process-oriented     | Product-oriented            |
| Preventive focus     | Detective focus             |
| Improves process     | Evaluates product           |
| Prevents defects     | Finds defects               |
| Process-focused      | Product-focused             |
+----------------------+-----------------------------+


IMPORTANT:

Software testing is commonly considered a QC activity, while QA is
broader and includes process-oriented quality activities.


====================================================================
12. QA VS TESTING
====================================================================

QA is broader than testing.

QA includes activities intended to improve and assure the quality
of the development process.

Testing is the systematic evaluation of software to identify
problems and determine whether expected requirements are met.


Think:

    QUALITY ASSURANCE
           |
           +----------------------+
           |                      |
       Process                Prevention
           |
       Standards
           |
       Improvement


Testing is one important part of the overall quality effort.


====================================================================
13. WHAT IS AN ERROR?
====================================================================

An Error is a human mistake that can lead to an incorrect result
or introduce a defect into a software work product.


Examples:

    - Developer misunderstands a requirement.
    - Developer writes incorrect logic.
    - Tester misunderstands expected behavior.
    - Business analyst documents a requirement incorrectly.


Example:

Requirement:

    Discount should be 20%.


Developer misunderstands it as:

    Discount should be 2%.


The developer's misunderstanding is an ERROR.


====================================================================
14. WHAT IS A DEFECT?
====================================================================

A Defect is a flaw or problem in a software work product that causes
the software to behave differently from what is expected or
specified.


Example:

Requirement:

    Discount = 20%


Implementation:

    Discount = 2%


The incorrect implementation is a DEFECT.


A defect may exist even if it has not yet caused a visible failure.


====================================================================
15. WHAT IS A BUG?
====================================================================

A Bug is commonly used to refer to a defect or problem in software.


Example:

Expected:

    Total = ₹800


Actual:

    Total = ₹900


Tester reports:

    "Incorrect total calculation."


This issue may be called:

    Bug
    Defect


In everyday software testing discussions, these terms are often used
interchangeably.


====================================================================
16. WHAT IS A FAILURE?
====================================================================

A Failure occurs when the software actually executes and produces
an incorrect result or behavior.


Example:

Code contains an incorrect discount calculation.

The defect exists in the software.

When a customer applies the discount:

    Expected: ₹800
    Actual:   ₹900


The incorrect observed behavior is a FAILURE.


Important distinction:

    ERROR
      ↓
    DEFECT
      ↓
    EXECUTION
      ↓
    FAILURE


Not every defect necessarily produces a failure in every situation.


====================================================================
17. WHAT IS ROOT CAUSE?
====================================================================

Root Cause is the underlying reason why a defect occurred.


Example:

Observed problem:

    Payment fails for some customers.


Defect:

    Payment API request contains incorrect currency code.


Root cause:

    Requirement for supported currency values was misunderstood.


So:

    FAILURE:
        Payment fails.


    DEFECT:
        Incorrect currency code sent.


    ROOT CAUSE:
        Requirement misunderstanding.


Finding the root cause helps prevent similar defects from appearing
again.


====================================================================
18. ERROR vs DEFECT vs FAILURE
====================================================================

These concepts are extremely important.


ERROR:

    Human mistake.


DEFECT:

    Flaw introduced into a software work product.


FAILURE:

    Incorrect behavior observed when the software executes.


Example:

Step 1:

Developer misunderstands:

    "Discount is 20%"

as:

    "Discount is 2%"


This is:

    ERROR


Step 2:

Developer implements:

    discount = 2


This creates:

    DEFECT


Step 3:

Customer purchases a ₹1000 product.

Expected:

    ₹800


Actual:

    ₹980


This observed incorrect behavior is:

    FAILURE


Relationship:

    HUMAN ERROR
         ↓
      DEFECT
         ↓
    EXECUTION
         ↓
      FAILURE


====================================================================
19. ROOT CAUSE EXAMPLE
====================================================================

Requirement:

    User must receive OTP within the expected time.


Observed:

    OTP arrives very late.


Investigation:

    OTP service timeout configured incorrectly.


Further investigation:

    Configuration was copied incorrectly.


Root cause:

    Incorrect configuration process.


The tester should not stop at:

    "OTP is delayed."


A stronger engineering approach asks:

    "Why did this happen?"


This supports Root Cause Analysis (RCA).

21. REAL-WORLD EXAMPLE — LOGIN SYSTEM
====================================================================

Requirement:

    User should log in using valid email and password.


ERROR:

Developer misunderstands the authentication requirement.


DEFECT:

Authentication logic incorrectly rejects valid users.


TESTING:

Tester enters valid credentials.


EXPECTED:

User should enter the application.


ACTUAL:

Application displays:

    "Invalid credentials."


FAILURE:

The system fails to perform the expected login behavior.


ROOT CAUSE:

The authentication requirement was incorrectly interpreted.


Possible corrective action:

    - Fix authentication logic.
    - Improve requirement clarification.
    - Add test cases.
    - Add automated regression test.
    - Improve requirement review.


====================================================================
22. REAL-WORLD EXAMPLE — E-COMMERCE PAYMENT
====================================================================

Requirement:

    Customer should be charged exactly the order amount.


Error:

Developer incorrectly handles decimal values.


Defect:

Payment calculation rounds the amount incorrectly.


Testing:

Order amount:

    ₹1,299.50


Expected:

    ₹1,299.50


Actual:

    ₹1,300.00


Failure:

Customer is charged an incorrect amount.


Root Cause:

Incorrect decimal/rounding logic.


QA actions:

    - Report defect.
    - Provide reproduction steps.
    - Retest the fix.
    - Perform regression testing.
    - Add edge-case test cases.
    - Recommend automation for payment calculation.

23. TESTING AND REQUIREMENTS
====================================================================

Testing starts with understanding requirements.

Example:

Requirement:

    "User should be able to withdraw money."


A QA engineer should ask:

    - Minimum withdrawal?
    - Maximum withdrawal?
    - Daily limit?
    - Insufficient balance?
    - Invalid amount?
    - Decimal amount?
    - Account blocked?
    - Network failure?
    - Transaction timeout?
    - Duplicate request?
    - Transaction receipt?


This demonstrates that testing is also an analytical activity.


====================================================================
24. TESTING AND RISK
====================================================================

Testing cannot guarantee that software contains zero defects.

Instead, testing helps reduce risk by providing information about
the software's quality and behavior.


Example:

An e-commerce application has:

    Login
    Product search
    Cart
    Payment
    Wishlist


Risk priority may be:

    Payment → HIGH
    Login → HIGH
    Cart → HIGH
    Search → MEDIUM
    Wishlist → LOW


Testing effort can be prioritized based on risk.


====================================================================
25. CAN TESTING PROVE SOFTWARE HAS NO BUGS?
====================================================================

No.

Testing can demonstrate that defects exist when tests expose them,
but testing cannot generally prove that software contains zero
defects.

Why?

Because:

    - Exhaustive testing is usually impossible.
    - There can be many input combinations.
    - Different environments may behave differently.
    - New defects can be introduced later.
    - Some conditions may not be tested.


Therefore:

    TESTING REDUCES RISK;
    IT DOES NOT GUARANTEE PERFECTION.


This concept becomes more important in Chapter 7:
Testing Principles.

====================================================================
27. EXPECTED RESULT VS ACTUAL RESULT
====================================================================

One of the most fundamental concepts in testing.


EXPECTED RESULT:

    What should happen according to the requirement.


ACTUAL RESULT:

    What actually happens when the software is executed.


Example:

Requirement:

    Password must be at least 8 characters.


Test:

    Enter password:

        abc


Expected:

    Validation error.


Actual:

    Account successfully created.


Result:

    FAIL


Reason:

    Actual behavior does not match expected behavior.


====================================================================
28. POSITIVE AND NEGATIVE THINKING
====================================================================

Testing should not only check valid inputs.

POSITIVE TESTING:

    Test valid inputs and expected behavior.


Example:

    Valid email
    Valid password


NEGATIVE TESTING:

    Test invalid or unexpected inputs and behavior.


Example:

    Invalid email
    Wrong password
    Empty password
    Very long password
    Special characters
    Invalid input format


Both help evaluate software quality.


====================================================================
29. QA ENGINEER'S QUALITY MINDSET
====================================================================

A good QA engineer asks:

    "What should happen?"

    "What could go wrong?"

    "What happens with invalid input?"

    "What happens at the boundary?"

    "What happens when a dependency fails?"

    "What happens when the network fails?"

    "What happens when the user performs the action twice?"

    "What happens when the session expires?"

    "What happens under unusual conditions?"


This mindset becomes very important in test case design.


====================================================================
30. COMMON BEGINNER MISCONCEPTIONS
====================================================================

MISCONCEPTION 1:

    Testing starts only after development is complete.

CORRECT:

    Quality activities should begin early and continue throughout
    the development process.


MISCONCEPTION 2:

    QA means only testing.

CORRECT:

    QA is broader and focuses strongly on process and prevention.


MISCONCEPTION 3:

    Testing means finding every bug.

CORRECT:

    Exhaustive testing is generally impossible. Testing provides
    useful information and reduces risk.


MISCONCEPTION 4:

    If all test cases pass, the software is perfect.

CORRECT:

    Passing tests increase confidence but do not prove absence of
    all defects.


MISCONCEPTION 5:

    A tester is responsible for software quality alone.

CORRECT:

    Quality is a shared responsibility across the team.

32. IMPORTANT INTERVIEW QUESTIONS
====================================================================

Q1. What is software testing?

Answer:

Software testing is the process of evaluating software to determine
whether it behaves as expected and satisfies specified requirements.


Q2. Why is software testing required?

Answer:

Testing helps identify defects, verify requirements, validate
software behavior, reduce risks, and increase confidence in the
quality of the product.


Q3. What is the difference between verification and validation?

Answer:

Verification asks, "Are we building the product correctly?"
Validation asks, "Are we building the right product?"


Q4. What is QA?

Answer:

QA is a process-oriented approach focused on preventing quality
problems and improving development processes.


Q5. What is QC?

Answer:

QC is a product-oriented approach focused on evaluating the product
and identifying defects.


Q6. What is the difference between QA and QC?

Answer:

QA focuses on process improvement and prevention, while QC focuses
on product evaluation and defect detection.


Q7. Is testing QA or QC?

Answer:

Testing is commonly considered a QC activity because it evaluates
the product, while QA is broader and focuses on process and
prevention.


Q8. What is an error?

Answer:

An error is a human mistake that can lead to an incorrect software
work product.


Q9. What is a defect?

Answer:

A defect is a flaw in a software work product that causes it to
differ from specified or expected behavior.


Q10. What is a bug?

Answer:

Bug is a commonly used term for a software defect or problem.


Q11. What is a failure?

Answer:

A failure is incorrect behavior observed when the software executes.


Q12. What is root cause?

Answer:

Root cause is the underlying reason that caused a defect or problem
to occur.


Q13. Can testing guarantee defect-free software?

Answer:

No. Testing can reveal defects and reduce risk, but it cannot
generally prove that software contains no defects.


Q14. What is the difference between expected and actual result?

Answer:

Expected result is what should happen according to requirements.
Actual result is what the software actually produces during test
execution.


Q15. Is QA only responsible for finding bugs?

Answer:

No. QA also focuses on prevention, process improvement, early
quality involvement, risk identification, and continuous improvement.

33. SCENARIO-BASED INTERVIEW QUESTION
====================================================================

QUESTION:

A login feature works correctly for valid credentials but crashes
when the password field is empty.

What would you do?


ANSWER:

1. Reproduce the issue.
2. Confirm the expected behavior from the requirement.
3. Record steps to reproduce.
4. Capture actual and expected results.
5. Collect relevant evidence such as screenshots/logs.
6. Report the defect.
7. Assign appropriate severity/priority based on impact.
8. Developer fixes the issue.
9. Retest the fix.
10. Perform relevant regression testing.
11. Close the defect if the expected behavior is restored.
