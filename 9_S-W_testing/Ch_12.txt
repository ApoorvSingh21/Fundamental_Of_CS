1. INTRODUCTION TO TEST PLANNING
====================================================================

Test Planning is the process of deciding:

1. WHAT will be tested?
2. WHY will it be tested?
3. HOW will it be tested?
4. WHEN will it be tested?
5. WHO will perform the testing?
6. WHERE will testing be performed?
7. WHAT resources are required?
8. WHAT risks may affect testing?
9. WHEN can testing start?
10. WHEN can testing be completed?

In simple words:

Test Planning = Preparing a roadmap for testing.


Example:

Suppose we are testing an E-Commerce application.

Features:
    - User Registration
    - Login
    - Product Search
    - Product Details
    - Cart
    - Checkout
    - Payment
    - Order Management

Before writing hundreds of test cases, QA needs to decide:

    What features are in scope?
    What features are out of scope?
    Which browsers will be tested?
    Which devices will be tested?
    What test data is required?
    Who will test?
    What tools will be used?
    What are the risks?
    What are the entry criteria?
    What are the exit criteria?

This entire planning process is Test Planning.


====================================================================
2. WHY IS TEST PLANNING REQUIRED?
====================================================================

Without proper planning, testing can become:

    - Unorganized
    - Incomplete
    - Time-consuming
    - Difficult to track
    - Difficult to measure
    - Difficult to report

Test planning helps QA teams to:

    1. Define testing scope
    2. Define testing objectives
    3. Identify testing approach
    4. Identify required resources
    5. Identify test environment
    6. Prepare test data
    7. Identify risks
    8. Define responsibilities
    9. Define schedule
    10. Define entry and exit criteria
    11. Estimate testing effort
    12. Communicate testing expectations

3. TEST PLAN
====================================================================

A Test Plan is a document that describes the overall plan for
testing a software application.

It explains:

    WHAT to test
    HOW to test
    WHEN to test
    WHO will test
    WHERE to test
    WHAT resources are needed
    WHAT risks exist
    WHEN testing can start/end


Typical Test Plan contains:

    1. Test Plan ID
    2. Introduction
    3. Test Objectives
    4. Test Scope
    5. Features to be tested
    6. Features not to be tested
    7. Test Approach
    8. Test Environment
    9. Test Data
    10. Entry Criteria
    11. Exit Criteria
    12. Roles and Responsibilities
    13. Resources
    14. Schedule
    15. Risks
    16. Assumptions
    17. Dependencies
    18. Deliverables
    19. Tools
    20. Reporting mechanism


====================================================================
4. TEST PLAN VS TEST STRATEGY
====================================================================

These two concepts are frequently asked in interviews.


TEST STRATEGY
-------------

Test Strategy defines the high-level testing approach.

It answers:

    HOW will testing be performed?

Example:

    - Manual testing
    - Automation testing
    - API testing
    - Database testing
    - Regression testing
    - Cross-browser testing


TEST PLAN
---------

Test Plan defines the specific testing plan for a particular
project/release.

It answers:

    WHAT?
    WHO?
    WHEN?
    WHERE?
    HOW?
    HOW MUCH?


Simple difference:

    Test Strategy
        ↓
    High-level testing approach

    Test Plan
        ↓
    Project/release-specific testing plan


Example:

TEST STRATEGY:
    Automation will be used for regression testing.

TEST PLAN:
    Login, Cart and Checkout regression tests will be automated
    using Playwright and executed during every release.


====================================================================
5. TEST OBJECTIVES
====================================================================

Test Objectives define what testing is expected to achieve.

Examples:

    - Verify that requirements are implemented correctly.
    - Identify defects before production.
    - Verify critical business workflows.
    - Validate application functionality.
    - Verify compatibility across supported browsers.
    - Validate API responses.
    - Verify database data.
    - Reduce production defects.


Example:

E-Commerce Test Objectives:

    1. Verify user registration.
    2. Verify login functionality.
    3. Verify product search.
    4. Verify cart operations.
    5. Verify checkout.
    6. Verify payment workflow.
    7. Verify order creation.
    8. Verify supported browsers.


====================================================================
6. TEST SCOPE
====================================================================

Test Scope defines the boundaries of testing.

It tells us:

    What will be tested?

and

    What will NOT be tested?


Two important categories:

    1. In Scope
    2. Out of Scope


IN SCOPE
--------

Features that will be tested.

Example:

    - Registration
    - Login
    - Product Search
    - Cart
    - Checkout
    - Order History


OUT OF SCOPE
------------

Features that will not be tested in the current testing cycle.

Example:

    - Admin analytics
    - Recommendation engine
    - Third-party advertisement system


Why scope is important?

Because testing everything may not be possible due to:

    - Limited time
    - Limited resources
    - Release deadlines
    - Technical limitations
    - Business priorities


====================================================================
7. TEST APPROACH
====================================================================

Test Approach describes how testing will be performed.

Example:

For an E-Commerce application:

    Functional Testing
            ↓
    Integration Testing
            ↓
    API Testing
            ↓
    Database Validation
            ↓
    Regression Testing
            ↓
    Cross-Browser Testing
            ↓
    Automation Testing


Possible approaches include:

    - Manual testing
    - Automation testing
    - Risk-based testing
    - Exploratory testing
    - Regression testing
    - API testing
    - Database testing
    - Compatibility testing


Example:

Critical features:

    Login
    Payment
    Checkout

These may receive higher testing priority because failure can
directly affect users and business.

====================================================================
9. TEST DATA
====================================================================

Test Data is the data used during testing.

Example:

For Login:

    Valid Username:
        user@test.com

    Valid Password:
        Test@123


Invalid data:

    Username:
        invalid@test.com

    Password:
        wrong123


Other examples:

    - Customer records
    - Product records
    - Payment data
    - Order data
    - API payloads
    - Database records


Types of test data:

    1. Valid data
    2. Invalid data
    3. Boundary data
    4. Empty data
    5. Null data
    6. Duplicate data
    7. Large data
    8. Special-character data


Example:

Age field accepts:

    18–60


Test data:

    17      → Invalid
    18      → Valid boundary
    30      → Valid
    60      → Valid boundary
    61      → Invalid


====================================================================
10. ENTRY CRITERIA
====================================================================

Entry Criteria define the conditions that must be satisfied
BEFORE testing can start.

In simple words:

    "Are we ready to start testing?"


Examples:

    - Requirements are available.
    - Build is deployed.
    - Test environment is ready.
    - Test data is available.
    - Required tools are available.
    - Test cases are prepared.
    - Major dependencies are available.


Example:

For system testing:

    Entry Criteria:

    1. Development is completed.
    2. Build is deployed to QA environment.
    3. Smoke testing is completed successfully.
    4. Test environment is available.
    5. Required test data is available.


====================================================================
11. EXIT CRITERIA
====================================================================

Exit Criteria define the conditions required to COMPLETE testing.

In simple words:

    "Are we ready to stop testing?"


Examples:

    - Planned test cases executed.
    - Critical defects resolved or accepted.
    - Regression testing completed.
    - Required pass percentage achieved.
    - Test summary prepared.
    - Business stakeholders accept remaining risks.


Example:

Exit Criteria:

    1. 100% critical test cases executed.
    2. No open Critical defects.
    3. No open blocker defects.
    4. Regression testing completed.
    5. Test summary report prepared.


Important:

Entry Criteria = Conditions before testing starts.

Exit Criteria = Conditions before testing ends.


====================================================================
12. ENTRY CRITERIA VS EXIT CRITERIA
====================================================================

+----------------+---------------------------------------------+
| Entry Criteria | Exit Criteria                               |
+----------------+---------------------------------------------+
| Before testing | Before testing completion                   |
| Defines start  | Defines completion                          |
| Environment    | Test execution completed                    |
| Build ready    | Required tests passed                       |
| Data ready     | Critical defects resolved/accepted         |
+----------------+---------------------------------------------+


Interview Question:

Q: What happens if exit criteria are not satisfied?

Answer:

Testing should not simply be declared complete.

The team should:

    - Evaluate remaining defects
    - Evaluate risks
    - Discuss business impact
    - Obtain appropriate approval if required
    - Document remaining issues
    - Make a release recommendation


====================================================================
13. TEST RISKS
====================================================================

A Test Risk is a possible problem that can negatively affect
testing or software quality.

Examples:

    - Requirements may change.
    - Environment may be unstable.
    - Test data may be unavailable.
    - Build may be delayed.
    - Limited testing time.
    - Limited QA resources.
    - Third-party service unavailable.
    - Automation tests may be unstable.


Example:

Risk:

    Payment gateway is unavailable.

Impact:

    Payment testing may be blocked.

Mitigation:

    Use a test/sandbox payment environment or mock service
    where appropriate.


====================================================================
14. RISK IDENTIFICATION
====================================================================

QA should identify:

    1. Risk
    2. Probability
    3. Impact
    4. Mitigation
    5. Contingency


Example:

Risk:
    QA environment may become unavailable.

Probability:
    Medium

Impact:
    High

Mitigation:
    Maintain backup environment or coordinate with DevOps.

Contingency:
    Execute available API/unit-level checks while environment
    is restored.


====================================================================
15. ASSUMPTIONS
====================================================================

Assumptions are things that the testing team expects to be true
while planning.

Examples:

    - Requirements are approved.
    - QA environment will be available.
    - Developers will provide stable builds.
    - Required test accounts will be available.
    - Required third-party services will be accessible.


Important:

An assumption may later turn out to be incorrect.

Therefore, important assumptions should be documented.


====================================================================
16. DEPENDENCIES
====================================================================

Dependencies are external conditions, systems, teams, tools,
services, or components required for testing.

Examples:

    Application testing may depend on:

        ↓

    Backend API
        ↓
    Database
        ↓
    Payment Gateway
        ↓
    Authentication Service
        ↓
    Email Service


Example:

Checkout testing depends on:

    Cart service
    Order service
    Payment service


If Payment API is unavailable:

    Checkout testing may be partially blocked.

24. TEST PLAN VS TEST STRATEGY — INTERVIEW VIEW
====================================================================

Q: What is Test Strategy?

Answer:

Test Strategy is a high-level document/approach that defines
how testing will be performed.

Q: What is Test Plan?

Answer:

Test Plan describes the project/release-specific testing scope,
objectives, approach, environment, resources, schedule, risks,
criteria and responsibilities.

Q: Which is more high-level?

Answer:

Test Strategy is generally more high-level.

25. WHAT HAPPENS WHEN REQUIREMENTS CHANGE?
====================================================================

Requirements may change during development.

QA should perform:

    1. Requirement impact analysis
    2. Identify affected test scenarios
    3. Update test cases
    4. Update test data
    5. Update RTM
    6. Update automation tests if required
    7. Re-evaluate risks
    8. Re-evaluate schedule
    9. Communicate impact


Example:

Original requirement:

    User can add maximum 5 products to cart.

Changed requirement:

    User can add maximum 10 products.

QA must review:

    - Test cases
    - Boundary tests
    - Negative tests
    - Automation scripts
    - Test data
    - Requirement traceability


====================================================================
26. RISK-BASED TEST PLANNING
====================================================================

Not every feature has equal business risk.

Example:

E-Commerce:

    Login       → High
    Payment     → Very High
    Checkout    → Very High
    Search      → Medium
    About Us    → Low


Testing priority can therefore be influenced by risk.

High-risk functionality:

    - Gets more test coverage
    - Gets more negative testing
    - Gets regression coverage
    - May receive automation coverage
    - May require additional validation

29. INTERVIEW QUESTIONS — TEST PLANNING
====================================================================

Q1. What is Test Planning?

Answer:
    Test Planning is the process of defining the objectives,
    scope, approach, resources, environment, schedule, risks,
    criteria and responsibilities for testing.

Q2. What is a Test Plan?

Answer:
    A Test Plan is a project/release-specific document that
    describes how testing will be organized and executed.

Q3. What is Test Strategy?

Answer:
    Test Strategy defines the high-level testing approach.

Q4. Difference between Test Plan and Test Strategy?

Answer:
    Strategy is high-level; Test Plan is more specific to a
    project/release and defines practical execution details.

Q5. What is Test Scope?

Answer:
    Test Scope defines what will and will not be tested.

Q6. What are Entry Criteria?

Answer:
    Conditions that must be satisfied before testing starts.

Q7. What are Exit Criteria?

Answer:
    Conditions used to determine whether testing can be completed.

Q8. What is Test Environment?

Answer:
    The hardware, software, systems, tools and configuration
    required to execute tests.

Q9. What is Test Data?

Answer:
    Data used to execute and validate test scenarios.

Q10. What are Test Risks?

Answer:
    Potential problems that can negatively affect testing,
    quality, schedule or release.

30. SCENARIO-BASED INTERVIEW QUESTIONS
====================================================================

Q1.
A payment service is unavailable. What will you do?

Answer:

    - Identify dependency.
    - Assess impact.
    - Inform stakeholders.
    - Check sandbox/mock availability.
    - Test other independent functionality.
    - Document blocked scenarios.
    - Re-test payment once service becomes available.


Q2.
Requirements change one day before release. What will you do?

Answer:

    - Perform impact analysis.
    - Identify affected tests.
    - Update test cases/data.
    - Update RTM.
    - Update automation where necessary.
    - Reassess risk and schedule.
    - Communicate impact.


Q3.
There are only two hours left for testing. What will you do?

Answer:

    Use risk-based prioritization.

    Test first:

        Critical business functionality
        High-risk areas
        Recent changes
        Major integrations
        Critical regression paths


Q4.
The QA environment is unstable. What will you do?

Answer:

    - Report the environment issue.
    - Coordinate with DevOps/development.
    - Identify unaffected testing.
    - Perform API/database/unit-level validation where possible.
    - Document blocked testing.
    - Re-run blocked tests after environment recovery.
