============================================================

Goal:
Learn how a QA Engineer studies requirements before writing
test scenarios and test cases.

This chapter covers:

============================================================
1. WHAT IS A REQUIREMENT?
============================================================

A requirement describes what a software system should provide,
how it should behave, or what constraints it must satisfy.

Simple definition:

    Requirement =
    A documented need, capability, behavior, or condition that
    the software/system is expected to satisfy.


Example:

    "The user should be able to login using a registered
     email address and password."


This requirement tells the team what the system should support.


============================================================
2. WHY REQUIREMENTS ARE IMPORTANT
============================================================

Requirements become the foundation for:

    Requirement
         ↓
    Design
         ↓
    Development
         ↓
    Testing
         ↓
    Release


QA engineers use requirements to determine:

    - What should be tested?
    - What should the expected result be?
    - What test scenarios are required?
    - What edge cases should be considered?
    - What business rules must be validated?


============================================================
3. REQUIREMENT ANALYSIS
============================================================

Requirement Analysis is the process of studying, understanding,
clarifying, and evaluating requirements before designing tests
and building the software.


QA should ask:

    - What is the expected behavior?
    - What inputs are allowed?
    - What outputs are expected?
    - What are the business rules?
    - What happens with invalid input?
    - What are the boundaries?
    - What are the dependencies?
    - What are the acceptance conditions?
    - Is the requirement testable?


============================================================
4. EXAMPLE — LOGIN REQUIREMENT
============================================================

Requirement:

    "A registered user can log in using email and password."


QA analyzes:

    Valid email?
    Invalid email?
    Empty email?
    Valid password?
    Invalid password?
    Empty password?
    Account locked?
    Unregistered email?
    Password case sensitivity?
    Error message?
    Session creation?
    Logout?


One simple requirement can generate many test scenarios.


============================================================
5. TYPES OF REQUIREMENTS
============================================================

Important requirement categories:

    1. Business Requirements
    2. Functional Requirements
    3. Non-Functional Requirements
    4. Technical Requirements


============================================================
6. BUSINESS REQUIREMENTS
============================================================

Business requirements describe the high-level business goal or
problem that the software should solve.

They answer:

    "Why is the system being built?"


Example:

    "The company wants to provide customers with online
     shopping capability."


Another example:

    "The bank wants customers to transfer money online."


Business requirement:

    Business goal


============================================================
7. FUNCTIONAL REQUIREMENTS
============================================================

Functional requirements describe what the system should do.

They define:

    - Features
    - Functions
    - User actions
    - Business rules
    - Inputs
    - Outputs
    - System behavior


Example:

    "The user shall be able to add a product to the cart."


Another:

    "The system shall send an OTP to the registered mobile
     number during login verification."


============================================================
8. FUNCTIONAL REQUIREMENT EXAMPLE
============================================================

Requirement:

    User can reset password.

Possible functional requirements:

    1. User can select "Forgot Password".
    2. User can enter registered email.
    3. System validates the email.
    4. System sends reset instructions.
    5. User can create a new password.
    6. System validates password rules.
    7. User can login using the new password.


============================================================
9. NON-FUNCTIONAL REQUIREMENTS
============================================================

Non-functional requirements describe quality characteristics,
constraints, or performance expectations.

Examples:

    - Performance
    - Security
    - Availability
    - Reliability
    - Scalability
    - Usability
    - Accessibility
    - Compatibility


Example:

    "The search results should be returned within the defined
     performance target under expected load."


Another:

    "The system must support the required number of concurrent
     users."


============================================================
10. FUNCTIONAL vs NON-FUNCTIONAL
============================================================

FUNCTIONAL:

    What should the system do?

Example:

    User can transfer money.


NON-FUNCTIONAL:

    How well or under what quality constraints should it work?

Example:

    Transfer request should meet the defined response-time
    requirement under expected load.


Memory:

    FUNCTIONAL
        = WHAT

    NON-FUNCTIONAL
        = HOW WELL / QUALITY / CONSTRAINT


============================================================
11. TECHNICAL REQUIREMENTS
============================================================

Technical requirements describe technical conditions,
technologies, architecture, interfaces, platforms, or constraints
that the system must satisfy.

Examples:

    - Database technology
    - API requirements
    - Supported operating systems
    - Browser support
    - Authentication mechanism
    - Programming/platform constraints
    - Integration requirements


Example:

    "The application shall expose a REST API for order management."


Another:

    "The system shall support the organization's required
     database platform."


============================================================
12. BUSINESS vs FUNCTIONAL vs NON-FUNCTIONAL
============================================================

BUSINESS:

    Why are we building it?

FUNCTIONAL:

    What should it do?

NON-FUNCTIONAL:

    How well should it work?

TECHNICAL:

    What technical constraints or implementation-related
    requirements must be satisfied?


Example:

    BUSINESS:
        Increase online sales.

    FUNCTIONAL:
        Customer can purchase products online.

    NON-FUNCTIONAL:
        Checkout must meet defined performance and availability
        requirements.

    TECHNICAL:
        Checkout communicates with payment service through the
        required API architecture.


============================================================
13. BRD — BUSINESS REQUIREMENTS DOCUMENT
============================================================

BRD stands for:

    Business Requirements Document


It generally describes high-level business needs and objectives.


Typical information may include:

    - Business problem
    - Business goals
    - Scope
    - Stakeholders
    - High-level requirements
    - Business expectations


Example:

    Goal:
        Build an online shopping platform.

    Business objectives:
        - Increase online sales
        - Provide online checkout
        - Support online payments


============================================================
14. SRS — SOFTWARE REQUIREMENTS SPECIFICATION
============================================================

SRS stands for:

    Software Requirements Specification


It describes software requirements in greater detail.

It can contain:

    - Functional requirements
    - Non-functional requirements
    - System behavior
    - Interfaces
    - Constraints
    - Data requirements
    - External dependencies


The exact structure depends on the organization/project.


============================================================
15. BRD vs SRS
============================================================

BRD:

    Focus:
        Business needs and goals.

    Question:
        "What does the business need?"


SRS:

    Focus:
        Detailed software/system requirements.

    Question:
        "What should the software/system provide?"


Memory:

    BRD → BUSINESS

    SRS → SOFTWARE


============================================================
16. USER STORY
============================================================

A User Story is a short description of a desired capability
from the perspective of a user or stakeholder.

Common format:

    As a <type of user>,
    I want <some capability>,
    so that <some benefit>.


Example:

    As a customer,
    I want to add products to my cart,
    so that I can purchase them later.


============================================================
17. USER STORY STRUCTURE
============================================================

        USER STORY
             |
    +--------+--------+
    |        |        |
    WHO      WHAT    WHY
    |        |        |
   User   Capability Benefit


Example:

    WHO:
        Customer

    WHAT:
        Add product to cart

    WHY:
        Purchase product later


============================================================
18. USER STORIES IN AGILE
============================================================

In Agile projects, requirements are frequently expressed as:

    Epic
      ↓
    User Story
      ↓
    Acceptance Criteria
      ↓
    Tasks/Test Cases


Example:

    EPIC:
        Shopping


    USER STORY:
        Customer can add products to cart.


    ACCEPTANCE CRITERIA:
        Product is added successfully.
        Cart count is updated.
        Correct product quantity is shown.


============================================================
19. ACCEPTANCE CRITERIA
============================================================

Acceptance Criteria define the conditions that must be satisfied
for a user story or requirement to be accepted.

They answer:

    "What must be true for this requirement to be considered
     complete and acceptable?"


============================================================
20. ACCEPTANCE CRITERIA EXAMPLE
============================================================

User Story:

    As a customer,
    I want to reset my password,
    so that I can regain access to my account.


Acceptance Criteria:

    1. User can select Forgot Password.
    2. User can enter a registered email.
    3. System sends reset instructions.
    4. Reset mechanism has the defined expiration behavior.
    5. User can create a valid new password.
    6. User can login with the new password.


These criteria become useful for:

    - Test scenarios
    - Test cases
    - Acceptance testing
    - Definition of done discussions


============================================================
21. GOOD REQUIREMENT CHARACTERISTICS
============================================================

A good requirement should ideally be:

    - Clear
    - Unambiguous
    - Complete
    - Consistent
    - Testable
    - Feasible
    - Traceable
    - Prioritized where appropriate
    - Understandable


============================================================
22. CLEAR REQUIREMENT
============================================================

Bad:

    "System should be fast."

Problem:

    "Fast" is unclear.


Better:

    "The system should meet the specified response-time
     requirement under the defined workload."


A testable requirement should provide measurable or
verifiable expectations where appropriate.


============================================================
23. AMBIGUOUS REQUIREMENT
============================================================

Ambiguous:

    "User should receive a quick response."


Questions:

    How quick?
    Under what conditions?
    What operation?
    What workload?
    What is the acceptable threshold?


QA should raise clarification questions before testing.


============================================================
24. INCOMPLETE REQUIREMENT
============================================================

Requirement:

    "User can register using email."

Missing information:

    - Email validation rules?
    - Duplicate email behavior?
    - Password rules?
    - Verification required?
    - Error messages?
    - Account activation?
    - Maximum attempts?


Incomplete requirements create uncertainty and testing gaps.


============================================================
25. TESTABLE REQUIREMENT
============================================================

A requirement is testable when its expected behavior or condition
can be verified through testing.

Bad:

    "Application should be user-friendly."


Better:

    "A new user should be able to complete registration without
     assistance using the documented workflow."


Even better when measurable criteria are available:

    Define measurable usability criteria appropriate to the
    product.


============================================================
26. REQUIREMENT REVIEW
============================================================

QA should review requirements before test case creation.

Review questions:

    [ ] Is the requirement clear?
    [ ] Is it complete?
    [ ] Is it testable?
    [ ] Are inputs defined?
    [ ] Are outputs defined?
    [ ] Are error conditions defined?
    [ ] Are business rules defined?
    [ ] Are dependencies identified?
    [ ] Are acceptance criteria available?
    [ ] Are assumptions documented?
    [ ] Are non-functional requirements included?


============================================================
27. REQUIREMENT AMBIGUITY — QA EXAMPLE
============================================================

Requirement:

    "User can upload a file."


QA questions:

    Which file types?
    Maximum file size?
    Minimum file size?
    Number of files?
    Duplicate files?
    Empty file?
    Corrupted file?
    Filename restrictions?
    Security restrictions?
    Upload timeout?
    What happens after failure?


A good QA engineer does not simply assume answers.


============================================================
28. REQUIREMENT ANALYSIS → TEST SCENARIOS
============================================================

Requirement:

    "User can upload PDF files up to 10 MB."


QA derives scenarios:

    Valid:
        PDF < 10 MB
        PDF = 10 MB


    Invalid:
        PDF > 10 MB
        JPG file
        EXE file
        Empty file
        Corrupted PDF


    Boundary:
        Just below 10 MB
        Exactly 10 MB
        Just above 10 MB


Requirement analysis directly influences test design.


============================================================
29. REQUIREMENT DEPENDENCIES
============================================================

Some requirements depend on other systems.

Example:

    Order Placement
          ↓
    Payment Service
          ↓
    Bank/Payment Gateway


QA should identify:

    - External APIs
    - Database dependencies
    - Authentication services
    - Third-party systems
    - Test environment dependencies


============================================================
30. REQUIREMENT RISKS
============================================================

Requirements can have different risk levels.

Example:

    Banking:
        Money transfer
            → High risk

    E-commerce:
        Payment
            → High risk

    Profile theme:
        → Lower business risk in many contexts


QA should consider risk when deciding:

    - Test depth
    - Priority
    - Automation
    - Regression coverage
    - Negative testing


============================================================
31. REQUIREMENT PRIORITY
============================================================

Requirements may be prioritized based on business value,
risk, dependencies, urgency, or release needs.

Example:

    HIGH:
        Login
        Payment
        Order placement

    MEDIUM:
        Product filtering

    LOWER:
        Optional UI customization


Priority helps QA focus effort appropriately.


============================================================
32. TRACEABILITY
============================================================

Traceability means being able to connect requirements to
corresponding test scenarios, test cases, and results.

Example:

    Requirement
        ↓
    Test Scenario
        ↓
    Test Case
        ↓
    Execution
        ↓
    Result
        ↓
    Defect (if any)


This provides visibility into requirement coverage.


============================================================
33. RTM — REQUIREMENT TRACEABILITY MATRIX
============================================================

RTM stands for:

    Requirement Traceability Matrix


It maps requirements to test cases.

Basic example:

    +------+----------------------+-----------+
    | Req  | Requirement          | Test Case |
    +------+----------------------+-----------+
    | R01  | User Login           | TC01-TC05 |
    | R02  | Product Search       | TC06-TC10 |
    | R03  | Add to Cart          | TC11-TC15 |
    | R04  | Checkout             | TC16-TC20 |
    +------+----------------------+-----------+


============================================================
34. WHY RTM IS IMPORTANT
============================================================

RTM helps:

    - Verify requirement coverage
    - Identify missing tests
    - Track test coverage
    - Support audits
    - Track requirement changes
    - Connect defects to requirements
    - Improve project visibility


============================================================
35. TYPES OF TRACEABILITY
============================================================

Common concepts:

    Forward Traceability
    Backward Traceability
    Bi-directional Traceability


------------------------------------------------------------
FORWARD TRACEABILITY
------------------------------------------------------------

Requirement
    ↓
Test Cases

Question:

    "Has every requirement been covered by tests?"


------------------------------------------------------------
BACKWARD TRACEABILITY
------------------------------------------------------------

Test Case
    ↓
Requirement

Question:

    "Does every test have a valid requirement?"


------------------------------------------------------------
BI-DIRECTIONAL
------------------------------------------------------------

Requirement
    ↔
Test Case

Coverage can be traced in both directions.


============================================================
36. QA ROLE IN REQUIREMENT ANALYSIS
============================================================

QA should not wait until coding is finished.

QA can participate from the requirement stage.

Responsibilities may include:

    1. Review requirements.
    2. Identify ambiguity.
    3. Ask clarification questions.
    4. Identify missing requirements.
    5. Identify test scenarios.
    6. Identify risks.
    7. Identify dependencies.
    8. Review acceptance criteria.
    9. Estimate testing effort.
   10. Prepare traceability.


============================================================
37. SHIFT-LEFT CONNECTION
============================================================

Traditional thinking:

    Requirements
        ↓
    Development
        ↓
    Testing


Shift-left approach:

    QA involvement starts earlier.

    Requirements
        ↓
    QA review
        ↓
    Development
        ↓
    Testing


Benefits:

    - Earlier defect prevention
    - Better requirements
    - Reduced ambiguity
    - Earlier risk identification
    - Lower downstream cost


============================================================
38. REQUIREMENT CHANGE
============================================================

Requirements can change during development.

Example:

Original:

    "Maximum file size = 10 MB"


Changed:

    "Maximum file size = 25 MB"


QA must identify affected:

    - Requirements
    - Test cases
    - Test data
    - Automation
    - RTM
    - Regression suite
    - Documentation


============================================================
39. CHANGE IMPACT ANALYSIS
============================================================

When a requirement changes, ask:

    What changed?
        ↓
    Which features are affected?
        ↓
    Which test cases are affected?
        ↓
    Which automation scripts are affected?
        ↓
    Which APIs/DB components are affected?
        ↓
    What regression testing is required?

============================================================
41. FROM REQUIREMENT TO TEST CASE
============================================================

Requirement:

    "User should be able to login with valid credentials."


Test Scenario:

    Verify login with valid credentials.


Test Case:

    ID:
        TC_LOGIN_001

    Preconditions:
        Registered user exists.

    Steps:
        1. Open login page.
        2. Enter valid email.
        3. Enter valid password.
        4. Click Login.

    Expected:
        User successfully reaches the authenticated area.


Additional scenarios:

    Invalid password
    Invalid email
    Empty fields
    Locked account
    Session behavior
    Password visibility
    Remember-me behavior if supported

============================================================
43. COMMON QA MISTAKES DURING REQUIREMENT ANALYSIS
============================================================

Mistake 1:

    Assuming unclear requirements.

Better:

    Ask for clarification.


Mistake 2:

    Testing only happy paths.

Better:

    Include negative, boundary, and error scenarios.


Mistake 3:

    Ignoring non-functional requirements.

Better:

    Review performance, security, usability, compatibility,
    accessibility, and other applicable requirements.


Mistake 4:

    Not updating tests after requirement changes.

Better:

    Perform change impact analysis.


Mistake 5:

    Testing without traceability.

Better:

    Maintain appropriate requirement-to-test mapping.

44. INTERVIEW QUESTIONS
============================================================

Q1. What is Requirement Analysis?

Answer:

Requirement Analysis is the process of studying, understanding,
clarifying, and evaluating requirements to determine what the
software should provide and how it should be verified.


Q2. What is a requirement?

Answer:

A requirement describes a business need, capability, behavior,
condition, or constraint that the system is expected to satisfy.


Q3. What is a Functional Requirement?

Answer:

A functional requirement describes what the system should do,
including features, behavior, inputs, outputs, and business rules.


Q4. What is a Non-Functional Requirement?

Answer:

A non-functional requirement describes quality characteristics or
constraints such as performance, security, usability, reliability,
scalability, and compatibility.


Q5. What is a Business Requirement?

Answer:

A business requirement describes the high-level business goal or
need that the software is intended to address.


Q6. What is a Technical Requirement?

Answer:

A technical requirement describes technical conditions,
interfaces, platforms, architecture-related constraints, or
technology requirements that the system must satisfy.


Q7. What is BRD?

Answer:

BRD stands for Business Requirements Document. It generally
describes high-level business needs, objectives, scope, and
stakeholder expectations.


Q8. What is SRS?

Answer:

SRS stands for Software Requirements Specification. It describes
software/system requirements in greater detail, including
functional and non-functional requirements and applicable
constraints/interfaces.


Q9. What is a User Story?

Answer:

A user story is a short description of a desired capability from
the perspective of a user or stakeholder.


Q10. What are Acceptance Criteria?

Answer:

Acceptance criteria define the conditions that must be satisfied
for a user story or requirement to be accepted.


Q11. What is RTM?

Answer:

RTM stands for Requirement Traceability Matrix. It maps
requirements to corresponding test cases and helps verify
requirement coverage.


Q12. Why is requirement analysis important for QA?

Answer:

It helps QA understand expected behavior, identify ambiguities,
discover missing scenarios, identify risks and dependencies, and
design appropriate tests before execution.


============================================================
45. SCENARIO-BASED INTERVIEW QUESTIONS
============================================================

Q1.

Requirement says:

    "The application should be fast."

What should QA do?

Answer:

Ask for clarification and request a measurable/testable
performance expectation.


Q2.

Requirement says:

    "User can upload files."

What should QA ask?

Answer:

Ask about file types, size limits, number of files, invalid files,
security restrictions, error behavior, and other applicable rules.


Q3.

A developer asks:

    "Why do you need acceptance criteria?"

Answer:

Acceptance criteria provide clear conditions that can be used to
determine whether the requirement/user story is complete and
acceptable.


Q4.

A new requirement changes maximum file size from 10 MB to 25 MB.

What should QA do?

Answer:

Perform impact analysis and update affected test cases, test data,
automation, traceability, and regression coverage as applicable.


Q5.

You have 100 requirements but only 70 are mapped to test cases.

What should QA investigate?

Answer:

Identify missing test coverage for the unmapped requirements and
update the traceability mapping.

============================================================
49. FINAL KEY TAKEAWAYS
============================================================

1. Requirements define what the software is expected to satisfy.

2. Requirement Analysis is one of the most important early QA
   activities.

3. Business requirements explain the business need.

4. Functional requirements describe system behavior and features.

5. Non-functional requirements describe quality characteristics
   and constraints.

6. Technical requirements describe technical conditions and
   constraints.

7. BRD generally focuses on business needs.

8. SRS describes software/system requirements in greater detail.

9. User Stories describe capabilities from the user's perspective.

10. Acceptance Criteria define conditions for acceptance.

11. RTM connects requirements with test coverage.

12. QA should identify ambiguity instead of making assumptions.

13. Requirement changes require impact analysis.

14. Strong requirement analysis leads to stronger test scenarios,
    test cases, and overall software quality.
