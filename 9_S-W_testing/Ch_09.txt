CHAPTER 9 — TYPES OF SOFTWARE TESTING
============================================================

Goal:
Understand the major categories of software testing and learn
when, why, and how each type is used in real QA projects.

This chapter covers:

    1. Functional Testing
    2. Non-Functional Testing
    3. Manual Testing
    4. Automation Testing
    5. Black Box Testing
    6. White Box Testing
    7. Grey Box Testing
    8. Positive Testing
    9. Negative Testing
   10. Exploratory Testing
   11. Ad-Hoc Testing

============================================================
1. WHAT ARE TESTING TYPES?
============================================================

Testing types describe different approaches, purposes, or
characteristics of software testing.

Different types answer different questions.

Examples:

    Functional Testing
        → Does the software perform the required function?

    Performance Testing
        → How well does the software perform under load?

    Security Testing
        → Is the software protected against security problems?

    Positive Testing
        → Does the system work with valid input?

    Negative Testing
        → Does the system handle invalid/unexpected input?

    Black Box Testing
        → Can we test behavior without knowing internal code?

============================================================

Software testing can be viewed from multiple dimensions.

============================================================
3. FUNCTIONAL TESTING
============================================================

Definition:

Functional Testing verifies whether software functions behave
according to specified requirements.

Main question:

    "Does the system do what it is supposed to do?"

Functional testing focuses on:

    - Features
    - Business rules
    - User actions
    - Inputs
    - Outputs
    - Expected behavior


============================================================
4. FUNCTIONAL TESTING EXAMPLE — LOGIN
============================================================

Requirement:

    User should be able to login using valid credentials.

Test:

    Username: apoorv
    Password: correct_password

Expected:

    User successfully logs in.


Another test:

    Username: apoorv
    Password: incorrect_password

Expected:

    Appropriate error message is displayed.


Both tests validate login functionality.


============================================================
5. FUNCTIONAL TESTING EXAMPLES
============================================================

E-commerce:

    - Login
    - Registration
    - Product search
    - Product filtering
    - Add to cart
    - Remove from cart
    - Checkout
    - Payment
    - Order placement
    - Cancellation
    - Refund


Banking:

    - Login
    - Balance inquiry
    - Fund transfer
    - Deposit
    - Withdrawal
    - Transaction history


============================================================
6. COMMON FUNCTIONAL TESTING TYPES
============================================================

Functional testing may include:

    - Unit Testing
    - Integration Testing
    - System Testing
    - Acceptance Testing
    - Smoke Testing
    - Sanity Testing
    - Regression Testing
    - Retesting
    - End-to-End Testing

Important:

These terms can represent different dimensions of testing.
Do not assume that every functional testing category is always
performed at the same testing level.


============================================================
7. NON-FUNCTIONAL TESTING
============================================================

Definition:

Non-Functional Testing evaluates characteristics of the software
other than specific business functions.

Main question:

    "How well does the system work?"


Examples:

    Performance
    Security
    Usability
    Reliability
    Scalability
    Compatibility
    Accessibility


============================================================
8. FUNCTIONAL vs NON-FUNCTIONAL
============================================================

FUNCTIONAL:

    Focus:
        What the system does.

    Example:
        User can transfer money.


NON-FUNCTIONAL:

    Focus:
        How well the system performs.

    Example:
        Money transfer response should complete within the
        required performance target under expected load.


Memory:

    FUNCTIONAL
        = WHAT

    NON-FUNCTIONAL
        = HOW WELL


============================================================
9. NON-FUNCTIONAL TESTING EXAMPLES
============================================================

Performance Testing
    → Measures behavior under load.

Security Testing
    → Checks security-related risks and controls.

Usability Testing
    → Evaluates ease of use.

Compatibility Testing
    → Checks behavior across supported environments.

Accessibility Testing
    → Evaluates accessibility for users with disabilities.

Reliability Testing
    → Evaluates consistent operation over time.

Scalability Testing
    → Evaluates behavior as workload/resources/users increase.


============================================================
10. MANUAL TESTING
============================================================

Definition:

Manual Testing is testing performed by a human without using
automated test scripts to execute the test steps.

The tester:

    1. Understands requirement
    2. Creates test scenarios
    3. Creates test cases
    4. Executes tests
    5. Compares actual vs expected result
    6. Reports defects
    7. Retests fixes
    8. Performs regression testing


============================================================
11. MANUAL TESTING EXAMPLE
============================================================

Tester opens:

    https://example.com/login

Then manually:

    Enter username
    Enter password
    Click Login
    Observe result

Expected:

    Dashboard should open.

Actual:

    Error message appears.

Tester:

    → Records evidence
    → Creates bug report
    → Assigns severity/priority
    → Tracks defect


============================================================
12. ADVANTAGES OF MANUAL TESTING
============================================================

    - Useful for exploratory testing
    - Useful for usability evaluation
    - Human observation is valuable
    - Good for changing requirements
    - Useful when automation is not cost-effective
    - Helpful for new features during early development


============================================================
13. LIMITATIONS OF MANUAL TESTING
============================================================

    - Time-consuming for repetitive tests
    - Human error is possible
    - Difficult to repeat very large test suites quickly
    - Regression can become expensive
    - Large-scale execution requires more effort


============================================================
14. AUTOMATION TESTING
============================================================

Definition:

Automation Testing uses software tools/scripts/frameworks to
execute tests and evaluate results automatically or
semi-automatically.

Examples:

    Selenium
    Playwright
    PyTest
    TestNG
    REST Assured
    Postman/Newman


============================================================
15. AUTOMATION TESTING EXAMPLE
============================================================

Instead of manually performing:

    Open browser
    Login
    Search product
    Add product to cart
    Logout

An automation script performs these steps.

Example conceptual flow:

    test_login()
        ↓
    open_browser()
        ↓
    enter_username()
        ↓
    enter_password()
        ↓
    click_login()
        ↓
    assert_dashboard()


============================================================
16. ADVANTAGES OF AUTOMATION
============================================================

    - Fast repeated execution
    - Useful for regression suites
    - Consistent execution
    - Can run unattended
    - Supports CI/CD
    - Useful for large test suites
    - Generates repeatable results
    - Can support parallel execution


============================================================
17. LIMITATIONS OF AUTOMATION
============================================================

Automation is NOT a complete replacement for human testing.

Limitations:

    - Initial development cost
    - Maintenance required
    - Flaky tests can occur
    - Poorly designed tests provide poor value
    - Not everything should be automated
    - UI changes may require script maintenance


============================================================
18. WHAT SHOULD BE AUTOMATED?
============================================================

Good candidates:

    - Stable functionality
    - Repetitive tests
    - Regression tests
    - Smoke tests
    - Large data-driven tests
    - Frequently executed tests
    - Critical business flows
    - API tests
    - Cross-browser tests


============================================================
19. WHAT MAY NOT BE IDEAL FOR AUTOMATION?
============================================================

Examples:

    - One-time tests
    - Highly unstable functionality
    - Exploratory testing
    - Usability evaluation
    - Tests requiring subjective human judgment
    - Very low-value tests

Important:

The decision depends on project requirements, maintenance cost,
risk, stability, and return on investment.


============================================================
20. MANUAL vs AUTOMATION
============================================================

+-------------------+-------------------------+
| Manual            | Automation              |
+-------------------+-------------------------+
| Human executes    | Tool/script executes   |
| Slower repetition | Fast repetition        |
| Flexible          | Highly repeatable      |
| Good exploratory  | Good regression        |
| Lower initial     | Higher initial effort  |
| Human observation | Programmatic checks    |
+-------------------+-------------------------+


============================================================
21. BLACK BOX TESTING
============================================================

Definition:

Black Box Testing tests software behavior without requiring
knowledge of the internal implementation/code.

The tester focuses on:

    Input
      ↓
    Software
      ↓
    Output


Example:

Login page:

    Input:
        Username + Password

    Output:
        Dashboard or error


The tester does not need to know the internal login code.


============================================================
22. BLACK BOX TESTING FOCUS
============================================================

Focus:

    - Requirements
    - Inputs
    - Outputs
    - User behavior
    - Business rules
    - External behavior


Common techniques include:

    - Equivalence Partitioning
    - Boundary Value Analysis
    - Decision Table Testing
    - State Transition Testing
    - Use Case Testing
    - Error Guessing

These techniques are covered in greater detail in later chapters.


============================================================
23. BLACK BOX EXAMPLE
============================================================

Requirement:

    Age must be between 18 and 60.

Tester can test:

    17
    18
    30
    60
    61

The tester focuses on expected behavior.

The tester does not need to inspect the source code.


============================================================
24. WHITE BOX TESTING
============================================================

Definition:

White Box Testing tests software with knowledge of its internal
implementation, code, logic, control flow, or structure.

Main focus:

    "How does the internal code work?"


============================================================
25. WHITE BOX EXAMPLE
============================================================

Consider:

    if (age >= 18)
        allowAccess();
    else
        denyAccess();


White box testing can consider:

    - Both branches
    - Conditions
    - Paths
    - Statements
    - Internal logic


============================================================
26. WHITE BOX TESTING CONCEPTS
============================================================

Common concepts:

    Statement Coverage
    Branch Coverage
    Condition Coverage
    Path Coverage

These techniques help evaluate how much of the code structure
has been exercised by tests.


============================================================
27. WHO COMMONLY PERFORMS WHITE BOX TESTING?
============================================================

Commonly:

    - Developers
    - SDETs
    - Automation engineers
    - QA engineers with programming knowledge
    - Specialized testing teams


============================================================
28. BLACK BOX vs WHITE BOX
============================================================

BLACK BOX:

    Internal code knowledge:
        Not required

    Focus:
        External behavior

    Typical perspective:
        User/requirements

    Example:
        Enter input and verify output


WHITE BOX:

    Internal code knowledge:
        Used

    Focus:
        Internal logic/structure

    Typical perspective:
        Code/design


Memory:

    BLACK BOX
        → Outside view

    WHITE BOX
        → Inside view


============================================================
29. GREY BOX TESTING
============================================================

Definition:

Grey Box Testing is testing where the tester has partial
knowledge of the internal system/design.

It lies conceptually between black box and white box testing.


============================================================
30. GREY BOX EXAMPLE
============================================================

Suppose a tester knows:

    - Database structure
    - API architecture
    - Authentication mechanism
    - Some system design details

But the tester does not inspect or fully test the application's
internal source code.

The tester uses this partial knowledge to create stronger tests.


============================================================
31. BLACK vs WHITE vs GREY BOX
============================================================

                TESTING

                    |
       +------------+------------+
       |            |            |
    BLACK         GREY        WHITE
       |            |            |
    No/limited   Partial      Internal
    internal     knowledge    knowledge
    knowledge


Simple memory:

    BLACK
        → No internal view

    GREY
        → Partial internal view

    WHITE
        → Internal/code view


============================================================
32. POSITIVE TESTING
============================================================

Definition:

Positive Testing verifies that the system works correctly when
provided with valid and expected input.

Question:

    "Does the system work correctly when the user does the
     correct thing?"


============================================================
33. POSITIVE TESTING EXAMPLE
============================================================

Login requirement:

    Valid username
    Valid password

Input:

    Username = valid_user
    Password = valid_password

Expected:

    Login successful.


This is positive testing.


============================================================
34. NEGATIVE TESTING
============================================================

Definition:

Negative Testing verifies how the system behaves when invalid,
unexpected, incorrect, or unacceptable input is provided.

Question:

    "Does the system handle incorrect input correctly?"


============================================================
35. NEGATIVE TESTING EXAMPLE
============================================================

Login:

    Username = valid_user
    Password = wrong_password

Expected:

    Login should fail safely and display an appropriate message.

Other examples:

    Empty username
    Empty password
    Invalid email
    Extremely long input
    Unsupported characters
    Invalid file format


============================================================
36. POSITIVE vs NEGATIVE TESTING
============================================================

POSITIVE:

    Valid input
       ↓
    Expected successful behavior


NEGATIVE:

    Invalid/unexpected input
       ↓
    Expected safe/error behavior


Example:

    Age field accepts 18–60.

Positive:

    18
    25
    60

Negative:

    17
    61
    abc
    empty


============================================================
37. EXPLORATORY TESTING
============================================================

Definition:

Exploratory Testing is an approach where learning, test design,
and execution occur together.

Instead of strictly following only predefined test cases, the
tester explores the application and uses observations to guide
further testing.


============================================================
38. EXPLORATORY TESTING EXAMPLE
============================================================

Tester receives a new shopping application.

Instead of only following predefined cases:

    Login
    Search
    Add to cart

The tester explores:

    Search unusual terms
    Navigate rapidly
    Change filters
    Refresh pages
    Open multiple tabs
    Try unexpected navigation
    Observe error messages
    Test unusual combinations


The tester learns from the application while testing it.


============================================================
39. EXPLORATORY TESTING CHARACTERISTICS
============================================================

    - Simultaneous learning and testing
    - Tester creativity is important
    - Useful when requirements are incomplete
    - Useful for discovering unexpected problems
    - Can complement scripted testing
    - Often uses sessions/charters in structured exploratory
      approaches


============================================================
40. WHEN TO USE EXPLORATORY TESTING
============================================================

Useful when:

    - New feature has limited documentation
    - Requirements are changing
    - Time is limited
    - Tester wants to discover unexpected behavior
    - Existing test cases do not cover enough possibilities
    - Product needs quick investigation


============================================================
41. AD-HOC TESTING
============================================================

Definition:

Ad-Hoc Testing is informal testing performed without detailed
predefined test cases, often with the goal of quickly discovering
defects.

It relies heavily on tester intuition and experience.


============================================================
42. AD-HOC EXAMPLE
============================================================

Tester opens a login page and informally tries:

    Empty username
    Empty password
    Very long username
    Special characters
    Copy/paste
    Refresh
    Back button
    Multiple rapid clicks


The tester is not necessarily following a formal test-case
document.


============================================================
43. EXPLORATORY vs AD-HOC
============================================================

EXPLORATORY:

    - More structured than random testing
    - Tester learns and tests simultaneously
    - Can use a test charter/session
    - Purposeful exploration


AD-HOC:

    - Informal
    - Less structured
    - Relies heavily on intuition
    - Often quick and unscripted


Memory:

    EXPLORATORY
        = Explore with purpose

    AD-HOC
        = Informal testing


============================================================
44. IMPORTANT: THESE TYPES CAN OVERLAP
============================================================

A real test can belong to multiple categories.

Example:

    Tester manually tests an e-commerce checkout.

It can be:

    Manual Testing
        +
    Functional Testing
        +
    Black Box Testing
        +
    Positive Testing
        +
    System Testing


Another test:

    Automated API regression test

Can be:

    Automation Testing
        +
    Functional Testing
        +
    Black Box Testing
        +
    Regression Testing
        +
    Integration/System context


Testing classifications are not always mutually exclusive.

47. INTERVIEW QUESTIONS
============================================================

Q1. What is Functional Testing?

Answer:

Functional testing verifies whether software functions behave
according to specified requirements.


Q2. What is Non-Functional Testing?

Answer:

Non-functional testing evaluates quality characteristics such as
performance, security, usability, reliability, and compatibility.


Q3. What is Manual Testing?

Answer:

Manual testing is testing performed by a human without using
automated test scripts to execute the test steps.


Q4. What is Automation Testing?

Answer:

Automation testing uses software tools, scripts, or frameworks
to execute tests and evaluate results automatically or
semi-automatically.


Q5. What is Black Box Testing?

Answer:

Black box testing evaluates external behavior without requiring
knowledge of the internal implementation.


Q6. What is White Box Testing?

Answer:

White box testing uses knowledge of internal code, logic, or
structure to design and execute tests.


Q7. What is Grey Box Testing?

Answer:

Grey box testing uses partial knowledge of the internal system
or design while primarily testing its external behavior.


Q8. What is Positive Testing?

Answer:

Positive testing verifies behavior using valid and expected
inputs.


Q9. What is Negative Testing?

Answer:

Negative testing verifies how the software handles invalid,
unexpected, or unacceptable inputs.


Q10. What is Exploratory Testing?

Answer:

Exploratory testing combines learning, test design, and execution,
allowing the tester to explore the system and adapt testing based
on observations.


Q11. What is Ad-Hoc Testing?

Answer:

Ad-hoc testing is informal, largely unscripted testing intended
to quickly discover defects.


============================================================
48. SCENARIO-BASED INTERVIEW QUESTIONS
============================================================

Q1.

You enter valid username and password and verify successful login.

Answer:

    Positive + Functional Testing


Q2.

You enter invalid password and verify an appropriate error.

Answer:

    Negative + Functional Testing


Q3.

You test an application without looking at its source code.

Answer:

    Black Box Testing


Q4.

You examine branches and conditions in source code.

Answer:

    White Box Testing


Q5.

You know the database schema and API architecture but do not
have complete source-code knowledge.

Answer:

    Grey Box Testing


Q6.

You repeatedly run the same login and checkout tests after every
release.

Answer:

    Automation Testing may be appropriate, commonly as part of
    Regression Testing.


Q7.

A new feature has limited documentation and you actively explore
different workflows to discover unexpected problems.

Answer:

    Exploratory Testing


Q8.

You quickly try unusual inputs without preparing detailed test
cases.

Answer:

    Ad-Hoc Testing

49. COMMON INTERVIEW TRAPS
============================================================

TRAP 1:

"Automation testing means no manual testing is required."

Incorrect.

Automation complements manual testing.

------------------------------------------------------------

TRAP 2:

"Black box testing means tester knows nothing about the system."

Not necessarily.

The key idea is that internal implementation/code knowledge is
not required for the test approach.

------------------------------------------------------------

TRAP 3:

"Positive testing means the test must pass."

Incorrect.

Positive testing means valid/expected inputs are used.

The system can still fail the test.

------------------------------------------------------------

TRAP 4:

"Negative testing means intentionally breaking production."

Incorrect.

Negative testing safely verifies how software handles invalid
or unexpected inputs.

------------------------------------------------------------

TRAP 5:

"Exploratory testing means random testing."

Not necessarily.

Good exploratory testing is purposeful and guided by learning,
risk, observations, and tester expertise.

52. FINAL KEY TAKEAWAYS
============================================================

1. Testing types provide different ways to evaluate software.

2. Functional testing verifies what the software does.

3. Non-functional testing evaluates quality characteristics.

4. Manual testing depends on human execution.

5. Automation uses tools/scripts to execute repeatable tests.

6. Black box testing focuses on external behavior.

7. White box testing considers internal implementation.

8. Grey box testing uses partial internal knowledge.

9. Positive testing uses valid/expected inputs.

10. Negative testing checks invalid/unexpected inputs.

11. Exploratory testing combines learning, test design, and
    execution.

12. Ad-hoc testing is informal and largely unscripted.

13. One test can belong to several classifications at once.

14. A job-ready QA engineer should understand not only definitions
    but also when each approach is useful.
