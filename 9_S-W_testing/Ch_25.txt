25.1 MOBILE TESTING INTRODUCTION
======================================================================

Mobile testing is the process of testing applications that
run on mobile devices.

The syllabus specifically includes:

    • Android
    • iOS
    • Native applications
    • Hybrid applications
    • Mobile web applications


Mobile testing verifies:

    • Functionality
    • UI behavior
    • Navigation
    • Installation
    • Compatibility
    • Permissions
    • Network behavior
    • Device behavior
    • Orientation
    • Notifications
    • Battery-related behavior
    • Interruptions
    • Offline/online behavior
    • Background/foreground behavior


Mobile applications are different from traditional desktop
applications because the application operates in a more
variable environment.


======================================================================
25.2 WHY MOBILE TESTING IS DIFFERENT
======================================================================

A desktop web application may primarily be tested using:

    Browser
       +
    Operating System
       +
    Screen


Mobile applications introduce additional variables:

    Device
       +
    Mobile OS
       +
    Screen size
       +
    Orientation
       +
    Network
       +
    Battery
       +
    Permissions
       +
    Notifications
       +
    Calls/messages
       +
    Background/foreground state


Therefore, mobile testing requires broader environmental
coverage.


Example:

    Desktop:

        User opens website
             ↓
        Browser
             ↓
        Application


    Mobile:

        User opens application
             ↓
        Mobile OS
             ↓
        Device
             ↓
        Network
             ↓
        Application


The application can also be interrupted by:

    • Phone calls
    • Notifications
    • Messages
    • Low battery
    • Network changes
    • Application switching


These conditions must be considered during testing.


======================================================================
25.3 ANDROID AND iOS
======================================================================

The syllabus identifies Android and iOS as the major
mobile platforms to understand.


ANDROID
-------

Android applications run on Android devices.

Testing may need to consider differences in:

    • Device models
    • Screen sizes
    • Android versions
    • Hardware capabilities
    • Manufacturer-specific behavior


Examples of Android devices may have different:

    • Screen dimensions
    • RAM
    • CPU capabilities
    • OS versions
    • Manufacturer customizations


Therefore, an application may behave differently across
different Android environments.


iOS
---

iOS is Apple's mobile operating system.

iOS testing commonly involves:

    • iPhone
    • iPad where applicable
    • Different supported iOS versions
    • Different screen sizes
    • Different device capabilities


A QA Engineer should test according to the application's
supported iOS devices and versions.


======================================================================
25.4 TYPES OF MOBILE APPLICATIONS
======================================================================

The syllabus identifies three important categories:

    1. Native applications
    2. Hybrid applications
    3. Mobile web applications


These applications differ in how they are built and
therefore may require different testing approaches.


======================================================================
25.5 NATIVE APPLICATIONS
======================================================================

A native application is developed specifically for a
particular mobile platform.

Examples:

    Android application
        → designed for Android

    iOS application
        → designed for iOS


Native applications can interact closely with device
capabilities.

Examples include:

    • Camera
    • GPS/location
    • Notifications
    • Files
    • Contacts
    • Device sensors


Therefore, testing should consider both application
functionality and device interaction.


--------------------------------------------------------------
NATIVE APP TESTING EXAMPLE
--------------------------------------------------------------

Suppose an application contains:

    "Take Profile Photo"


Tester should verify:

    1. Camera permission.
    2. Camera opens correctly.
    3. Photo can be captured.
    4. Photo is returned to application.
    5. Photo is displayed correctly.
    6. Cancel behavior works.
    7. Permission denial is handled correctly.


======================================================================
25.6 HYBRID APPLICATIONS
======================================================================

A hybrid application combines characteristics of web
technologies and mobile application behavior.

For QA purposes, hybrid applications may require testing
of both:

    • Application UI/functionality
    • Web-based components


Testing may therefore involve areas associated with both
mobile applications and web applications.


Example:

    Mobile application
          |
          +-- Native shell
          |
          +-- Web-based UI/component
          |
          +-- Backend/API


A QA Engineer may need to investigate both the mobile
application behavior and the underlying web/API behavior.


======================================================================
25.7 MOBILE WEB APPLICATIONS
======================================================================

A mobile web application is accessed through a mobile
browser rather than necessarily being installed as a
native application.


Example:

    Mobile device
         ↓
    Mobile browser
         ↓
    Web application
         ↓
    Backend/API


Testing includes:

    • Responsive layout
    • Navigation
    • Forms
    • Touch interaction
    • Browser compatibility
    • Network behavior
    • Screen sizes
    • Orientation


This connects mobile testing with the browser compatibility
and responsive testing concepts from previous chapters.


======================================================================
25.8 MOBILE TESTING AREAS
======================================================================

The syllabus identifies several important mobile testing
areas.


--------------------------------------------------------------
1. INSTALLATION
--------------------------------------------------------------

Verify that the application can be installed correctly.

Test:

    • Installation
    • Installation success/failure
    • First launch
    • Required permissions
    • Initial configuration


Example:

    Download application
        ↓
    Install
        ↓
    Open
        ↓
    Verify first-launch behavior


--------------------------------------------------------------
2. UNINSTALLATION
--------------------------------------------------------------

Verify that the application can be removed correctly.

Test:

    • Uninstall
    • Application removal
    • Behavior after reinstall
    • Relevant stored state according to requirements


--------------------------------------------------------------
3. UPGRADE
--------------------------------------------------------------

Verify application behavior when upgrading from an
older version to a newer version.


Example:

    Version 1
       ↓
    User data/state
       ↓
    Upgrade
       ↓
    Version 2


Verify:

    • Application launches
    • Existing data behaves correctly
    • User remains in the expected state
    • Features work correctly


--------------------------------------------------------------
4. PERMISSIONS
--------------------------------------------------------------

Mobile applications may request access to device
capabilities.

Examples:

    • Camera
    • Microphone
    • Location
    • Notifications
    • Files/photos


Test both:

    Permission ALLOWED

and:

    Permission DENIED


Example:

    Camera permission:
        Allow
        ↓
        Camera works

    Camera permission:
        Deny
        ↓
        Application should handle denial correctly


A permission denial should not unexpectedly crash
the application.


--------------------------------------------------------------
5. NOTIFICATIONS
--------------------------------------------------------------

Verify notifications behave correctly.

Test:

    • Notification appears when expected
    • Notification content
    • Tapping notification
    • Navigation after tapping
    • Notification behavior when app is foreground
    • Notification behavior when app is background


Example:

    New order notification
         ↓
    User taps notification
         ↓
    Application opens
         ↓
    Correct order page displayed


--------------------------------------------------------------
6. NETWORK CHANGES
--------------------------------------------------------------

Mobile users may switch between network conditions.

Examples:

    Wi-Fi
      ↓
    Mobile data


or:

    Connected
      ↓
    Disconnected


or:

    Strong network
      ↓
    Weak network


Test how the application behaves during these changes.


--------------------------------------------------------------
7. BATTERY
--------------------------------------------------------------

Mobile applications operate under battery constraints.

Testing can include behavior under:

    • Low battery
    • Charging
    • Battery-saving conditions


The application should behave according to product
requirements without unexpected failures.


--------------------------------------------------------------
8. ORIENTATION
--------------------------------------------------------------

Mobile devices can commonly change between:

    Portrait

and:

    Landscape


Example:

    Portrait
       ↓
    Rotate device
       ↓
    Landscape


Verify:

    • Layout
    • Content
    • Navigation
    • Input state
    • Data persistence
    • Controls


The application should handle supported orientation
changes correctly.


--------------------------------------------------------------
9. SCREENS
--------------------------------------------------------------

Different mobile devices can have different screen sizes.

Test:

    • Small screens
    • Medium screens
    • Large screens


Verify:

    • Text
    • Images
    • Buttons
    • Forms
    • Menus
    • Navigation


No important content should become inaccessible
because of screen size.


--------------------------------------------------------------
10. INTERRUPTIONS
--------------------------------------------------------------

Mobile applications can be interrupted by external events.

Examples:

    • Phone call
    • Message
    • Notification
    • System dialog
    • Another application


Example:

    User is filling a payment form
           ↓
    Incoming phone call
           ↓
    User returns to application


Verify:

    • Application state
    • Entered data
    • Navigation
    • Recovery


--------------------------------------------------------------
11. OFFLINE
--------------------------------------------------------------

Test application behavior when network connectivity
is unavailable.

Example:

    Connected
       ↓
    Network lost
       ↓
    User performs action


Expected behavior depends on requirements.

Possible behavior:

    • Display appropriate error
    • Show offline state
    • Queue operation
    • Allow offline functionality


The tester should validate the actual requirement rather
than assuming one universal behavior.


--------------------------------------------------------------
12. BACKGROUND / FOREGROUND
--------------------------------------------------------------

Mobile applications frequently move between states.


Example:

    Application
       ↓
    Foreground
       ↓
    User opens another app
       ↓
    Background
       ↓
    User returns
       ↓
    Foreground


Verify:

    • Application state
    • Data
    • Session
    • Current screen
    • Pending operation
    • User input


======================================================================
25.9 MOBILE APPLICATION STATE
======================================================================

A mobile application can move through different states.


              +----------------+
              |   FOREGROUND   |
              +----------------+
                      |
                      | User leaves
                      v
              +----------------+
              |   BACKGROUND   |
              +----------------+
                      |
                      | User returns
                      v
              +----------------+
              |   FOREGROUND   |
              +----------------+


Other events can occur during these transitions:

    • Notification
    • Phone call
    • Network change
    • System interruption
    • Rotation


A QA Engineer should verify that important application
state is handled correctly.


======================================================================
25.10 MOBILE TESTING MATRIX
======================================================================

A mobile test matrix can organize coverage.


Example:

    --------------------------------------------------------------
    Platform     Device Type     Orientation     Network
    --------------------------------------------------------------
    Android      Mobile          Portrait        Wi-Fi
    Android      Mobile          Landscape       Wi-Fi
    Android      Mobile          Portrait        Mobile Data
    iOS          Mobile          Portrait        Wi-Fi
    iOS          Mobile          Landscape       Wi-Fi
    iOS          Mobile          Portrait        Mobile Data
    --------------------------------------------------------------


The actual combinations should be selected based on:

    • Supported devices
    • Supported OS versions
    • Target users
    • Business requirements
    • Risk

25.11 PRACTICAL SCENARIO — INSTALLATION
======================================================================

Requirement:

    User should be able to install and launch
    the application successfully.


Test:

    1. Download application.
    2. Install application.
    3. Launch application.
    4. Verify first screen.
    5. Verify required permissions.
    6. Verify basic navigation.


Expected:

    Application installs and launches successfully.


Possible defects:

    • Installation fails
    • Application crashes on launch
    • Required screen does not appear
    • Permission flow fails


======================================================================
25.12 PRACTICAL SCENARIO — PERMISSION DENIED
======================================================================

Requirement:

    Application should allow users to upload a photo.


Steps:

    1. Open upload feature.
    2. Application requests camera/photo permission.
    3. Select DENY.
    4. Continue using application.


Expected:

    Application should handle denied permission gracefully
    according to requirements.


Actual:

    Application crashes.


This should be reported as a defect.


======================================================================
25.13 PRACTICAL SCENARIO — NETWORK LOSS
======================================================================

Requirement:

    User should receive appropriate feedback
    when network connectivity is unavailable.


Steps:

    1. Open application.
    2. Login.
    3. Start an operation.
    4. Disable network.
    5. Continue operation.


Check:

    • Error message
    • Application state
    • Retry behavior
    • Data loss
    • Recovery after network restoration


Example:

    Network OFF
        ↓
    API request fails
        ↓
    Application displays appropriate message
        ↓
    Network ON
        ↓
    User retries
        ↓
    Operation succeeds


======================================================================
25.14 PRACTICAL SCENARIO — ORIENTATION CHANGE
======================================================================

Requirement:

    User should be able to rotate the device without
    losing entered information.


Steps:

    1. Open registration form.
    2. Enter information.
    3. Rotate device.
    4. Continue filling form.


Expected:

    Previously entered data remains available
    according to the application's requirements.


Possible defect:

    All entered information disappears after rotation.


======================================================================
25.15 PRACTICAL SCENARIO — INTERRUPTION
======================================================================

Scenario:

    User is entering payment information.

    Incoming call occurs.

    User answers call.

    User returns to application.


Verify:

    • Payment screen
    • Entered information
    • Application state
    • Session
    • Navigation


Expected:

    Application should recover according to requirements.


======================================================================
25.16 PRACTICAL SCENARIO — BACKGROUND/FOREGROUND
======================================================================

Steps:

    1. Login.
    2. Navigate to product page.
    3. Put application in background.
    4. Wait.
    5. Return to application.


Check:

    • Product page
    • Session
    • Data
    • Navigation
    • Application stability


Possible defect:

    Application returns to an unexpected screen
    or loses important user-entered data.


======================================================================
25.17 MOBILE TESTING VS WEB TESTING
======================================================================

WEB TESTING
-----------

Typical considerations:

    • Browser
    • Web UI
    • HTTP requests
    • Responsive layout
    • Browser compatibility


MOBILE APP TESTING
------------------

Additional considerations:

    • Mobile OS
    • Device
    • Installation
    • Permissions
    • Notifications
    • Orientation
    • Battery
    • Interruptions
    • Background/foreground
    • Mobile network changes


Mobile web testing may share many web-testing concerns,
while native/hybrid apps introduce additional mobile
device and OS behavior.


======================================================================
25.18 NATIVE vs HYBRID vs MOBILE WEB
======================================================================

    NATIVE
    ------
    Platform-specific application.

    Testing focus:
        Device features
        OS behavior
        UI
        Permissions
        Installation
        Notifications
        Network
        Device state


    HYBRID
    ------
    Combination of mobile application behavior
    and web-based components.

    Testing focus:
        Mobile behavior
        Web components
        APIs
        Device integration


    MOBILE WEB
    ----------
    Web application accessed through mobile browser.

    Testing focus:
        Browser
        Responsive UI
        Navigation
        Forms
        Network
        Browser compatibility

25.19 MOBILE TESTING INTERVIEW QUESTIONS
======================================================================

Q1. What is mobile testing?

Answer:
Mobile testing is the process of testing applications
on mobile platforms such as Android and iOS across
supported devices and environments.


Q2. What are the major types of mobile applications?

Answer:

    • Native
    • Hybrid
    • Mobile web


Q3. What is a native application?

Answer:
A native application is developed specifically for
a particular mobile platform and can interact closely
with platform/device capabilities.


Q4. What is a hybrid application?

Answer:
A hybrid application combines characteristics of
mobile application behavior with web-based components.


Q5. What is a mobile web application?

Answer:
A mobile web application is a web application accessed
through a mobile browser.


Q6. What is permission testing?

Answer:
Permission testing verifies application behavior when
permissions are granted, denied, or otherwise changed.


Q7. What happens if a user denies camera permission?

Answer:
The application should handle the denial according
to its requirements and should not unexpectedly fail
or crash.


Q8. What is interruption testing?

Answer:
It verifies application behavior when external events
such as calls, messages, notifications, or system events
interrupt the application.


Q9. What is orientation testing?

Answer:
It verifies application behavior when the device changes
between supported orientations such as portrait and
landscape.


Q10. What is background/foreground testing?

Answer:
It verifies application behavior when the application
moves into the background and later returns to the
foreground.


Q11. Why is network testing important for mobile applications?

Answer:
Mobile users may experience changing connectivity,
including Wi-Fi/mobile-data transitions, weak networks,
and network loss.


Q12. What would you test after disabling the network?

Answer:

    • Error handling
    • Application state
    • Retry behavior
    • Data handling
    • Recovery after reconnecting

25.20 INTERVIEW SCENARIO
======================================================================

INTERVIEWER:

    "A mobile application works correctly when opened,
     but after receiving a phone call and returning to
     the application, entered data is lost. How would
     you test and report it?"


STRONG ANSWER:

    "I would reproduce the issue consistently and verify
     whether the behavior violates the requirements.

     I would test the same flow across relevant supported
     devices and OS versions.

     I would record:

         • Device
         • OS version
         • Application version
         • Steps
         • Data entered
         • Interruption
         • Result after returning

     I would then create a defect with clear expected
     and actual results and supporting evidence."

25.21 MOBILE TESTING BUG REPORT EXAMPLE
======================================================================

BUG TITLE
---------

    Entered registration data is lost after returning
    from an incoming call


ENVIRONMENT
-----------

    Platform:
        Android

    Device:
        Supported Android device

    Application:
        Relevant application version


PRECONDITION
------------

    Registration form is open.


STEPS
-----

    1. Open registration form.
    2. Enter required information.
    3. Receive an incoming call.
    4. Answer the call.
    5. End the call.
    6. Return to the application.


EXPECTED
--------

    Previously entered registration data should remain
    available according to the requirement.


ACTUAL
------

    Entered data is lost.


EVIDENCE
--------

    • Screenshot
    • Screen recording if available
    • Device/OS information

CHAPTER 25 — FINAL TAKEAWAY
======================================================================

Mobile testing is not simply:

    "Open the application and check the buttons."


A professional mobile QA Engineer thinks about:

    APPLICATION
         +
    DEVICE
         +
    OPERATING SYSTEM
         +
    SCREEN
         +
    ORIENTATION
         +
    NETWORK
         +
    PERMISSIONS
         +
    NOTIFICATIONS
         +
    INTERRUPTIONS
         +
    BACKGROUND/FOREGROUND
         +
    BATTERY


The key mindset is:

    "What happens when the real-world mobile environment
     changes while the user is using the application?"


That is the major difference between basic functional
testing and strong mobile testing.
