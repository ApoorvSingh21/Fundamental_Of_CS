1. INTRODUCTION TO TEST DOCUMENTATION
====================================================================

Test Documentation is the process of creating and maintaining
documents/artifacts that describe testing activities.

It helps the QA team record:

    - What needs to be tested
    - How it will be tested
    - What data is required
    - What was executed
    - What passed
    - What failed
    - What defects were found
    - What requirements were covered
    - What the final testing status was


In simple words:

    Test Documentation
          =
    Written record of testing activities and results.


Typical testing flow:

    Requirements
          ↓
    Test Plan
          ↓
    Test Scenarios
          ↓
    Test Cases
          ↓
    Test Data
          ↓
    Test Execution
          ↓
    Defect Reports
          ↓
    Regression Testing
          ↓
    Test Summary Report
          ↓
    Requirement Traceability


====================================================================
2. WHY TEST DOCUMENTATION IS REQUIRED
====================================================================

Test documentation helps QA teams to:

    1. Organize testing
    2. Track requirements
    3. Define test coverage
    4. Maintain consistency
    5. Record execution results
    6. Track defects
    7. Support regression testing
    8. Communicate testing status
    9. Provide evidence of testing
    10. Identify missing coverage


Example:

Suppose an e-commerce application has:

    Login
    Search
    Cart
    Checkout
    Payment

Without documentation, a tester may forget important scenarios.

With documentation:

    Login       → Covered
    Search      → Covered
    Cart        → Covered
    Checkout    → Covered
    Payment     → Covered

====================================================================
4. TEST SCENARIO
====================================================================

A Test Scenario is a high-level condition or functionality that
needs to be tested.

It describes:

    WHAT should be tested?


Example:

Application:
    E-Commerce

Test Scenarios:

    TS01 → Verify user registration
    TS02 → Verify user login
    TS03 → Verify product search
    TS04 → Verify adding product to cart
    TS05 → Verify checkout
    TS06 → Verify payment
    TS07 → Verify order history


A scenario does NOT normally provide detailed execution steps.


====================================================================
5. TEST SCENARIO EXAMPLE
====================================================================

Feature:
    Login

Possible scenarios:

    TS01:
        Verify login with valid credentials.

    TS02:
        Verify login with invalid username.

    TS03:
        Verify login with invalid password.

    TS04:
        Verify login with blank username.

    TS05:
        Verify login with blank password.

    TS06:
        Verify login with both fields blank.

    TS07:
        Verify password masking.

    TS08:
        Verify Forgot Password functionality.


Notice:

Scenario = WHAT to test.

Detailed steps come later in Test Cases.


====================================================================
6. TEST CASE
====================================================================

A Test Case is a detailed set of instructions used to verify
a specific condition or functionality.

A test case generally contains:

    - Test Case ID
    - Test Case Title
    - Preconditions
    - Test Steps
    - Test Data
    - Expected Result
    - Actual Result
    - Status
    - Priority
    - Severity, where applicable


Example:

Test Case ID:
    TC_LOGIN_001

Title:
    Verify login with valid credentials.

Precondition:
    User has a valid registered account.

Steps:
    1. Open Login page.
    2. Enter valid username.
    3. Enter valid password.
    4. Click Login.

Expected Result:
    User should successfully log in.

Actual Result:
    Recorded during execution.

Status:
    Pass / Fail / Blocked


====================================================================
7. TEST SCENARIO VS TEST CASE
====================================================================

TEST SCENARIO:

    High-level testing idea.

Example:

    Verify Login functionality.


TEST CASE:

    Detailed procedure.

Example:

    Enter valid username.
    Enter valid password.
    Click Login.
    Verify dashboard appears.


Comparison:

+----------------+-----------------------------+
| Test Scenario  | Test Case                   |
+----------------+-----------------------------+
| High-level     | Detailed                    |
| What to test   | How to test                 |
| Less detailed  | Step-by-step                |
| Broad coverage | Specific validation         |
+----------------+-----------------------------+


Interview Question:

Q:
    What is the difference between Test Scenario and Test Case?

Answer:

    A Test Scenario identifies what functionality or condition
    should be tested, while a Test Case provides the detailed
    steps, data and expected result needed to perform that test.


====================================================================
8. TEST CONDITION
====================================================================

A Test Condition is a specific condition, rule, or aspect of
the software that needs to be verified.

Example:

Requirement:

    Password must contain at least 8 characters.


Possible test conditions:

    - Password has exactly 8 characters.
    - Password has fewer than 8 characters.
    - Password has more than 8 characters.
    - Password contains valid characters.
    - Password is empty.


Relationship:

Requirement
    ↓
Test Condition
    ↓
Test Scenario
    ↓
Test Case


The exact level of detail may vary depending on the team's
documentation approach.


====================================================================
9. TEST DATA
====================================================================

Test Data is the input information used during test execution.

Examples:

    Username
    Password
    Email
    Product ID
    Customer ID
    Order ID
    API request payload
    Database records


Example:

Login test data:

    Valid:
        user@test.com
        Test@123

    Invalid:
        wrong@test.com
        Wrong@123

    Boundary/negative:
        Empty username
        Empty password


Good test data should support:

    - Positive testing
    - Negative testing
    - Boundary testing
    - Business-rule validation
    - Data validation


====================================================================
10. TEST SUITE
====================================================================

A Test Suite is a collection/group of related test cases.

Example:

LOGIN TEST SUITE:

    TC_LOGIN_001
    TC_LOGIN_002
    TC_LOGIN_003
    TC_LOGIN_004
    TC_LOGIN_005


CART TEST SUITE:

    TC_CART_001
    TC_CART_002
    TC_CART_003
    TC_CART_004


CHECKOUT TEST SUITE:

    TC_CHECKOUT_001
    TC_CHECKOUT_002
    TC_CHECKOUT_003


Benefits:

    - Organizes test cases
    - Makes execution easier
    - Helps regression testing
    - Groups related functionality


====================================================================
11. TEST EXECUTION
====================================================================

Test Execution is the process of executing test cases against
the application and recording their results.

Typical process:

    Select Test Suite
          ↓
    Execute Test Case
          ↓
    Compare Actual vs Expected
          ↓
    Record Result
          ↓
    Pass / Fail / Blocked
          ↓
    Report Defect if required


Example:

Expected:

    User should reach Dashboard after valid login.

Actual:

    Error message appears.

Result:

    FAIL

Then:

    Defect should be reported.


====================================================================
12. TEST EXECUTION STATUS
====================================================================

Common execution results include:

    PASS
        Actual result matches expected result.

    FAIL
        Actual result does not match expected result.

    BLOCKED
        Test cannot be executed because of a dependency/problem.

    NOT EXECUTED
        Test has not yet been executed.

Example:

    TC001 → PASS
    TC002 → PASS
    TC003 → FAIL
    TC004 → BLOCKED
    TC005 → NOT EXECUTED


====================================================================
13. TEST EXECUTION RECORD
====================================================================

Example:

+---------+----------------------+----------+
| TC ID   | Test                 | Status   |
+---------+----------------------+----------+
| TC001   | Valid Login          | PASS     |
| TC002   | Invalid Password     | PASS     |
| TC003   | Blank Username       | FAIL     |
| TC004   | Forgot Password      | BLOCKED  |
| TC005   | Password Masking     | PASS     |
+---------+----------------------+----------+


This allows the team to understand current testing progress.


====================================================================
14. TEST RESULT
====================================================================

During execution:

    Expected Result
           ↓
    Actual Result
           ↓
       Compare
           ↓
    PASS / FAIL


Example:

Expected:
    Login button should redirect to Dashboard.

Actual:
    Login button redirects to Error page.

Result:
    FAIL


A failed test does not automatically mean the test case is wrong.

It may indicate a software defect, environment issue, data issue,
or another cause that needs investigation.


====================================================================
15. DEFECT DOCUMENTATION
====================================================================

When a test fails because of a software problem, QA creates a
defect/bug report.

A professional defect report can contain:

    - Bug ID
    - Title
    - Environment
    - Preconditions
    - Steps to reproduce
    - Test data
    - Expected result
    - Actual result
    - Severity
    - Priority
    - Attachments
    - Reproducibility


Example:

Bug ID:
    BUG-101

Title:
    Login fails with valid credentials.

Steps:

    1. Open Login page.
    2. Enter valid username.
    3. Enter valid password.
    4. Click Login.

Expected:
    Dashboard should open.

Actual:
    "Internal Server Error" appears.

Severity:
    High

Priority:
    High

16. TEST SUMMARY REPORT
====================================================================

A Test Summary Report is prepared after a testing cycle/release
to communicate the overall testing status.

It summarizes:

    - What was tested
    - How much was tested
    - Passed tests
    - Failed tests
    - Blocked tests
    - Defects
    - Risks
    - Overall testing status


Example:

Total Test Cases:
    100

Executed:
    95

Passed:
    88

Failed:
    7

Blocked:
    5

Critical Defects:
    0

High Defects:
    2

Overall Status:
    Testing completed with documented remaining risks.


====================================================================
17. TEST SUMMARY REPORT — IMPORTANT SECTIONS
====================================================================

A summary may contain:

    1. Project information
    2. Testing scope
    3. Testing performed
    4. Test execution statistics
    5. Defect statistics
    6. Critical issues
    7. Blocked tests
    8. Risks
    9. Limitations
    10. Overall conclusion


The exact format depends on the organization.


====================================================================
18. REQUIREMENT TRACEABILITY MATRIX — RTM
====================================================================

RTM stands for:

    Requirement Traceability Matrix


It maps requirements to corresponding test cases.

Purpose:

    To ensure that requirements are covered by testing.


Example:

+--------+-------------------+----------------+
| Req ID | Requirement       | Test Case      |
+--------+-------------------+----------------+
| R001   | User Login        | TC001, TC002   |
| R002   | Product Search    | TC003, TC004   |
| R003   | Add to Cart       | TC005, TC006   |
| R004   | Checkout          | TC007, TC008   |
+--------+-------------------+----------------+


This helps answer:

    "Which test cases validate this requirement?"


====================================================================
19. FORWARD TRACEABILITY
====================================================================

Forward traceability:

    Requirement
        ↓
    Test Case


It checks whether every requirement has corresponding tests.


Example:

R001
    ↓
TC001
TC002


R002
    ↓
TC003


Question:

    Has every requirement been tested?


====================================================================
20. BACKWARD TRACEABILITY
====================================================================

Backward traceability:

    Test Case
        ↓
    Requirement


It checks whether each test case is linked to a valid requirement.

Example:

TC001
    ↓
R001


TC002
    ↓
R001


Question:

    Does every test case have a valid requirement?


====================================================================
21. BI-DIRECTIONAL TRACEABILITY
====================================================================

Bi-directional traceability works in both directions:

    Requirement
         ↓
      Test Case
         ↓
    Requirement


It helps verify:

    1. Every requirement has test coverage.
    2. Every test case is associated with a requirement.


Example:

    R001 ←→ TC001
    R001 ←→ TC002
    R002 ←→ TC003


This provides stronger traceability.


====================================================================
22. RTM EXAMPLE — E-COMMERCE
====================================================================

Requirements:

    R001:
        User should be able to register.

    R002:
        Registered user should be able to log in.

    R003:
        User should be able to add products to cart.

    R004:
        User should be able to complete checkout.


RTM:

+--------+--------------------------+---------------------+
| Req ID | Requirement              | Test Cases          |
+--------+--------------------------+---------------------+
| R001   | Registration             | TC001, TC002, TC003 |
| R002   | Login                    | TC004, TC005, TC006 |
| R003   | Add to Cart              | TC007, TC008        |
| R004   | Checkout                 | TC009, TC010, TC011 |
+--------+--------------------------+---------------------+

====================================================================
28. TEST DOCUMENTATION BEST PRACTICES
====================================================================

1. Keep test cases clear.

2. Use unique IDs.

3. Use meaningful titles.

4. Keep steps reproducible.

5. Define expected results clearly.

6. Maintain accurate test data.

7. Keep requirements linked to tests.

8. Update documentation when requirements change.

9. Avoid unnecessary duplication.

10. Record actual execution results.

11. Attach useful evidence when appropriate.

12. Keep defect information reproducible.

13. Maintain traceability.

14. Keep reports accurate.

15. Make documentation understandable to the team.


====================================================================
29. COMMON DOCUMENTATION MISTAKES
====================================================================

Mistake 1:
    Vague test case title.

Bad:
    "Check login"

Better:
    "Verify login with valid credentials."


Mistake 2:
    Missing expected result.

Mistake 3:
    Missing test data.

Mistake 4:
    Multiple unrelated validations in one test case.

Mistake 5:
    No requirement mapping.

Mistake 6:
    Outdated test cases.

Mistake 7:
    Incorrect execution status.

Mistake 8:
    Missing defect evidence.

Mistake 9:
    Duplicate test cases.

Mistake 10:
    Not updating tests after requirement changes.

====================================================================
32. TEST EXECUTION VS TEST SUMMARY
====================================================================

TEST EXECUTION:

    Individual test cases are executed and results are recorded.


TEST SUMMARY:

    Overall testing status is communicated after the testing
    activity/cycle.


Example:

Execution:

    TC001 → PASS
    TC002 → PASS
    TC003 → FAIL


Summary:

    3 tests executed
    2 passed
    1 failed
    1 defect identified

33. REAL-WORLD QA WORKFLOW
====================================================================

Suppose a developer provides Build 1.5.

QA performs:

    1. Review requirements.
    2. Review test plan.
    3. Identify affected functionality.
    4. Prepare/maintain scenarios.
    5. Prepare test cases.
    6. Prepare test data.
    7. Execute smoke tests.
    8. Execute functional tests.
    9. Record results.
   10. Report defects.
   11. Developer fixes defects.
   12. QA retests fixes.
   13. QA performs regression.
   14. Update execution records.
   15. Update RTM.
   16. Prepare test summary.

34. INTERVIEW QUESTIONS
====================================================================

Q1. What is Test Documentation?

Answer:
    It is the set of testing artifacts used to plan, design,
    execute, track and report software testing activities.


Q2. What is a Test Scenario?

Answer:
    A high-level condition or functionality that needs to be tested.


Q3. What is a Test Case?

Answer:
    A detailed set of steps, data and expected results used to
    verify a specific condition or functionality.


Q4. What is Test Data?

Answer:
    Data used as input during test execution.


Q5. What is a Test Suite?

Answer:
    A collection of related test cases.


Q6. What is Test Execution?

Answer:
    The process of executing test cases and recording their
    actual results and status.


Q7. What is a Test Summary Report?

Answer:
    A report that summarizes the testing performed, execution
    results, defects, risks and overall testing status.


Q8. What is RTM?

Answer:
    Requirement Traceability Matrix maps requirements to test
    cases to verify requirement coverage.


Q9. What is forward traceability?

Answer:
    Mapping requirements to corresponding test cases.


Q10. What is backward traceability?

Answer:
    Mapping test cases back to their associated requirements.


Q11. What is bi-directional traceability?

Answer:
    Traceability between requirements and test cases in both
    directions.


====================================================================
35. SCENARIO-BASED INTERVIEW QUESTIONS
====================================================================

Q1.

A requirement has no corresponding test case.

What does this indicate?

Answer:

    Possible missing test coverage.

    QA should:
        - Review the requirement.
        - Create appropriate test cases.
        - Update RTM.


Q2.

A test case fails. What do you do?

Answer:

    1. Verify actual vs expected result.
    2. Reproduce the issue.
    3. Investigate whether it is a software defect.
    4. Check environment/data/dependencies.
    5. Report defect if appropriate.
    6. Record execution result.


Q3.

A test case is blocked.

What does that mean?

Answer:

    The test cannot currently be executed because a required
    dependency or condition is unavailable.


Q4.

A requirement changes after test cases are created.

What do you do?

Answer:

    - Perform impact analysis.
    - Update affected test cases.
    - Update test data.
    - Update RTM.
    - Review automation.
    - Execute affected tests again.
