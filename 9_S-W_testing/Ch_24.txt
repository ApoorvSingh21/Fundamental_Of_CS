24.1 BROWSER COMPATIBILITY TESTING
======================================================================

Browser compatibility testing verifies that a web application
works correctly across different browsers and browser versions.

A web application may work correctly in one browser but behave
differently in another.

Example:

    Application:
        Online Shopping Website

    Chrome:
        Login works

    Firefox:
        Login works

    Safari:
        Login button overlaps another element

This may be a browser compatibility defect.


The goal is to verify:

    • UI rendering
    • Functionality
    • Navigation
    • Forms
    • JavaScript behavior
    • CSS behavior
    • API interaction
    • Responsive behavior
    • Browser-specific behavior


======================================================================
24.2 WHY BROWSER COMPATIBILITY MATTERS
======================================================================

Users do not necessarily use the same browser.

A website may be accessed using:

    • Chrome
    • Firefox
    • Edge
    • Safari

Users may also use different:

    • Operating systems
    • Screen sizes
    • Devices
    • Browser versions


Therefore, testing only one browser may not provide
sufficient confidence.


Example:

    Developer tests:
        Chrome on Windows

    Real users:
        Chrome on Windows
        Edge on Windows
        Firefox on Linux
        Safari on macOS
        Safari on iPhone
        Chrome on Android


A QA Engineer should consider the browsers and platforms
that are relevant to the application's target users.


======================================================================
24.3 MAJOR BROWSERS
======================================================================

Important browsers mentioned in the syllabus include:

    1. Google Chrome
    2. Mozilla Firefox
    3. Microsoft Edge
    4. Apple Safari


Each browser may have differences in:

    • Rendering
    • CSS support
    • JavaScript behavior
    • Browser APIs
    • Developer tools
    • Performance
    • Default behavior


A QA Engineer should not assume:

    "If it works in Chrome, it must work everywhere."


======================================================================
24.4 CROSS-BROWSER TESTING
======================================================================

Cross-browser testing means executing relevant tests
across multiple browsers.

Example test:

    Test:
        User should be able to log in.


Browser matrix:

    Chrome
    Firefox
    Edge
    Safari


Expected:

    Login should work correctly in all supported browsers.


--------------------------------------------------------------
EXAMPLE TEST MATRIX
--------------------------------------------------------------

    Test Case: Login

    Browser       Result

    Chrome        PASS
    Firefox       PASS
    Edge          PASS
    Safari        FAIL


If Safari fails while other supported browsers pass,
the tester should investigate whether the problem is
browser-specific.


======================================================================
24.5 BROWSER VERSIONS
======================================================================

Compatibility testing may also involve browser versions.

Example:

    Browser:
        Chrome

    Versions:
        Supported/current version
        Previous supported version


A web application may behave differently between versions.

Therefore, the test strategy should identify which
browser versions are supported by the product.


--------------------------------------------------------------
IMPORTANT
--------------------------------------------------------------

Do not blindly test every browser version.

Instead, determine:

    • Supported browsers
    • Supported versions
    • Target users
    • Business requirements
    • Product support policy


This makes testing practical and efficient.


======================================================================
24.6 OPERATING SYSTEM COMPATIBILITY
======================================================================

Browser behavior can also depend on the operating system.

Examples:

    Windows
    macOS
    Linux
    Android
    iOS


A browser application may behave differently because
of differences in:

    • Operating system
    • Browser implementation
    • Fonts
    • Screen rendering
    • Input behavior
    • File handling
    • Device capabilities


Example:

    Chrome + Windows
        → PASS

    Chrome + macOS
        → PASS

    Safari + macOS
        → FAIL


The tester should record the complete environment
when reporting the issue.


======================================================================
24.7 RESPONSIVE TESTING
======================================================================

Responsive testing verifies that a web application
adapts correctly to different screen sizes.

A responsive web application should provide an appropriate
layout for different devices and screen dimensions.


Examples:

    Desktop
    Laptop
    Tablet
    Mobile


--------------------------------------------------------------
RESPONSIVE TESTING CHECKS
--------------------------------------------------------------

Verify:

    • Layout
    • Text
    • Images
    • Buttons
    • Navigation
    • Forms
    • Tables
    • Menus
    • Content visibility
    • Horizontal scrolling
    • Vertical scrolling


Example:

Desktop:

    ---------------------------------------------------
    | Logo | Home | Products | Cart | Account          |
    ---------------------------------------------------


Mobile:

    ---------------------------
    | Logo               Menu |
    ---------------------------


The layout may change based on screen size.


--------------------------------------------------------------
COMMON RESPONSIVE DEFECTS
--------------------------------------------------------------

    • Text overlaps
    • Buttons are cut off
    • Images overflow
    • Navigation disappears incorrectly
    • Horizontal scrolling appears unexpectedly
    • Form fields become unusable
    • Content is outside the viewport
    • Tables become unreadable


======================================================================
24.8 SCREEN SIZES
======================================================================

A QA Engineer should test relevant screen sizes rather
than assuming one screen size represents all users.


Examples:

    Desktop
        ↓
    Laptop
        ↓
    Tablet
        ↓
    Mobile


Testing should consider both:

    • Width
    • Height


Example:

    Large desktop
    Standard laptop
    Tablet portrait
    Tablet landscape
    Mobile portrait
    Mobile landscape


The exact dimensions should be selected based on the
product's target devices and supported environments.


======================================================================
24.9 CROSS-PLATFORM TESTING
======================================================================

Cross-platform testing verifies application behavior
across different platforms.


Example matrix:

    ------------------------------------------------------------
    Platform       Browser       Device Type
    ------------------------------------------------------------
    Windows        Chrome        Desktop
    Windows        Edge          Desktop
    Linux          Firefox       Desktop
    macOS          Safari        Desktop
    Android        Chrome        Mobile
    iOS            Safari        Mobile
    ------------------------------------------------------------


The actual matrix should be based on the application's
supported platforms and users.


--------------------------------------------------------------
WHY TESTING EVERYTHING IS NOT ALWAYS PRACTICAL
--------------------------------------------------------------

Suppose a product claims support for:

    10 browsers
    ×
    5 versions
    ×
    6 operating systems
    ×
    5 screen sizes

The number of possible combinations can become very large.


Therefore QA teams use:

    • Risk
    • User statistics
    • Business requirements
    • Supported environments
    • Critical workflows


to select an effective test matrix.


======================================================================
24.10 COMPATIBILITY TEST STRATEGY
======================================================================

A good compatibility strategy can follow these steps.


STEP 1 — IDENTIFY TARGET USERS
------------------------------

Determine:

    • Who uses the application?
    • Desktop users?
    • Mobile users?
    • Enterprise users?
    • Specific operating systems?


STEP 2 — IDENTIFY SUPPORTED ENVIRONMENTS
----------------------------------------

Determine:

    • Supported browsers
    • Supported browser versions
    • Supported operating systems
    • Supported devices
    • Supported screen sizes


STEP 3 — PRIORITIZE
--------------------

Not every combination has equal importance.

Prioritize:

    HIGH
        Critical user environments

    MEDIUM
        Common but less critical environments

    LOW
        Rare or lower-priority combinations


STEP 4 — EXECUTE CORE TESTS
---------------------------

Run critical workflows such as:

    • Login
    • Registration
    • Search
    • Navigation
    • Forms
    • Checkout
    • Payment
    • Logout


STEP 5 — EXECUTE DETAILED TESTS
-------------------------------

Test:

    • UI
    • Functional behavior
    • Forms
    • Links
    • Images
    • Responsive layout
    • Browser-specific behavior


STEP 6 — REPORT ENVIRONMENT
---------------------------

A compatibility bug report should clearly identify:

    Browser
    Browser version
    Operating system
    Device
    Screen size
    Application version/build
    Steps
    Expected result
    Actual result

======================================================================

    --------------------------------------------------------------
    Login        PASS     PASS      PASS   PASS

    Cart + Safari

    --------------------------------------------------------------
    Windows   Chrome        PASS     PASS      PASS
    Windows   Edge          PASS     PASS      PASS
    Linux     Firefox       PASS     PASS      PASS
    macOS     Safari        PASS     PASS      FAIL
    --------------------------------------------------------------

24.12 PRACTICAL SCENARIO — UI BREAKS IN SAFARI
======================================================================

Problem:

    Checkout page works correctly in Chrome
    but layout is broken in Safari.


Investigation:

    1. Reproduce in Safari.
    2. Record Safari version.
    3. Record operating system.
    4. Compare with Chrome.
    5. Inspect page layout.
    6. Check CSS/DOM using DevTools.
    7. Identify the affected component.
    8. Capture evidence.
    9. Report browser-specific defect.


Bug title:

    Checkout address form layout overlaps in Safari


Environment:

    Browser:
        Safari

    OS:
        macOS

    Screen:
        Desktop


Expected:

    Address form should display correctly without
    overlapping fields.


Actual:

    Address fields overlap each other.


======================================================================
24.13 PRACTICAL SCENARIO — RESPONSIVE ISSUE
======================================================================

Requirement:

    Website should work correctly on mobile devices.


Tester checks:

    Desktop:
        PASS

    Tablet:
        PASS

    Mobile:
        FAIL


Problem:

    Checkout button extends beyond the screen.


Investigation:

    • Check viewport
    • Check button dimensions
    • Check responsive layout
    • Check CSS
    • Compare different mobile sizes


Possible defect:

    Button is not responsive and becomes partially
    inaccessible on smaller screens.


======================================================================
24.14 PRACTICAL SCENARIO — BROWSER-SPECIFIC FUNCTIONALITY
======================================================================

Suppose:

    File upload works in Chrome
    but fails in Firefox.


Test steps:

    1. Open application in Firefox.
    2. Navigate to upload page.
    3. Select supported file.
    4. Click Upload.
    5. Observe result.
    6. Check Console.
    7. Check Network.
    8. Compare with Chrome.


Possible investigation areas:

    • JavaScript behavior
    • Browser APIs
    • Request generation
    • File handling
    • Browser-specific behavior


The bug should not simply say:

    "Upload doesn't work."

Instead:

    "File upload fails in Firefox under the supported
     environment while the same workflow succeeds in
     Chrome."

Browser compatibility testing becomes much more powerful
when combined with DevTools.


Example:

    Browser-specific failure
            ↓
    DevTools
            ↓
    Elements
            ↓
    Console
            ↓
    Network
            ↓
    Application
            ↓
    Root-cause investigation


Example:

    Safari page broken
            ↓
    Elements
            ↓
    CSS/layout difference found
            ↓
    Evidence collected
            ↓
    Bug reported


======================================================================
24.16 COMPATIBILITY VS RESPONSIVE TESTING
======================================================================

These concepts are related but different.


BROWSER COMPATIBILITY
---------------------

Question:

    "Does the application work correctly
     in different browsers?"


Examples:

    Chrome
    Firefox
    Edge
    Safari


RESPONSIVE TESTING
------------------

Question:

    "Does the application adapt correctly
     to different screen sizes/devices?"


Examples:

    Desktop
    Tablet
    Mobile


They can overlap.

Example:

    Safari on iPhone

involves both:

    • Browser/platform compatibility
    • Mobile/responsive behavior

24.17 COMPATIBILITY DEFECT REPORT
======================================================================

Example:

BUG TITLE
---------

    Checkout button is partially hidden on mobile Safari


ENVIRONMENT
-----------

    Browser:
        Safari

    Platform:
        iOS

    Device:
        Mobile device

    Screen:
        Mobile viewport


PRECONDITION
------------

    User has items in cart.


STEPS
-----

    1. Open application.
    2. Login.
    3. Add product to cart.
    4. Open checkout.
    5. Scroll to payment section.


EXPECTED
--------

    Checkout button should be completely visible
    and usable.


ACTUAL
------

    Checkout button is partially hidden.


EVIDENCE
--------

    • Screenshot
    • Screen recording if needed
    • Browser/device information


This is a useful compatibility defect because
the environment is clearly specified.

24.20 INTERVIEW QUESTIONS
======================================================================

Q1. What is browser compatibility testing?

Answer:
Browser compatibility testing verifies that a web
application works correctly across supported browsers
and browser versions.


Q2. Why do we perform cross-browser testing?

Answer:
Because users may access the application through
different browsers, and rendering or functionality
can vary between browsers.


Q3. Which major browsers should a QA Engineer know?

Answer:

    • Chrome
    • Firefox
    • Edge
    • Safari


Q4. What is responsive testing?

Answer:
Responsive testing verifies that a web application
adapts correctly to different screen sizes and devices.


Q5. Is responsive testing the same as cross-browser testing?

Answer:
No.

Cross-browser testing focuses on different browsers.

Responsive testing focuses on different screen sizes
and device layouts.

They can overlap.


Q6. What information should be included when reporting
a browser compatibility defect?

Answer:

    • Browser
    • Browser version
    • Operating system
    • Device
    • Screen size
    • Application version/build
    • Steps to reproduce
    • Expected result
    • Actual result
    • Evidence


Q7. Should QA test every browser and every version?

Answer:
Not necessarily.

Testing should be based on supported environments,
target users, business requirements, and risk.


Q8. What would you do if a feature works in Chrome
but fails in Firefox?

Answer:

    1. Reproduce the issue in Firefox.
    2. Confirm the Chrome behavior.
    3. Record browser/version/OS.
    4. Inspect Console.
    5. Inspect Network.
    6. Inspect Elements if UI-related.
    7. Compare behavior.
    8. Report the browser-specific defect.


Q9. What is a browser compatibility matrix?

Answer:
It is a structured list of browsers, versions,
platforms, or devices against which testing is performed,
along with the results.


Q10. Why is environment information important in a bug report?

Answer:
Because compatibility defects may occur only under
specific browser, OS, device, or screen-size combinations.

24.21 INTERVIEW SCENARIO
======================================================================

INTERVIEWER:

    "The website works perfectly on Chrome but is broken
     on Safari. What will you do?"


STRONG ANSWER:

    "First, I would reproduce the issue on the supported
     Safari environment and record the browser version,
     operating system, device, and screen size.

     Then I would determine whether the problem is UI,
     JavaScript, network, or browser-storage related.

     I would use DevTools to inspect Elements, Console,
     Network, and Application as appropriate.

     I would compare the behavior with Chrome and collect
     evidence before creating a browser-specific defect."


This demonstrates:

    • Testing knowledge
    • Debugging ability
    • DevTools knowledge
    • Compatibility understanding
    • Good bug reporting practice

CHAPTER 24 — FINAL TAKEAWAY
======================================================================

A professional QA Engineer does not ask only:

    "Does the website work?"

The better question is:

    "Does the website work correctly in all supported
     browsers, platforms, devices, and screen sizes?"


The compatibility testing flow is:

    REQUIREMENTS
         ↓
    Supported browsers/platforms
         ↓
    Test matrix
         ↓
    Core functionality
         ↓
    UI + responsive testing
         ↓
    DevTools investigation
         ↓
    Defect reporting
         ↓
    Retesting


Remember:

    Browser Compatibility
        =
    Browser + Version + OS + Device + Screen Size


Do not attempt to test every possible combination blindly.

Use:

    Business Requirements
          +
    Target Users
          +
    Supported Environments
          +
    Risk


to create practical and effective coverage.
