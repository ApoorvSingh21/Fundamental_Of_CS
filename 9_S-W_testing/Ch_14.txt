1. INTRODUCTION TO TEST CASE DESIGN
====================================================================

Test Case Design is the process of creating detailed test cases
that can be used to verify whether software behaves according
to its requirements.

In simple words:

    Test Case Design
        =
    Deciding WHAT to test and HOW to test it.

A good test case should help a tester:

    - Execute the test consistently
    - Understand the required input
    - Know the expected result
    - Record the actual result
    - Determine Pass/Fail
    - Reproduce a defect if one is found


Example:

Requirement:

    User should be able to log in using valid credentials.

Test Case Design:

    TC_LOGIN_001
    Verify login with valid credentials.

    Steps:
        1. Open login page.
        2. Enter valid username.
        3. Enter valid password.
        4. Click Login.

    Expected:
        User should successfully reach the dashboard.


====================================================================
2. OBJECTIVES OF TEST CASE DESIGN
====================================================================

The main objectives are:

    1. Verify requirements.
    2. Identify defects.
    3. Provide repeatable testing.
    4. Improve test coverage.
    5. Validate positive scenarios.
    6. Validate negative scenarios.
    7. Validate business rules.
    8. Cover important edge cases.
    9. Support regression testing.
   10. Provide traceability to requirements.


====================================================================
3. CHARACTERISTICS OF A GOOD TEST CASE
====================================================================

A good test case should be:

    Clear
    Specific
    Repeatable
    Testable
    Traceable
    Independent where practical
    Easy to understand
    Easy to maintain
    Focused on one meaningful validation
    Associated with expected results


A good test case should answer:

    What are we testing?
    What is required before testing?
    What steps should be performed?
    What data should be used?
    What should happen?
    What actually happened?
    What is the result?


====================================================================
4. BASIC TEST CASE STRUCTURE
====================================================================

A typical test case can contain:

    1. Test Case ID
    2. Test Case Title
    3. Requirement ID
    4. Preconditions
    5. Test Steps
    6. Test Data
    7. Expected Result
    8. Actual Result
    9. Status
   10. Priority
   11. Severity, where applicable
   12. Environment
   13. Comments/Notes


Example:

    Test Case ID:
        TC_LOGIN_001

    Title:
        Verify login with valid credentials.

    Requirement:
        R_LOGIN_001

    Preconditions:
        Valid registered user exists.

    Steps:
        1. Open login page.
        2. Enter valid username.
        3. Enter valid password.
        4. Click Login.

    Test Data:
        Username = user@test.com
        Password = Test@123

    Expected:
        Dashboard should be displayed.

    Actual:
        Dashboard displayed.

    Status:
        PASS

    Priority:
        High


====================================================================
5. TEST CASE ID
====================================================================

Test Case ID uniquely identifies a test case.

Example:

    TC_LOGIN_001
    TC_LOGIN_002
    TC_CART_001
    TC_CHECKOUT_001


A useful naming convention may include:

    Feature + Sequence Number


Example:

    TC_LOGIN_001

Meaning:

    TC       → Test Case
    LOGIN    → Feature
    001      → Sequence


Benefits:

    - Easy identification
    - Easy tracking
    - Easy reporting
    - Easy traceability
    - Easier defect discussion


====================================================================
6. TEST CASE TITLE
====================================================================

The title should clearly describe what is being verified.

Bad:

    Check login

Better:

    Verify login with valid credentials.


Bad:

    Test password

Better:

    Verify that password is masked on the login page.


Good titles should be:

    - Short
    - Specific
    - Meaningful
    - Action/validation oriented


====================================================================
7. REQUIREMENT ID
====================================================================

A test case should ideally be linked to its requirement.

Example:

    Requirement:
        R_LOGIN_001

    Test Cases:
        TC_LOGIN_001
        TC_LOGIN_002
        TC_LOGIN_003


This supports Requirement Traceability Matrix (RTM).

Example:

    R_LOGIN_001
         |
         +---- TC_LOGIN_001
         +---- TC_LOGIN_002
         +---- TC_LOGIN_003


This helps determine whether the requirement has adequate
test coverage.


====================================================================
8. PRECONDITIONS
====================================================================

Preconditions are conditions that must be satisfied before
executing the test case.

Example:

Test:

    Verify login with valid credentials.

Preconditions:

    - User account exists.
    - Login page is accessible.
    - Application is available.


Another example:

Test:

    Verify checkout.

Preconditions:

    - User is logged in.
    - Product is available.
    - Product is added to cart.
    - Required checkout information is available.


====================================================================
9. TEST STEPS
====================================================================

Test steps describe the actions the tester should perform.

Good steps should be:

    - Sequential
    - Clear
    - Specific
    - Reproducible


Example:

    1. Open the application.
    2. Navigate to Login.
    3. Enter a valid email address.
    4. Enter a valid password.
    5. Click Login.


Avoid vague steps such as:

    "Perform login."


Instead:

    "Enter the registered email address in the Email field."


====================================================================
10. TEST DATA
====================================================================

Test data is the actual input used while executing the test.

Example:

    Email:
        user@test.com

    Password:
        Test@123


For negative testing:

    Email:
        invalid-email

    Password:
        wrong


Test data may include:

    - Valid values
    - Invalid values
    - Boundary values
    - Empty values
    - Null values
    - Duplicate values
    - Special characters
    - Large values


====================================================================
11. EXPECTED RESULT
====================================================================

Expected Result describes what should happen if the software
works correctly.

Example:

Action:

    Enter valid credentials and click Login.

Expected:

    User should be authenticated and redirected to the dashboard.


Expected results should be:

    - Clear
    - Observable
    - Testable
    - Specific


Bad:

    "Login should work."


Better:

    "User should be successfully authenticated and redirected
     to the dashboard."


====================================================================
12. ACTUAL RESULT
====================================================================

Actual Result records what actually happened during execution.

Example:

Expected:

    Dashboard should be displayed.

Actual:

    Dashboard displayed.

Status:

    PASS


Another example:

Expected:

    Error message should be displayed for invalid password.

Actual:

    Application crashes.

Status:

    FAIL


Actual result is generally recorded during execution rather than
during initial test case design.


====================================================================
13. PASS / FAIL STATUS
====================================================================

PASS:

    Actual result matches expected result.


FAIL:

    Actual result does not match expected result.


BLOCKED:

    Test cannot be executed because a required condition or
    dependency is unavailable.


NOT EXECUTED:

    Test has not yet been executed.


Example:

    TC001 → PASS
    TC002 → FAIL
    TC003 → BLOCKED
    TC004 → NOT EXECUTED


====================================================================
14. PRIORITY
====================================================================

Priority indicates how important it is to test or address
something from a business/testing perspective.

Typical levels:

    High
    Medium
    Low


Example:

    Payment functionality:
        High priority

    Login:
        High priority

    Minor visual formatting:
        Low priority


Priority helps QA teams decide what should receive attention first.


====================================================================
15. SEVERITY
====================================================================

Severity indicates the impact of a defect on the software/system.

Typical levels may include:

    Critical
    High
    Medium
    Low


Example:

    Application crashes during payment:
        Critical/High severity depending on context.

    Minor alignment issue:
        Low severity.


Important:

    Priority = How urgently it should be addressed.

    Severity = How seriously it affects the system.


These concepts are discussed in greater detail in Chapter 18.


====================================================================
16. PRIORITY VS SEVERITY
====================================================================

Example 1:

Bug:
    Company logo has incorrect spelling on homepage.

Impact:
    Low

But:
    Company may want immediate correction.

Possible:

    Severity = Low
    Priority = High


Example 2:

Bug:
    Rare crash in a low-use administrative feature.

Possible:

    Severity = High
    Priority = Medium

The exact classification depends on business context.


====================================================================
17. POSITIVE TEST CASE
====================================================================

A positive test verifies expected behavior using valid inputs.

Example:

Requirement:

    Password must contain at least 8 characters.

Positive test:

    Input:
        Password123

Expected:

    Password should be accepted.


Another example:

    Valid username
    +
    Valid password
    ↓
    Login successful


====================================================================
18. NEGATIVE TEST CASE
====================================================================

A negative test verifies how the system behaves with invalid,
unexpected, or unacceptable inputs.

Example:

Requirement:

    Password must contain at least 8 characters.

Negative test:

    Input:
        abc123

Expected:

    Validation message should be displayed.


Other negative cases:

    - Invalid email
    - Wrong password
    - Empty required field
    - Unsupported file
    - Duplicate record
    - Unauthorized access


====================================================================
19. EDGE CASES
====================================================================

An edge case occurs around extreme or unusual conditions.

Example:

Requirement:

    Username length:
        5–20 characters


Test values:

    4 characters
    5 characters
    6 characters
    19 characters
    20 characters
    21 characters


Important values include:

    Minimum - 1
    Minimum
    Minimum + 1
    Normal
    Maximum - 1
    Maximum
    Maximum + 1


These concepts are expanded in Black Box Test Design.

25. TEST CASE DESIGN PROCESS
====================================================================

A practical test case design process:

STEP 1:
    Understand requirement.

STEP 2:
    Identify testable conditions.

STEP 3:
    Identify positive scenarios.

STEP 4:
    Identify negative scenarios.

STEP 5:
    Identify boundary/edge conditions.

STEP 6:
    Identify business rules.

STEP 7:
    Identify dependencies.

STEP 8:
    Prepare test data.

STEP 9:
    Write test cases.

STEP 10:
    Link test cases to requirements.

STEP 11:
    Review test cases.

STEP 12:
    Execute and maintain them.


====================================================================
26. REQUIREMENT → TEST CASE MAPPING
====================================================================

Example requirement:

    R001:
    User should be able to reset password using registered email.


Test cases:

    TC001:
        Reset password with valid registered email.

    TC002:
        Reset password with unregistered email.

    TC003:
        Reset password with blank email.

    TC004:
        Reset password with invalid email format.

    TC005:
        Verify password reset link.


Mapping:

    R001
      |
      +---- TC001
      +---- TC002
      +---- TC003
      +---- TC004
      +---- TC005


This improves test coverage.


====================================================================
27. TEST CASE REVIEW
====================================================================

Before execution, test cases may be reviewed by:

    - QA Lead
    - Senior QA
    - Product Owner
    - Business Analyst
    - Other relevant team members


Review questions:

    - Is the requirement covered?
    - Are steps clear?
    - Is expected result testable?
    - Is test data correct?
    - Are positive cases covered?
    - Are negative cases covered?
    - Are edge cases covered?
    - Is priority appropriate?
    - Is requirement mapping correct?


====================================================================
28. MAINTAINABLE TEST CASES
====================================================================

Software changes continuously.

Therefore, test cases must be maintained.

If a UI changes:

    Old:
        Click "Submit Order"

    New:
        Click "Place Order"


The corresponding test case should be updated.


If a requirement changes:

    Review:
        Test scenarios
        Test cases
        Test data
        RTM
        Automation scripts


====================================================================
29. AVOIDING DUPLICATE TEST CASES
====================================================================

Bad approach:

    TC001:
        Verify valid login.

    TC002:
        Check successful login using valid credentials.

If both test exactly the same behavior, they may be duplicates.


Better:

    TC001:
        Valid login.

    TC002:
        Invalid username.

    TC003:
        Invalid password.

    TC004:
        Blank username.

    TC005:
        Blank password.


Each case adds meaningful coverage.


====================================================================
30. ONE TEST CASE — ONE CLEAR PURPOSE
====================================================================

Avoid putting too many unrelated validations into one test case.

Bad:

    TC001:
        Verify login, search product, add product to cart,
        checkout and logout.


Problems:

    - Difficult to debug
    - Difficult to identify failure point
    - Difficult to maintain
    - Difficult to report results


Better:

    TC001 → Verify Login
    TC002 → Verify Search
    TC003 → Verify Add to Cart
    TC004 → Verify Checkout
    TC005 → Verify Logout


====================================================================
31. DATA-DRIVEN TEST CASE DESIGN
====================================================================

The same logical test may be executed with multiple data sets.

Example:

Login test:

    +----------------------+----------------------+----------+
    | Username             | Password             | Expected |
    +----------------------+----------------------+----------+
    | valid@test.com       | Valid@123            | Pass     |
    | valid@test.com       | Wrong@123            | Fail     |
    | invalid@test.com     | Valid@123            | Fail     |
    | blank                | Valid@123            | Fail     |
    | valid@test.com       | blank                | Fail     |
    +----------------------+----------------------+----------+


This concept becomes especially useful in automation.


====================================================================
32. TEST CASE PRIORITIZATION
====================================================================

When there are many test cases and limited time, prioritize them.

High Priority:

    - Login
    - Payment
    - Checkout
    - Security-critical functionality
    - Major business workflows


Medium Priority:

    - Search
    - Filters
    - Product sorting


Low Priority:

    - Minor UI formatting
    - Low-impact optional functionality


Prioritization should consider:

    - Business impact
    - User impact
    - Risk
    - Frequency of use
    - Recent changes
    - Defect history

33. TEST CASE DESIGN AND REGRESSION
====================================================================

Good test cases should be reusable for regression testing.

Example:

After fixing checkout:

    Execute:

    TC_CHECKOUT_001
    TC_CHECKOUT_002
    TC_CHECKOUT_003
    TC_PAYMENT_001
    TC_PAYMENT_002


A stable set of important test cases can become a regression
suite.

38. TEST CASE DESIGN — COMMON MISTAKES
====================================================================

Mistake 1:
    No clear expected result.

Mistake 2:
    Missing preconditions.

Mistake 3:
    Vague steps.

Mistake 4:
    No test data.

Mistake 5:
    Only positive testing.

Mistake 6:
    Ignoring boundary cases.

Mistake 7:
    Duplicate test cases.

Mistake 8:
    Multiple unrelated purposes in one case.

Mistake 9:
    Missing requirement mapping.

Mistake 10:
    Test cases not updated after requirements change.

39. INTERVIEW QUESTIONS
====================================================================

Q1. What is Test Case Design?

Answer:

    Test Case Design is the process of creating detailed test
    cases to verify software behavior against requirements.


Q2. What should a test case contain?

Answer:

    It may contain ID, title, requirement, preconditions,
    steps, test data, expected result, actual result, status,
    priority and other relevant information.


Q3. What is a precondition?

Answer:

    A condition that must be satisfied before executing a test case.


Q4. What is expected result?

Answer:

    The behavior that should occur when the test is executed
    correctly.


Q5. What is actual result?

Answer:

    The behavior actually observed during test execution.


Q6. What is a positive test case?

Answer:

    A test case that verifies expected behavior using valid
    inputs or valid conditions.


Q7. What is a negative test case?

Answer:

    A test case that verifies system behavior when invalid,
    unexpected or unacceptable input/conditions are provided.


Q8. Why are test case IDs important?

Answer:

    They uniquely identify test cases and make tracking,
    reporting and traceability easier.


Q9. Why is expected result important?

Answer:

    It provides the basis for comparing actual behavior and
    determining whether the test passed or failed.


Q10. Why should test cases be linked to requirements?

Answer:

    To maintain traceability and verify requirement coverage.


====================================================================
40. SCENARIO-BASED INTERVIEW QUESTIONS
====================================================================

Q1.

You have a login page. What test cases will you write?

Answer:

    - Valid username + valid password
    - Invalid username
    - Invalid password
    - Both invalid
    - Blank username
    - Blank password
    - Both blank
    - Password masking
    - Account lock behavior where applicable
    - Error message validation
    - Remember-me behavior where applicable
    - Relevant navigation behavior


Q2.

A requirement says:

    "Password must contain 8–20 characters."

What values will you test?

Answer:

    7
    8
    9
    19
    20
    21

Also consider valid/invalid character combinations according
to the actual requirement.


Q3.

A test case fails. What will you check before reporting a bug?

Answer:

    - Reproduce the issue.
    - Verify expected result.
    - Verify test data.
    - Check environment.
    - Check dependencies.
    - Check whether requirement changed.
    - Check whether the issue is actually a software defect.


Q4.

You have 500 test cases but only one day.

What will you do?

Answer:

    Use risk-based prioritization.

    First execute:

        - Critical business workflows
        - High-risk functionality
        - Recent changes
        - Critical integrations
        - Important regression tests
