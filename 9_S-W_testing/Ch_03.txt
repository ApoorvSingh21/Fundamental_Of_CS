============================================================
3.1 WHAT IS SDLC?
============================================================

SDLC = Software Development Life Cycle

SDLC is a structured process used by software organizations to
plan, develop, test, deploy, and maintain software.

Simple definition:

"SDLC is a systematic process followed by a software team to
develop and maintain a software application."

Typical flow:

Requirement
    ↓
Analysis
    ↓
Design
    ↓
Development
    ↓
Testing
    ↓
Deployment
    ↓
Maintenance


Example:

Suppose a company wants to build an online shopping application.

Requirement:
    User should be able to search products.

Analysis:
    Understand how search should work.

Design:
    Design search UI, API and database structure.

Development:
    Developers implement search functionality.

Testing:
    Testers test search functionality.

Deployment:
    Application is released to users.

Maintenance:
    Bugs are fixed and new improvements are added.


============================================================
3.2 WHY DO WE NEED SDLC?
============================================================

Without a proper development process, software projects can face:

- unclear requirements
- poor design
- coding problems
- missed test cases
- late defect discovery
- cost overruns
- delays
- security problems
- performance problems
- poor customer satisfaction

SDLC provides a structured approach.

Benefits:

1. Better planning
2. Clear responsibilities
3. Better communication
4. Better quality
5. Early defect detection
6. Better risk management
7. Better documentation
8. Predictable delivery
9. Easier maintenance
10. Customer satisfaction

============================================================
3.4 PHASE 1 — REQUIREMENT GATHERING
============================================================

The first major activity is understanding what the customer
actually wants.

Example:

Customer says:

"I want an online shopping website."

This is too general.

The team needs to understand:

- What products?
- How will users register?
- How will users login?
- How will users search?
- How will users add products to cart?
- How will payment work?
- How will orders be cancelled?
- How will refunds work?

Requirement gathering converts business needs into
understandable requirements.


WHO PARTICIPATES?

Common stakeholders:

- Customer
- Product Owner
- Business Analyst
- Project Manager
- Developers
- QA/Testers
- UI/UX designers
- Architects


TYPES OF REQUIREMENTS

1. Functional Requirements
2. Non-Functional Requirements


FUNCTIONAL REQUIREMENT

Describes what the system should do.

Examples:

- User can register.
- User can login.
- User can reset password.
- User can add products to cart.
- User can place an order.
- Admin can add products.


NON-FUNCTIONAL REQUIREMENT

Describes how well the system should work.

Examples:

- Page should load within 2 seconds.
- System should support 10,000 concurrent users.
- Password must be securely stored.
- Application should be available 99.9% of the time.


TESTER ROLE

A tester should start thinking about testing from the
requirement stage.

Tester checks:

- Is requirement clear?
- Is requirement complete?
- Is requirement testable?
- Is there any ambiguity?
- Are acceptance criteria defined?
- Are error scenarios considered?
- Are boundary conditions mentioned?
- Are security requirements mentioned?


Example:

Requirement:

"Password must be strong."

This is ambiguous.

Tester may ask:

- Minimum password length?
- Uppercase required?
- Lowercase required?
- Number required?
- Special character required?
- Maximum length?
- Can spaces be used?


A tester can identify these problems BEFORE coding begins.

3.5 REQUIREMENT DOCUMENT
============================================================

Requirements can be documented in different forms.

Examples:

- BRD
- SRS
- User Stories
- Acceptance Criteria
- Product Requirements
- Functional Specifications


SRS

SRS = Software Requirements Specification

It describes what the software should do.

Example:

Requirement ID:
    LOGIN-001

Requirement:
    Registered users shall be able to login using
    valid email and password.

Acceptance Criteria:

- Valid credentials should allow login.
- Invalid password should show an error.
- Invalid email should show an error.
- Empty email should be rejected.
- Empty password should be rejected.


Tester uses requirements as a major source for designing
test cases.

3.6 PHASE 2 — REQUIREMENT ANALYSIS
============================================================

After gathering requirements, the team analyzes them.

Questions:

- Is requirement technically possible?
- Is it complete?
- Is it consistent?
- Is it testable?
- What dependencies exist?
- What risks exist?
- What resources are required?


Example:

Requirement:

"Application should support 1 million users."

Team analyzes:

- Server capacity
- Database capacity
- Network
- Load balancing
- Caching
- Performance
- Security
- Infrastructure cost


TESTER INVOLVEMENT

QA may perform:

- Requirement review
- Testability analysis
- Risk identification
- Ambiguity identification
- Missing scenario identification
- Acceptance criteria review

============================================================

Testing verifies whether the software meets requirements and

Testing activities include:

- Functional testing
- UI testing
- Integration testing
- System testing
- Regression testing
- Smoke testing
- Sanity testing
- API testing
- Database testing
- Compatibility testing
- Performance testing
- Security testing


Example:

"User should login using valid credentials."

Tester checks:

        ↓
Login successful

Invalid email
        ↓
Error message


Invalid password
        ↓
Error message


Empty email
        ↓
Validation message


Empty password
        ↓
Validation message


Boundary:

Password minimum length
Password maximum length


Security:

SQL injection
Brute-force attempts
Session handling
Unauthorized access


API:

POST /api/login


Database:

Check whether correct user information is stored/retrieved.

3.11 PHASE 7 — DEPLOYMENT
============================================================

After testing and approval, software is deployed.

Deployment environments can include:

Development
     ↓
QA
     ↓
Staging
     ↓
Production


Production = environment used by real users.


Deployment may involve:

- Build creation
- Configuration
- Database migration
- Server deployment
- Environment variables
- DNS
- SSL/TLS
- Monitoring
- Smoke testing


TESTER ROLE

After deployment, QA may perform:

- Production smoke testing
- Sanity testing
- Critical-path verification
- API health checks
- Login verification
- Payment verification
- Monitoring validation


Example:

After production deployment:

1. Open website
2. Login
3. Search product
4. Add product to cart
5. Checkout
6. Verify order


If critical functionality works, deployment can be considered
healthy from a basic QA perspective.


============================================================
3.12 PHASE 8 — MAINTENANCE
============================================================

Software does not end after deployment.

After release:

- Users report bugs
- New features are requested
- Security patches are released
- Performance improvements are made
- Compatibility changes are required


Maintenance includes:

1. Corrective maintenance
2. Adaptive maintenance
3. Perfective maintenance
4. Preventive maintenance


CORRECTIVE

Fix existing defects.

Example:

Checkout crashes for some users.


ADAPTIVE

Adapt software to environmental changes.

Example:

Support a new operating system or browser version.


PERFECTIVE

Improve existing software.

Example:

Improve search performance or UI.


PREVENTIVE

Reduce chances of future problems.

Example:

Refactoring code and improving automated tests.

============================================================
3.16 SHIFT-LEFT TESTING
============================================================

Shift-left testing means moving testing activities earlier
in the software development lifecycle.

Traditional:

Requirements → Development → Testing


Shift-left:

Requirements
     ↓
QA review
     ↓
Design review
     ↓
Development
     ↓
Testing


Goal:

Find defects as early as possible.


Example:

Requirement says:

"Password must be secure."

QA identifies that "secure" is not measurable.

This issue is found before development.

Therefore:

Early detection → lower cost → better quality


============================================================
3.17 COST OF DEFECT FIXING
============================================================

Generally, the later a defect is discovered, the more expensive
it can be to fix.

Example:

Requirement stage:
    Ambiguous requirement discovered
    ↓
    Easy to clarify

Development stage:
    Code already implemented
    ↓
    Code changes required

Testing stage:
    Code + build + test cases affected
    ↓
    Fix + retest + regression

Production:
    Real users affected
    ↓
    Emergency fix
    ↓
    Customer impact
    ↓
    Possible financial/reputation loss


IMPORTANT:

Early testing is not only about finding bugs.

It is about PREVENTING defects.


============================================================
3.18 VERIFICATION vs VALIDATION
============================================================

VERIFICATION

"Are we building the product right?"

Focus:

- Documents
- Requirements
- Design
- Code
- Reviews


Examples:

- Requirement review
- Design review
- Code review
- Static analysis


VALIDATION

"Are we building the right product?"

Focus:

Actual software behavior.

Examples:

- Functional testing
- System testing
- User acceptance testing


Simple memory trick:

Verification:
    Product development process is correct?


Validation:
    Final product satisfies user needs?

3.19 SDLC VS STLC
============================================================

SDLC = Software Development Life Cycle

STLC = Software Testing Life Cycle


SDLC covers the COMPLETE software development process.

STLC focuses specifically on TESTING activities.


SDLC:

Requirement
    ↓
Planning
    ↓
Design
    ↓
Development
    ↓
Testing
    ↓
Deployment
    ↓
Maintenance


STLC:

Requirement Analysis
    ↓
Test Planning
    ↓
Test Case Design
    ↓
Test Environment Setup
    ↓
Test Execution
    ↓
Defect Reporting
    ↓
Test Closure


IMPORTANT INTERVIEW QUESTION:

Q: Is testing a part of SDLC?

Answer:

Yes. Testing is one of the major activities within SDLC,
while STLC specifically defines the testing-related process.

3.21 SDLC MODELS — BASIC OVERVIEW
============================================================

Different projects use different SDLC models.


Common models:

1. Waterfall
2. V-Model
3. Iterative
4. Incremental
5. Spiral
6. Agile


Detailed model discussion comes later, but testers must know
the basic idea.


------------------------------------------------------------
WATERFALL
------------------------------------------------------------

Sequential approach.

Requirement
    ↓
Design
    ↓
Development
    ↓
Testing
    ↓
Deployment


Each phase generally follows the previous phase.


Advantages:

- Simple
- Structured
- Easy to understand
- Documentation-focused


Disadvantages:

- Changes are difficult
- Testing comes relatively late
- Customer feedback may come late


------------------------------------------------------------
V-MODEL
------------------------------------------------------------

V-Model emphasizes testing alongside development stages.

Requirement          Acceptance Testing
      \              /
       \            /
       System Design
            \      /
          System Testing
              \  /
          Architecture
             /\
            /  \
        Integration Testing
           /    \
      Module Design
          /\
         /  \
      Unit Testing
         |
      Coding


Important concept:

Development activities are associated with corresponding
testing activities.


------------------------------------------------------------
ITERATIVE MODEL
------------------------------------------------------------

Software is developed through repeated cycles.

Iteration 1
    ↓
Build + Test
    ↓
Iteration 2
    ↓
Build + Test
    ↓
Iteration 3


------------------------------------------------------------
INCREMENTAL MODEL
------------------------------------------------------------

Product is delivered in pieces/increments.

Example:

Release 1:
    Login

Release 2:
    Product Search

Release 3:
    Cart

Release 4:
    Payment

Release 5:
    Order Tracking


------------------------------------------------------------
SPIRAL MODEL
------------------------------------------------------------

Focuses strongly on:

- Risk analysis
- Prototyping
- Iterative development


Useful for complex/high-risk projects.


------------------------------------------------------------
AGILE
------------------------------------------------------------

Agile develops software in small iterations, commonly called
sprints.

Typical sprint:

Planning
   ↓
Development
   ↓
Testing
   ↓
Review
   ↓
Retrospective


Agile will be covered in greater detail in the Agile chapter.

3.23 SDLC AND DEFECT FLOW
============================================================

Suppose requirement:

"User should receive OTP within 30 seconds."


Possible defect introduced at:

Requirement:
    Requirement does not specify retry behavior.

Design:
    No OTP retry mechanism.

Development:
    Developer uses incorrect timeout.

Testing:
    Tester fails to test delayed OTP.

Production:
    Users don't receive OTP.


This demonstrates why QA should participate throughout SDLC.

3.25 ENTRY CRITERIA AND EXIT CRITERIA
============================================================

ENTRY CRITERIA

Conditions that should be satisfied before a phase/activity
starts.


Example for testing:

- Build is available
- Test environment is ready
- Requirements are available
- Test data is ready
- Test cases are prepared


EXIT CRITERIA

Conditions required to complete a phase/activity.


Example:

- Planned tests executed
- Critical defects resolved
- Required pass percentage achieved
- Test report completed
- QA sign-off provided


Simple:

Entry Criteria:
    "Can we start?"


Exit Criteria:
    "Can we finish?"

3.28 QA SIGN-OFF
============================================================

QA sign-off means QA provides an assessment that the tested
release meets defined quality criteria.

It does NOT necessarily mean:

"Software has zero bugs."

Instead, it means testing was performed according to agreed
criteria and known risks/defects are understood.


Example:

Critical defects:
    0

High defects:
    0

Medium:
    2 known and accepted

Test execution:
    100%

Critical scenarios:
    Passed

Then QA may recommend release, depending on project policy.

3.30 SDLC VS QA VS QC
============================================================

QA = Quality Assurance

Focus:
    Prevent defects by improving processes.


QC = Quality Control

Focus:
    Detect defects in the product.


Testing is primarily a QC activity, but modern QA roles include
both prevention and detection activities.


Simple:

QA:
    "How can we prevent problems?"


Testing/QC:
    "Can we find problems in the product?"


============================================================
3.31 HOW A QA ENGINEER THINKS DURING SDLC
============================================================

Requirement:

"User can withdraw money from ATM."


QA does not think only:

"Does withdrawal work?"


QA thinks:

Positive:
    Valid card + valid PIN + sufficient balance


Negative:
    Invalid PIN
    Expired card
    Insufficient balance


Boundary:
    Minimum withdrawal
    Maximum withdrawal
    Daily withdrawal limit


Security:
    Wrong PIN attempts
    Card blocking


Integration:
    ATM ↔ Bank server


Database:
    Balance updated correctly


Network:
    What happens if connection is lost?


Failure:
    Cash not dispensed but account debited


Concurrency:
    Multiple transactions


Performance:
    Response time


This is the mindset required for a professional tester.

3.35 INTERVIEW ANSWER — "EXPLAIN SDLC"
============================================================

A professional answer:

"SDLC stands for Software Development Life Cycle. It is a
structured process used to develop, test, deploy, and maintain
software. The major activities include requirement gathering
and analysis, planning, design, development, testing,
deployment, and maintenance. As a QA engineer, I participate
early by reviewing requirements, identifying risks and
testability issues, preparing test scenarios and test cases,
executing tests, reporting defects, performing regression
testing, and supporting release validation."


============================================================
3.36 INTERVIEW ANSWER — "WHAT IS THE ROLE OF TESTER IN SDLC?"
============================================================

A good answer:

"A tester's role is not limited to executing test cases after
development. A QA engineer can participate throughout the SDLC.
During requirements, QA reviews requirements and identifies
ambiguities and testability issues. During design, QA identifies
risks and integration scenarios. During development, QA prepares
test cases, test data, API tests, and automation. During testing,
QA executes tests, reports defects, performs retesting and
regression testing. Before and after deployment, QA performs
smoke or sanity validation and supports production quality
checks."
