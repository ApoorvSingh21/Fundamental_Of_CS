CHAPTER 16 — ADVANCED TEST CASE DESIGN
====================================================================

GOAL
----
Learn advanced test-case design techniques that help a QA Engineer

This chapter focuses on:

1. Positive Testing

3. Edge Cases
4. Corner Cases

6. Data Validation Testing
7. Cross-Browser Testing
8. Cross-Platform Testing
9. Advanced Test Coverage
10. Practical QA Scenarios
11. Interview Questions

====================================================================
1. INTRODUCTION TO ADVANCED TEST CASE DESIGN
====================================================================

Basic test cases verify whether the application works under normal
conditions.

Advanced test design goes further.

A professional QA Engineer asks:

    "What can go wrong?"

    "What happens at the limits?"

    "What happens when multiple conditions occur together?"

    "What if the user provides invalid data?"

    "What if the business rule is violated?"

    "Does the application behave consistently on different browsers
     and platforms?"

Example:

Suppose an application allows a user to enter age:

    Allowed age = 18 to 60

Basic testing:

    25 → Pass

Advanced testing:

    17
    18
    19
    59
    60
    61
    0
    -1
    empty
    alphabetic input
    decimal input
    extremely large value

The objective is to maximize meaningful defect detection without
creating unnecessary test cases.


====================================================================
2. POSITIVE TESTING
====================================================================

2.1 Definition
---------------

Positive testing verifies that the system works correctly when the
user provides valid input and follows the expected workflow.

It answers:

    "Does the application work when used correctly?"

Example:

Login requires:

    Email
    Password

Valid test:

    Email    = user@example.com
    Password = CorrectPassword123

Expected:

    User should successfully log in.


--------------------------------------------------------------------
2.2 Positive Testing Examples
--------------------------------------------------------------------

Example 1 — Login

Valid username + valid password
        ↓
Successful login


Example 2 — Registration

Valid:

    Name
    Email
    Password
    Confirm Password

Expected:

    Account should be created.


Example 3 — Shopping Cart

Valid product
    ↓
Add to cart
    ↓
Product appears in cart


Example 4 — Payment

Valid card details
    ↓
Valid amount
    ↓
Valid authentication
    ↓
Payment succeeds


--------------------------------------------------------------------
2.3 Positive Test Case Structure
--------------------------------------------------------------------

Example:

Test Case ID:
    TC_LOGIN_001

Title:
    Login with valid credentials

Precondition:
    Registered user exists.

Steps:
    1. Open login page.
    2. Enter valid email.
    3. Enter valid password.
    4. Click Login.

Expected Result:
    User should be successfully logged in.


====================================================================
3. NEGATIVE TESTING
====================================================================

3.1 Definition
---------------

Negative testing verifies how the application behaves when invalid,
unexpected, incomplete, or unauthorized input is provided.

It answers:

    "Does the application handle incorrect usage safely and
     correctly?"


--------------------------------------------------------------------
3.2 Examples
--------------------------------------------------------------------

Login:

    Invalid username
    Invalid password
    Empty username
    Empty password
    Both fields empty
    Invalid email format
    Very long input
    Unsupported characters


Registration:

    Existing email
    Weak password
    Password mismatch
    Missing required field
    Invalid phone number


Payment:

    Expired card
    Invalid card
    Insufficient balance
    Invalid CVV
    Cancelled transaction


--------------------------------------------------------------------
3.3 Negative Testing Example
--------------------------------------------------------------------

Input:

    Email = abc
    Password = 123

Expected:

    System should reject the input and display an appropriate
    validation/error message.

The application should not:

    - Crash
    - Freeze
    - Accept invalid data
    - Expose sensitive information
    - Create corrupted records


====================================================================
4. POSITIVE VS NEGATIVE TESTING
====================================================================

+----------------------+------------------------------------------+
| Positive Testing     | Negative Testing                         |
+----------------------+------------------------------------------+
| Valid input          | Invalid input                            |
| Expected usage       | Unexpected/incorrect usage              |
| Happy path           | Error path                               |
| Verifies success     | Verifies rejection/handling              |
| Normal conditions    | Abnormal conditions                      |
+----------------------+------------------------------------------+

Professional QA requires BOTH.

5. EDGE CASE TESTING
====================================================================

5.1 Definition
---------------

An edge case occurs at or very close to the boundary of an allowed
range or condition.

Example:

Allowed quantity:

    1 to 10

Edge values:

    1
    2
    9
    10

Values outside the boundary:

    0
    11


--------------------------------------------------------------------
5.2 Example — Age
--------------------------------------------------------------------

Requirement:

    Age must be between 18 and 60.

Important tests:

    17
    18
    19
    59
    60
    61


--------------------------------------------------------------------
5.3 Example — Password Length
--------------------------------------------------------------------

Requirement:

    Password must contain 8–20 characters.

Tests:

    7 characters
    8 characters
    9 characters
    19 characters
    20 characters
    21 characters


--------------------------------------------------------------------
5.4 Example — Product Quantity
--------------------------------------------------------------------

Requirement:

    Quantity = 1–100

Test:

    0
    1
    2
    99
    100
    101


====================================================================
6. CORNER CASE TESTING
====================================================================

6.1 Definition
---------------

A corner case generally occurs under extreme or unusual combinations
of conditions.

Edge case:

    One boundary condition.

Corner case:

    Multiple unusual/extreme conditions occurring together.


--------------------------------------------------------------------
6.2 Example
--------------------------------------------------------------------

Suppose:

    Maximum file size = 10 MB
    Supported format = PDF

Edge testing:

    10 MB PDF

Corner testing:

    10 MB PDF
    + unusual filename
    + slow network
    + user session near expiry


--------------------------------------------------------------------
6.3 E-Commerce Example
--------------------------------------------------------------------

Suppose checkout has:

    100 products
    Maximum discount
    Minimum shipping amount
    Expiring session

A corner case could combine several boundary conditions.

The objective is to identify defects caused by interactions between
multiple conditions.


====================================================================
7. EDGE CASE VS CORNER CASE
====================================================================

+------------------+---------------------------------------------+
| Edge Case        | Corner Case                                 |
+------------------+---------------------------------------------+
| Near boundary    | Extreme/unusual combination                 |
| Usually one      | Often multiple conditions interact          |
| Boundary focused | Combination focused                         |
| Example: 100     | Example: 100 + max discount + session end   |
+------------------+---------------------------------------------+


====================================================================
8. BUSINESS RULE TESTING
====================================================================

8.1 Definition
---------------

Business rules define how an application should behave according to
business requirements.

QA Engineers must verify that the software correctly implements these
rules.


--------------------------------------------------------------------
8.2 Example — Discount
--------------------------------------------------------------------

Business rule:

    If order amount >= ₹5000
    → Customer gets 10% discount.

Test cases:

    ₹4999
    ₹5000
    ₹5001


Expected:

    ₹4999 → No discount
    ₹5000 → 10% discount
    ₹5001 → 10% discount


--------------------------------------------------------------------
8.3 Multiple Business Rules
--------------------------------------------------------------------

Example:

    Order >= ₹5000
        → 10% discount

    Premium customer
        → Additional 5% discount

    Coupon applied
        → Additional discount according to coupon rules


Important testing:

    Normal customer
    Premium customer
    Coupon + normal customer
    Coupon + premium customer
    Boundary order amount
    Invalid coupon
    Expired coupon


--------------------------------------------------------------------
8.4 Business Rule Test Checklist
--------------------------------------------------------------------

Check:

    - Rules are implemented correctly
    - Rules are applied consistently
    - Boundary conditions work
    - Conflicting rules are handled
    - Invalid combinations are rejected
    - Calculations are correct
    - Rule changes do not break existing behavior

9. DATA VALIDATION TESTING
====================================================================

9.1 Definition
---------------

Data validation testing verifies that the application accepts,
processes, stores, and displays correct data.

Data can exist in:

    UI
    API
    Database
    Files
    External systems


--------------------------------------------------------------------
9.2 UI Data Validation
--------------------------------------------------------------------

Example:

Registration form:

    Name
    Email
    Phone
    Date of Birth

Validate:

    Required fields
    Format
    Length
    Allowed characters
    Boundary values
    Duplicate values


--------------------------------------------------------------------
9.3 Database Validation
--------------------------------------------------------------------

Example:

User enters:

    Name = Apoorv
    Email = user@example.com

After registration:

UI
 ↓
API
 ↓
Backend
 ↓
Database

QA can verify that the correct values are stored.


--------------------------------------------------------------------
9.4 Data Validation Questions
--------------------------------------------------------------------

Check:

    - Was the correct data submitted?
    - Was it processed correctly?
    - Was it stored correctly?
    - Was it retrieved correctly?
    - Was it displayed correctly?
    - Was unwanted data rejected?
    - Were relationships maintained?

====================================================================

    Age must be an integer between 18 and 60.

Test data:

    18
    25
    60
    17
    61
    -1

    18.5

        18–60 integer values

        NULL


====================================================================
11. UI VALIDATION VS BACKEND VALIDATION
====================================================================

A professional QA Engineer should not assume that UI validation is
enough.

Example:

UI blocks:

    Age = "abc"

But a tester may send a direct API request containing:

    age = "abc"

The backend should also validate the data.

Therefore:

    UI validation
         +
    API validation
         +
    Database validation

can provide stronger coverage.

12. CROSS-BROWSER TESTING
====================================================================

12.1 Definition
---------------

Cross-browser testing verifies that the application behaves correctly
across supported web browsers.

Common browsers include:

    Chrome
    Firefox
    Edge
    Safari


--------------------------------------------------------------------
12.2 What to Test
--------------------------------------------------------------------

Check:

    - UI layout
    - Buttons
    - Forms
    - Navigation
    - JavaScript behavior
    - CSS rendering
    - File upload/download
    - Popups
    - Authentication
    - API-dependent functionality
    - Responsive behavior


--------------------------------------------------------------------
12.3 Example
--------------------------------------------------------------------

Login page works in:

    Chrome → Pass
    Firefox → Pass
    Edge → Pass
    Safari → ?

If Safari has a layout or functional issue, it may indicate a
browser compatibility defect.

15. ADVANCED TEST COVERAGE
====================================================================

Test coverage means how thoroughly the application's requirements,
features, conditions, and scenarios have been tested.

Good coverage does NOT simply mean:

    "I have written many test cases."

The objective is:

    Meaningful coverage
        +
    Risk coverage
        +
    Requirement coverage
        +
    Scenario coverage


--------------------------------------------------------------------
15.1 Requirement Coverage
--------------------------------------------------------------------

Every important requirement should have corresponding test coverage.

Example:

Requirement:

    User can reset password.

Test coverage:

    Valid email
    Invalid email
    Unregistered email
    Expired reset link
    Used reset link
    Password mismatch
    Successful reset


--------------------------------------------------------------------
15.2 Functional Coverage
--------------------------------------------------------------------

Verify important application functionality.

Example — E-commerce:

    Login
    Search
    Product details
    Cart
    Checkout
    Payment
    Order
    Cancellation
    Refund


--------------------------------------------------------------------
15.3 Negative Coverage
--------------------------------------------------------------------

Verify invalid conditions:

    Invalid input
    Missing data
    Unauthorized access
    Duplicate data
    Invalid state
    Network failure
    Server failure


--------------------------------------------------------------------
15.4 Boundary Coverage
--------------------------------------------------------------------

Test:

    Minimum
    Minimum + 1
    Maximum - 1
    Maximum
    Outside boundary


--------------------------------------------------------------------
15.5 Browser/Platform Coverage
--------------------------------------------------------------------

Verify important combinations of:

    Browser
    Operating system
    Device
    Screen size


====================================================================
16. RISK-BASED ADVANCED TEST DESIGN
====================================================================

Not every feature has equal risk.

High-risk functionality should receive greater testing attention.

Example — E-commerce:

HIGH RISK:

    Payment
    Login
    Checkout
    Order creation

MEDIUM RISK:

    Search
    Product filtering

LOWER RISK:

    Static informational page


Therefore testing effort can be prioritized according to business
impact and risk.

====================================================================

Good test cases require good test data.

Test data categories:

    1. Valid data
    2. Invalid data
    3. Boundary data
    4. Empty data
    5. Duplicate data
    6. Large data
    7. Special-character data
    8. Null data
    9. Existing data
    10. Non-existing data


--------------------------------------------------------------------
17.1 Example — Username
--------------------------------------------------------------------

Requirement:

    5–20 characters
    Alphanumeric

Test data:

    abc              → Invalid
    abcde            → Valid
    abcdef           → Valid
    12345            → Valid
    abc@12            → Invalid
    20-character     → Valid
    21-character     → Invalid


====================================================================
18. SPECIAL CHARACTER TESTING
====================================================================

Fields should be tested with appropriate special characters.

Examples:

    @
    #
    $
    %
    &
    *
    -
    _
    '
    "

Also consider:

    spaces
    leading spaces
    trailing spaces
    multiple spaces


Expected behavior should be determined by the requirement.

Do not automatically assume every special character should be
accepted or rejected.


====================================================================
19. EMPTY / NULL / MISSING DATA TESTING
====================================================================

Test:

    Empty string
    Null value
    Missing field
    Whitespace
    Missing JSON property
    Missing API parameter


Example:

API request:

    {
        "name": "Apoorv"
    }

If email is required, the API should return appropriate validation
behavior rather than incorrectly processing incomplete data.


====================================================================
20. DUPLICATE DATA TESTING
====================================================================

Test duplicate values where uniqueness is expected.

Examples:

    Duplicate email
    Duplicate username
    Duplicate order
    Duplicate transaction
    Duplicate record


Example:

Existing:

    user@example.com

Attempt:

    Register user@example.com again.

Expected:

    Registration should be rejected according to the application's
    uniqueness rule.

23. COMBINED TEST DESIGN
====================================================================

Advanced QA often combines multiple techniques.

Example requirement:

    Age = 18–60
    Country = India
    Premium users get discount
    Discount applies only to orders >= ₹5000


Possible test dimensions:

    Age boundary
    Country
    User type
    Order amount
    Discount condition


A strong test strategy considers interactions between these
conditions instead of testing each field only in isolation.

29. COMMON QA MISTAKES
====================================================================

Mistake 1:
    Testing only valid inputs.

Solution:
    Always include meaningful negative cases.


Mistake 2:
    Testing only middle values.

Example:

    Requirement = 1–100

Only testing:

    50

Solution:

    Test boundaries and nearby values.


Mistake 3:
    Writing many duplicate test cases.

Solution:

    Use effective test design techniques.


Mistake 4:
    Ignoring business rules.

Solution:

    Convert business requirements into testable scenarios.


Mistake 5:
    Testing only UI.

Solution:

    Where applicable, validate API/database behavior as well.


Mistake 6:
    Testing only one browser.

Solution:

    Test the supported browser/platform matrix.


Mistake 7:
    Ignoring combinations.

Solution:

    Identify important interactions between conditions.

30. INTERVIEW QUESTIONS
====================================================================

Q1. What is positive testing?

Answer:
Positive testing verifies that the application works correctly with
valid input and expected user behavior.


Q2. What is negative testing?

Answer:
Negative testing verifies how the application behaves when invalid,
unexpected, incomplete, or unauthorized input is provided.


Q3. What is an edge case?

Answer:
An edge case occurs at or near a boundary or limit of a condition.


Q4. What is a corner case?

Answer:
A corner case involves unusual or extreme conditions, often involving
a combination of conditions.


Q5. What is business rule testing?

Answer:
It verifies that application behavior correctly follows the business
rules defined by the requirements.


Q6. What is data validation testing?

Answer:
It verifies that data is correctly accepted, processed, stored, and
displayed.


Q7. Why is cross-browser testing required?

Answer:
Different browsers may render or execute application behavior
differently, so supported browser compatibility must be verified.


Q8. What is cross-platform testing?

Answer:
It verifies application behavior across supported operating systems,
devices, or platforms.


Q9. What is responsive testing?

Answer:
It verifies that the application's interface remains usable and
correct across different screen sizes and device types.


Q10. Should we test every possible combination?

Answer:
Exhaustive testing is generally impractical. Important combinations
should be selected based on requirements, risk, boundaries, and
meaningful interactions.

33. ADVANCED QA MINDSET
====================================================================

A beginner tester asks:

    "Does this feature work?"

An advanced QA Engineer asks:

    "Under what conditions does it work?"

    "When does it fail?"

    "What are the boundaries?"

    "What invalid data can be provided?"

    "What business rules apply?"

    "What happens when conditions interact?"

    "Does it work across supported browsers and platforms?"

    "Is the data correct throughout the system?"

    "What happens when the environment changes?"

This mindset is extremely important for professional QA work.
