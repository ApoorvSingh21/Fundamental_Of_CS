2.1 WHAT IS A WEB APPLICATION?
====================================================================

A web application is a software application that users access
through a web browser over a network.

Examples:

    Gmail
    GitHub
    Amazon
    Flipkart
    Banking Applications
    Online Examination Systems
    Learning Management Systems


Unlike a simple static webpage, a web application usually contains:

    Frontend
    Backend
    Database
    APIs
    Authentication
    Business Logic


Basic architecture:

                    USER
                      |
                      v
                  BROWSER
                      |
                 HTTP/HTTPS
                      |
                      v
                  WEB SERVER
                      |
                      v
              APPLICATION SERVER
                      |
                      v
                  DATABASE


====================================================================
2.2 WEB APPLICATION ARCHITECTURE
====================================================================

A modern web application commonly has several layers.

                    WEB APPLICATION
                           |
          +----------------+----------------+
          |                |                |
       Frontend         Backend          Database
          |                |
       Browser           API
                           |
                    Business Logic


Example:

    Online shopping application

    Frontend:
        Login
        Product page
        Cart
        Checkout

    Backend:
        Login processing
        Product processing
        Order processing
        Payment processing

    Database:
        Users
        Products
        Orders
        Payments


====================================================================
2.3 BROWSER
====================================================================

A browser is software used to access websites and web applications.

Examples:

    Google Chrome
    Mozilla Firefox
    Microsoft Edge
    Safari


Browser responsibilities:

    1. Accept URL
    2. Resolve domain name
    3. Send HTTP/HTTPS request
    4. Receive server response
    5. Process HTML/CSS/JavaScript
    6. Display webpage
    7. Store cookies
    8. Store local/session data
    9. Execute JavaScript
   10. Communicate with APIs


For testers, browser Developer Tools are extremely important.


====================================================================
2.4 CLIENT
====================================================================

A client is a software component that requests a service from a
server.

Examples:

    Web Browser
    Mobile Application
    Desktop Application
    API Client
    Postman


In web testing:

    Browser = Client


Example:

    Browser asks:

        "Give me the product information."


Server processes the request and sends:

        Product information


====================================================================
2.5 SERVER
====================================================================

A server is a system that receives requests and provides
services/data.

Example:

    Client:

        GET /products/101


    Server:

        Returns product information.


Server may perform:

    Authentication
    Authorization
    Business logic
    Database operations
    API processing
    Validation
    Error handling


====================================================================
2.6 WEB SERVER VS APPLICATION SERVER
====================================================================

WEB SERVER:

    Primarily handles HTTP requests and serves web content.

Examples:

    Apache
    Nginx
    IIS


APPLICATION SERVER:

    Runs application/business logic.

Examples:

    Java application servers
    Node.js applications
    Python web applications
    .NET applications


In modern architectures, the exact division can vary.

A simplified model:

    Browser
       |
       v
    Web Server
       |
       v
    Application
       |
       v
    Database


====================================================================
2.7 REQUEST
====================================================================

A request is a message sent by a client to a server.

Example:

    User opens:

        https://example.com/products


Browser sends a request to the server.


A simplified HTTP request:

    GET /products HTTP/1.1
    Host: example.com


A request can contain:

    Method
    URL
    Headers
    Query Parameters
    Body


====================================================================
2.8 RESPONSE
====================================================================

A response is the message sent by the server back to the client.

Example:

    Server response:

    HTTP/1.1 200 OK

    {
        "id": 101,
        "name": "Laptop",
        "price": 50000
    }


A response commonly contains:

    Status Code
    Headers
    Response Body


====================================================================
2.9 REQUEST-RESPONSE CYCLE
====================================================================

The basic communication is:

        CLIENT
           |
           | REQUEST
           v
        SERVER
           |
           | PROCESS
           v
        DATABASE
           |
           | DATA
           v
        SERVER
           |
           | RESPONSE
           v
        CLIENT


Example:

    User clicks:

        "View Profile"


    Step 1:
        Browser sends request.

    Step 2:
        Server receives request.

    Step 3:
        Server validates user.

    Step 4:
        Server retrieves user data.

    Step 5:
        Server creates response.

    Step 6:
        Browser displays profile.


====================================================================
2.10 URL
====================================================================

URL = Uniform Resource Locator

A URL identifies a resource on the internet/web.

Example:

    https://www.example.com/products?id=101


Parts:

    https://
       ↓
    Protocol/Scheme

    www.example.com
       ↓
    Domain/Host

    /products
       ↓
    Path

    ?id=101
       ↓
    Query Parameter


General structure:

    scheme://host/path?query


Example:

    https://api.example.com/users/101?active=true


    Scheme:
        https

    Host:
        api.example.com

    Path:
        /users/101

    Query parameter:
        active=true


====================================================================
2.11 DOMAIN NAME
====================================================================

A domain name is a human-readable name used to identify a website
or service.

Examples:

    google.com
    github.com
    amazon.in


Humans prefer:

    google.com


Computers communicate using:

    IP addresses


DNS connects the two.


====================================================================
2.12 DNS
====================================================================

DNS = Domain Name System

DNS translates domain names into IP addresses.

Example:

    User enters:

        www.example.com

    DNS helps determine the corresponding IP address.


Simplified flow:

    Browser
       |
       | "What is the IP of example.com?"
       v
      DNS
       |
       | IP address
       v
    Browser
       |
       v
    Server


Without DNS, users would generally need to remember IP addresses
instead of domain names.


====================================================================
2.13 IP ADDRESS
====================================================================

An IP address identifies a device/interface on an IP network.

Example IPv4:

    192.168.1.10


Example IPv6:

    2001:db8::1


Two broad categories commonly discussed:

    Private IP
    Public IP


Private IP:

    Used inside private networks.

Public IP:

    Used for internet-routable communication.


TESTER RELEVANCE:

    Understanding IP addresses helps when dealing with:

        Network problems
        Environment configuration
        Server connectivity
        API endpoints
        Deployment environments


====================================================================
2.14 HTTP
====================================================================

HTTP = HyperText Transfer Protocol

HTTP is a protocol used for communication between clients and
servers on the web.

Example:

    Browser → HTTP Request → Server

    Browser ← HTTP Response ← Server


HTTP is commonly used for:

    Web pages
    APIs
    Web applications
    Data communication


Important HTTP methods:

    GET
    POST
    PUT
    PATCH
    DELETE
    HEAD
    OPTIONS


====================================================================
2.15 HTTPS
====================================================================

HTTPS = HTTP Secure

HTTPS uses TLS to protect communication between client and server.

Simplified:

    HTTP:

        Client ←---- readable network communication ----→ Server


    HTTPS:

        Client ←---- encrypted/protected communication ----→ Server


HTTPS helps provide:

    Confidentiality
    Integrity
    Server authentication


Example:

    https://example.com


TESTER SHOULD CHECK:

    ✓ HTTPS is used where required
    ✓ Certificate is valid
    ✓ Sensitive information is not unnecessarily exposed
    ✓ Secure communication is working correctly


====================================================================
2.16 HTTP METHODS
====================================================================

HTTP methods indicate the intended action.

--------------------------------------------------------------------
GET
--------------------------------------------------------------------

Used to retrieve data.

Example:

    GET /users/101


Meaning:

    "Give me user 101."


Typically does not modify server state.


--------------------------------------------------------------------
POST
--------------------------------------------------------------------

Used to submit data, commonly for creating a resource or triggering
an operation.

Example:

    POST /users


Request body:

    {
        "name": "Apoorv",
        "email": "apoorv@example.com"
    }


--------------------------------------------------------------------
PUT
--------------------------------------------------------------------

Commonly used to replace/update a resource.

Example:

    PUT /users/101


--------------------------------------------------------------------
PATCH
--------------------------------------------------------------------

Commonly used for a partial update.

Example:

    PATCH /users/101


Request:

    {
        "email": "new@example.com"
    }


--------------------------------------------------------------------
DELETE
--------------------------------------------------------------------

Used to delete a resource.

Example:

    DELETE /users/101


====================================================================
2.17 HTTP STATUS CODES
====================================================================

HTTP status codes tell the client the general result of a request.


-------------------- 1xx -------------------------------------------

Informational responses.

Example:

    100 Continue


-------------------- 2xx -------------------------------------------

Successful responses.

    200 OK
        Request succeeded.

    201 Created
        Resource was successfully created.

    202 Accepted
        Request accepted for processing.

    204 No Content
        Request succeeded but response has no content.


-------------------- 3xx -------------------------------------------

Redirection.

    301 Moved Permanently
    302 Found
    304 Not Modified


-------------------- 4xx -------------------------------------------

Client-side/request-related errors.

    400 Bad Request
    401 Unauthorized
    403 Forbidden
    404 Not Found
    405 Method Not Allowed
    409 Conflict
    429 Too Many Requests


-------------------- 5xx -------------------------------------------

Server-side errors.

    500 Internal Server Error
    502 Bad Gateway
    503 Service Unavailable
    504 Gateway Timeout


IMPORTANT:

    401 and 403 are different.

    401:
        Authentication is required or failed.

    403:
        Server understood the request but refuses access.


====================================================================
2.18 HTTP HEADERS
====================================================================

Headers provide additional information about a request or response.

Example request:

    GET /users HTTP/1.1
    Host: example.com
    Accept: application/json
    Authorization: Bearer <token>


Common headers:

    Content-Type
    Accept
    Authorization
    Cookie
    User-Agent
    Cache-Control


Response may contain:

    Content-Type
    Set-Cookie
    Cache-Control
    Location


TESTER USE:

    Headers are very important during API testing.


====================================================================
2.19 CONTENT-TYPE
====================================================================

Content-Type tells the receiver what kind of data is being sent.

Example:

    Content-Type: application/json


Means:

    The body contains JSON data.


Other examples:

    text/html
    application/xml
    multipart/form-data
    application/x-www-form-urlencoded

Request body contains data sent by the client.

Example:

Response body contains data returned by the server.

2.22 JSON
====================================================================

JSON = JavaScript Object Notation

It is widely used for exchanging structured data between clients
and servers.

Example:

    {
        "id": 101,
        "name": "Apoorv",
        "age": 24,
        "active": true
    }


JSON supports values such as:

    String
    Number
    Boolean
    Null
    Object
    Array

        "products": [
            {
                "id": 1,
                "name": "Laptop"
            },
            {
                "id": 2,
                "name": "Mouse"
            }

    ✓ JSON syntax
    ✓ Required fields
    ✓ Data types
    ✓ Values
    ✓ Nested objects
    ✓ Arrays


====================================================================
2.23 QUERY PARAMETERS
====================================================================

Query parameters are values added to a URL after '?'.

Example:

    /products?category=laptop


Multiple parameters:

    /products?category=laptop&page=2&limit=20


Tester should test:

    Valid values
    Invalid values
    Missing values
    Empty values
    Special characters
    Boundary values


====================================================================
2.24 PATH PARAMETERS
====================================================================

Path parameters are values included directly in the URL path.

Example:

    GET /users/101


Here:

    101 = user ID


Another example:

    GET /products/500


Here:

    500 = product ID


Difference:

    Query parameter:

        /users?id=101


    Path parameter:

        /users/101


====================================================================
2.25 COOKIES
====================================================================

A cookie is a small piece of data stored by the browser and
associated with a website/domain.

Cookies can be used for:

    Session management
    Preferences
    Authentication-related state
    Tracking


Example:

    Server sends:

        Set-Cookie: session_id=abc123


Browser stores the cookie and may send it with later requests.


TESTER CHECKS:

    ✓ Cookie creation
    ✓ Cookie expiration
    ✓ Secure attribute
    ✓ HttpOnly attribute
    ✓ SameSite behavior
    ✓ Login/logout behavior


====================================================================
2.26 SESSION
====================================================================

A session represents a user's interaction/state with an application
over a period of time.

Example:

    User logs in.

    Server establishes authenticated state.

    User visits:

        Dashboard
        Profile
        Orders

    User does not need to authenticate independently on every page.


Typical flow:

    Login
      ↓
    Authentication
      ↓
    Session/token
      ↓
    Access protected resources
      ↓
    Logout
      ↓
    Session/token invalidated


TESTER CHECKS:

    ✓ Session creation
    ✓ Session timeout
    ✓ Logout
    ✓ Back-button behavior
    ✓ Unauthorized access after logout


====================================================================
2.27 AUTHENTICATION
====================================================================

Authentication answers:

    "Who are you?"


Examples:

    Username + Password
    OTP
    Biometrics
    Access Token
    OAuth-based login


Example:

    User enters:

        Username
        Password

    Server verifies credentials.


If correct:

    Authentication succeeds.


====================================================================
2.28 AUTHORIZATION
====================================================================

Authorization answers:

    "What are you allowed to do?"


Example:

    Admin:
        Can delete users.

    Normal user:
        Cannot delete users.


Important distinction:

    Authentication:
        Identity verification.

    Authorization:
        Permission verification.


Tester should test both.


====================================================================
2.29 CACHE
====================================================================

Cache stores previously retrieved data temporarily to improve
performance.

Examples:

    Browser cache
    CDN cache
    Server cache
    Application cache


Example:

    User visits a website.

    Browser may reuse cached resources such as:

        Images
        CSS
        JavaScript


Benefits:

    Faster loading
    Reduced network usage
    Reduced server load


Testing concerns:

    ✓ Stale data
    ✓ Cache invalidation
    ✓ Updated content
    ✓ User-specific data
    ✓ Logout/security behavior

    }

2.31 COMPLETE LOGIN FLOW
====================================================================

Let's understand a real-world login process.

USER:

    Username: apoorv
    Password: ********


STEP 1:
    User clicks LOGIN.


STEP 2:
    Frontend validates basic input.


STEP 3:
    Frontend sends API request.

    POST /api/login


STEP 4:
    Request body:

    {
        "username": "apoorv",
        "password": "********"
    }


STEP 5:
    Backend receives request.


STEP 6:
    Backend validates the request.


STEP 7:
    Backend checks user information in database.


STEP 8:
    Database returns matching information.


STEP 9:
    Backend verifies the credentials.


STEP 10:
    Server generates authenticated state/token as appropriate.


STEP 11:
    Server sends response.

    Example:

    HTTP 200 OK

    {
        "message": "Login successful",
        "token": "..."
    }


STEP 12:
    Frontend stores/uses authentication state according to the
    application's design.


STEP 13:
    User accesses dashboard.


STEP 14:
    Browser sends authenticated request.


STEP 15:
    Server validates authentication/authorization.


STEP 16:
    Dashboard data is returned.

2.35 EXAMPLE — UI BUG VS API BUG
====================================================================

Suppose:

    UI displays:

        Price = ₹1,000


But API response says:

        "price": 1200


Possible conclusion:

    Backend/API may be correct,
    but frontend may be displaying incorrect data.


Another situation:

    UI displays:

        ₹1,200

    API response:

        ₹1,000


Now the tester has evidence that the issue may be related to
frontend/API integration or data processing.


This is much better than simply reporting:

    "Price is wrong."

2.38 IMPORTANT WEB TESTING CONCEPTS
====================================================================

STATIC WEB PAGE:

    Mostly fixed content.

DYNAMIC WEB APPLICATION:

    Content and behavior can change based on:

        User
        Database
        Request
        Business rules
        Time
        Permissions


STATELESS HTTP:

    HTTP itself is fundamentally stateless.

    Applications use mechanisms such as:

        Cookies
        Sessions
        Tokens

    to maintain user-related state.


SINGLE-PAGE APPLICATION (SPA):

    Application where much of the user interaction happens within
    a single web page while data is dynamically loaded.


RESPONSIVE WEB DESIGN:

    UI adapts to different screen sizes.

COMMON STATUS CODES:

    200 = OK
    201 = Created
    204 = No Content
    400 = Bad Request
    401 = Authentication required/failed
    403 = Forbidden
    404 = Not Found
    409 = Conflict
    429 = Too Many Requests
    500 = Internal Server Error
    503 = Service Unavailable

2.43 MOST IMPORTANT CONCEPT
====================================================================

For a Software Tester, remember this architecture:

                         USER
                           |
                           v
                      FRONTEND/UI
                           |
                           | HTTP/HTTPS
                           v
                         API
                           |
                           v
                     BACKEND
                           |
                    +------+------+
                    |             |
                    v             v
                DATABASE      EXTERNAL API
                    |
                    v
                   DATA


A good tester does not stop at the UI.

If a feature fails:

    UI
     ↓
    Check Network
     ↓
    Check API
     ↓
    Check Backend/Logs
     ↓
    Check Database
     ↓
    Find the actual failure point
