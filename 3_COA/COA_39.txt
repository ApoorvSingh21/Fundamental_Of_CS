============================================================
CHAPTER 39 — COMPUTER ARCHITECTURE SECURITY
============================================================

LEVEL:
B.Tech 1st Year → Foundation → Intermediate → Advanced
→ Exam Ready → Interview Ready

GOAL:
Understand how computer hardware protects data, software,
memory, and system execution from unauthorized access and
hardware-level attacks.


============================================================
39.1 WHAT IS HARDWARE SECURITY?
============================================================

Hardware security means protecting the physical and
architectural components of a computer system from:

    • Unauthorized access
    • Malicious modification
    • Information leakage
    • Firmware attacks
    • Physical attacks
    • Privilege escalation
    • Side-channel attacks

Important hardware components include:

    CPU
    Memory
    Storage
    Firmware
    I/O controllers
    Security modules
    System buses


Simple idea:

    Hardware Security
          |
          +---- Protect hardware
          |
          +---- Protect data
          |
          +---- Protect execution
          |
          +---- Protect system startup
          |
          +---- Prevent information leakage


============================================================
39.2 SECURITY TRIAD
============================================================

A basic security model is the CIA triad.

CIA:

    C = Confidentiality
    I = Integrity
    A = Availability


CONFIDENTIALITY:

    Prevent unauthorized people from reading information.


INTEGRITY:

    Prevent unauthorized modification of information.


AVAILABILITY:

    Ensure systems and information remain accessible when
    legitimately required.


Example:

    A secure computer should:

    • Keep passwords secret
    • Prevent unauthorized modification
    • Continue operating reliably


============================================================
39.3 HARDWARE SECURITY VS SOFTWARE SECURITY
============================================================

SOFTWARE SECURITY:

    Security implemented mainly through software.

Examples:

    • Antivirus
    • Firewalls
    • Authentication software
    • Operating-system security
    • Application security


HARDWARE SECURITY:

    Security implemented using hardware mechanisms and
    processor/memory architecture.

Examples:

    • Secure boot
    • Hardware encryption support
    • Trusted execution environments
    • Memory protection
    • Hardware security modules


IMPORTANT:

    Hardware and software security work together.


============================================================
39.4 SECURITY BOUNDARIES
============================================================

A computer system contains different privilege levels.

Conceptually:

              User Applications
                     |
                     ↓
              Operating System
                     |
                     ↓
                   Kernel
                     |
                     ↓
                  Hardware


The goal is to prevent one component from accessing resources
that it is not authorized to use.


============================================================
39.5 PRIVILEGE LEVELS
============================================================

Modern processors commonly provide privilege levels.

A simplified model:

    Low privilege
         |
         ↓
    User programs
         |
         ↓
    Operating system
         |
         ↓
    High privilege
         |
         ↓
    Hardware / firmware


Higher privilege generally provides greater access to
system resources.


============================================================
39.6 WHY PRIVILEGE IS IMPORTANT
============================================================

Imagine a normal application could directly:

    • Modify page tables
    • Disable security controls
    • Access every memory location
    • Control hardware devices

That would be extremely dangerous.

Therefore:

    User programs
         ↓
    Limited privileges
         ↓
    OS controls sensitive operations


This is called privilege separation.


============================================================
39.7 MEMORY PROTECTION
============================================================

Memory protection prevents one program from improperly
accessing another program's memory.

Example:

    Program A memory
    +----------------+
    | A's data       |
    +----------------+

    Program B memory
    +----------------+
    | B's data       |
    +----------------+


Program A should normally NOT be able to access:

    Program B's private memory.


Hardware mechanisms such as:

    • Page tables
    • Protection bits
    • Privilege checks
    • Memory-management units

help enforce this separation.


============================================================
39.8 READ / WRITE / EXECUTE PERMISSIONS
============================================================

Memory pages can have permissions.

Common permissions:

    R = Read
    W = Write
    X = Execute


Example:

    +---------------------------+
    | Code page                 |
    | R = Yes                   |
    | W = No                    |
    | X = Yes                   |
    +---------------------------+


This means:

    Can read     → YES
    Can write    → NO
    Can execute  → YES


Another example:

    Data page:

    R = Yes
    W = Yes
    X = No


This helps prevent malicious code execution in certain
memory regions.


============================================================
39.9 EXECUTE-NO-EXECUTE
============================================================

A memory page can sometimes be marked:

    NX = No Execute


Meaning:

    Data stored in that page cannot normally be executed as
    instructions.

Purpose:

    Reduce certain code-injection attacks.


Concept:

    +-----------------------+
    | Memory Page           |
    +-----------------------+
    | Read                  |
    | Write                 |
    | Execute = NO         |
    +-----------------------+


============================================================
39.10 HARDWARE ISOLATION
============================================================

Isolation means separating sensitive components from
untrusted components.

Examples:

    • User space vs kernel space
    • Secure world vs normal world
    • Virtual machines
    • Trusted execution environments
    • Memory regions with different permissions


Basic principle:

    Untrusted code
          |
          X
          |
    Protected resources


============================================================
39.11 TRUSTED EXECUTION
============================================================

Trusted execution means running sensitive code inside a
protected execution environment.

The environment attempts to protect:

    • Code
    • Data
    • Execution state


from other software running on the system.


Concept:

        Normal Software
              |
              X
              |
       +--------------+
       | Trusted      |
       | Environment  |
       |              |
       | Secure Code  |
       | Secure Data  |
       +--------------+


============================================================
39.12 TRUSTED EXECUTION ENVIRONMENT
============================================================

TEE:

    Trusted Execution Environment


A TEE is an isolated environment designed to execute
sensitive operations securely.


Possible applications:

    • Secure payments
    • Cryptographic key protection
    • Biometric processing
    • Digital rights management
    • Secure authentication


============================================================
39.13 SECURE BOOT
============================================================

Secure Boot is a mechanism that helps ensure that only
trusted software is executed during system startup.


Normal startup:

    Power ON
       ↓
    Firmware
       ↓
    Bootloader
       ↓
    Operating System


Secure startup:

    Power ON
       ↓
    Trusted Firmware
       ↓
    Verify Bootloader
       ↓
    Verify OS
       ↓
    Start OS


If verification fails:

    Boot may be stopped or restricted.


============================================================
39.14 WHY SECURE BOOT IS NEEDED
============================================================

Without protection, an attacker might modify the bootloader.

Then:

    Power ON
       ↓
    Malicious Bootloader
       ↓
    Modified OS
       ↓
    Attacker-controlled system


This can be extremely difficult to detect because the
malicious software starts before the operating system's
security mechanisms.


============================================================
39.15 DIGITAL SIGNATURE IN SECURE BOOT
============================================================

Secure Boot commonly relies on cryptographic verification.

Concept:

    Trusted key
        |
        ↓
    Verify signature
        |
        ↓
    Boot component


If:

    Signature valid
        ↓
    Continue boot


If:

    Signature invalid
        ↓
    Reject component


IMPORTANT:

    Secure Boot is about establishing a chain of trust.


============================================================
39.16 CHAIN OF TRUST
============================================================

A chain of trust means each trusted stage verifies the next
stage.

Example:

    Hardware Root of Trust
             ↓
         Firmware
             ↓
         Bootloader
             ↓
             OS
             ↓
       Trusted software


Each stage establishes trust in the next stage.


============================================================
39.17 ROOT OF TRUST
============================================================

Root of Trust is a foundational component that is trusted
by the security system.

It should be difficult to modify or impersonate.

Examples can include:

    • Secure hardware keys
    • Trusted firmware
    • Security processors
    • Hardware security modules


Concept:

             ROOT OF TRUST
                   |
                   ↓
              Firmware
                   |
                   ↓
              Bootloader
                   |
                   ↓
                  OS


============================================================
39.18 HARDWARE SECURITY MODULE
============================================================

HSM:

    Hardware Security Module


A dedicated hardware device designed to protect and perform
cryptographic operations.

Possible functions:

    • Key storage
    • Encryption
    • Decryption
    • Digital signatures
    • Key generation


Important property:

    Sensitive keys can be protected inside dedicated hardware.


============================================================
39.19 TPM
============================================================

TPM:

    Trusted Platform Module


A TPM is a security component used to support functions such
as:

    • Secure key storage
    • Platform measurements
    • Cryptographic operations
    • System integrity verification


Concept:

    CPU / OS
       |
       ↓
      TPM
       |
       ↓
    Protected
    cryptographic
    information


============================================================
39.20 HARDWARE-BASED ISOLATION
============================================================

Hardware can enforce boundaries between:

    • Applications
    • Operating system
    • Hypervisor
    • Secure environments
    • Devices


Examples:

    Memory protection
    Privilege levels
    IOMMU
    TEE
    Virtualization support


============================================================
39.21 IOMMU
============================================================

IOMMU:

    Input-Output Memory Management Unit


It controls how devices access memory.

Without protection, a compromised device could potentially
access memory that it should not access.

Concept:

    Device
      |
      ↓
    IOMMU
      |
      ↓
    Allowed memory


The IOMMU can restrict device memory accesses.


============================================================
39.22 DMA AND SECURITY
============================================================

DMA:

    Direct Memory Access


DMA allows devices to transfer data directly to memory.

Security problem:

    What if a malicious or compromised device accesses
    sensitive memory?

Solution:

    IOMMU can restrict which memory regions the device can
    access.


Concept:

    Device
       |
       ↓
      DMA
       |
       ↓
     IOMMU
       |
       +------→ Allowed memory
       |
       X
       |
    Protected memory


============================================================
39.23 SIDE-CHANNEL ATTACKS
============================================================

A side-channel attack does not necessarily attack the
algorithm directly.

Instead, it observes information leaked by the physical or
microarchitectural behavior of a system.

Possible side channels:

    • Timing
    • Cache behavior
    • Power consumption
    • Electromagnetic emissions
    • Branch-prediction behavior


Basic idea:

    Secret
      ↓
    Hardware behavior
      ↓
    Observable signal
      ↓
    Attacker learns information


============================================================
39.24 TIMING ATTACK
============================================================

A timing attack observes how long an operation takes.

Suppose:

    Operation A → 10 ns
    Operation B → 20 ns


If execution time depends on secret information, an attacker
may infer something about that secret.


Concept:

    Secret
      ↓
    Different execution time
      ↓
    Attacker measures time
      ↓
    Information leakage


============================================================
39.25 CACHE SIDE CHANNEL
============================================================

Modern CPUs use caches for performance.

Cache behavior can depend on what data was accessed.

An attacker may observe:

    Cache hit
    Cache miss
    Access timing


and infer information about another program's activity.


Basic idea:

    Secret-dependent access
             ↓
          Cache state
             ↓
        Timing difference
             ↓
        Information leak


============================================================
39.26 CACHE HIT VS MISS
============================================================

CACHE HIT:

    Requested data is already in cache.

    → Faster


CACHE MISS:

    Requested data is not in cache.

    → Slower


Therefore:

    Hit time ≠ Miss time


This timing difference can potentially become a
side channel.


============================================================
39.27 SPECTRE
============================================================

Spectre is a class of CPU vulnerabilities involving
speculative execution and information leakage.

Important concepts:

    • Speculative execution
    • Branch prediction
    • CPU caches
    • Side-channel observation


Simplified idea:

    Branch prediction
          ↓
    Speculative execution
          ↓
    Secret-dependent activity
          ↓
    Cache state changes
          ↓
    Attacker observes side channel


IMPORTANT:

    Spectre is not simply "a virus."

It is a class of microarchitectural security vulnerabilities.


============================================================
39.28 MELTDOWN
============================================================

Meltdown is a class of vulnerabilities that exploited
specific CPU implementations where speculative/out-of-order
behavior could allow unauthorized information to influence
observable microarchitectural state.

Simplified conceptual chain:

    Unauthorized access attempt
             ↓
    Speculative execution
             ↓
    Microarchitectural side effect
             ↓
    Cache observation
             ↓
    Information leakage


IMPORTANT:

    Meltdown and Spectre are different vulnerability classes.


============================================================
39.29 SPECTRE VS MELTDOWN
============================================================

+----------------+-------------------------------+
| Spectre        | Meltdown                      |
+----------------+-------------------------------+
| Exploits       | Exploited certain             |
| speculative    | implementations' handling    |
| execution and  | of privilege checks during   |
| prediction     | speculative execution        |
|               |                               |
| Can target     | Historically associated with |
| isolation      | leakage across privilege     |
| boundaries     | boundaries                    |
|               |                               |
| Broad class of | More specific class of       |
| attacks        | implementation vulnerabilities|
+----------------+-------------------------------+


For exams:

    Spectre → speculative execution / branch prediction
               + side channel

    Meltdown → speculative execution / privilege isolation
               + side channel


============================================================
39.30 SPECULATIVE EXECUTION
============================================================

Modern processors may execute instructions before it is
certain that they are needed.

Example:

    if (condition)
        execute A
    else
        execute B


CPU may predict the condition and begin executing one path.


If prediction is wrong:

    Architectural result can be discarded.


However, some microarchitectural state such as cache state
may have changed.

This can become relevant to side-channel attacks.


============================================================
39.31 BRANCH PREDICTION AND SECURITY
============================================================

Branch prediction improves performance.

But it can also contribute to speculative-execution attacks.

Concept:

    Branch
      ↓
    Prediction
      ↓
    Speculative execution
      ↓
    Cache effects
      ↓
    Potential information leak


This demonstrates an important COA principle:

    PERFORMANCE OPTIMIZATION
            ↕
         SECURITY


============================================================
39.32 OUT-OF-ORDER EXECUTION AND SECURITY
============================================================

Out-of-order execution allows a CPU to execute independent
instructions in an order different from the original program
order, while maintaining the required architectural behavior.

Benefits:

    • Higher performance
    • Better utilization of execution units


Security concern:

    Microarchitectural side effects can sometimes reveal
    information even when architectural results appear correct.


============================================================
39.33 ARCHITECTURAL VS MICROARCHITECTURAL STATE
============================================================

ARCHITECTURAL STATE:

    State visible through the defined ISA.

Examples:

    • Register values
    • Program counter
    • Defined memory state


MICROARCHITECTURAL STATE:

    Internal implementation details.

Examples:

    • Cache contents
    • Branch predictor state
    • Pipeline state
    • TLB state


Security attacks can exploit differences in microarchitectural
state.


============================================================
39.34 WHY CACHE IS IMPORTANT FOR SECURITY
============================================================

Cache provides:

    Faster memory access


But cache also creates observable timing behavior.

Therefore:

    Cache
      |
      +---- Performance benefit
      |
      +---- Potential side channel


This is an important COA-security connection.


============================================================
39.35 HARDWARE SECURITY ATTACK SURFACE
============================================================

Attack surface means the possible points through which an
attacker may interact with or influence a system.

Hardware attack surfaces may include:

    CPU
    Cache
    Memory
    Firmware
    Boot process
    DMA
    Devices
    I/O controllers
    Debug interfaces
    Speculative execution


============================================================
39.36 FIRMWARE SECURITY
============================================================

Firmware is software stored in or closely associated with
hardware.

Examples:

    • BIOS/UEFI firmware
    • Device firmware
    • Embedded controller firmware


Firmware is security-sensitive because it may execute before
the operating system.


Therefore:

    Firmware integrity
          ↓
    Secure startup
          ↓
    Trusted OS


============================================================
39.37 SECURE BOOT VS TRUSTED EXECUTION
============================================================

SECURE BOOT:

    Protects the startup chain.


TRUSTED EXECUTION:

    Protects sensitive execution during operation.


Simple distinction:

    Secure Boot
        ↓
    "What software is allowed to start?"


    Trusted Execution
        ↓
    "Where can sensitive software safely execute?"


============================================================
39.38 HARDWARE ENCRYPTION SUPPORT
============================================================

Modern CPUs may provide hardware acceleration for
cryptographic algorithms.

Benefits:

    • Faster cryptographic operations
    • Reduced CPU overhead
    • Better performance for encryption workloads


Examples of hardware-supported cryptographic operations may
include:

    • AES acceleration
    • Hash acceleration
    • Random-number generation support


============================================================
39.39 RANDOM NUMBER GENERATION
============================================================

Cryptography often requires unpredictable random values.

Hardware may provide mechanisms for generating random
numbers or entropy.

Used for:

    • Encryption keys
    • Authentication
    • Secure protocols
    • Nonces


Security requires high-quality randomness.


============================================================
39.40 PHYSICAL ATTACKS
============================================================

Hardware can also be attacked physically.

Examples:

    • Device theft
    • Chip probing
    • Fault injection
    • Power analysis
    • Electromagnetic analysis
    • Cold-boot-style attacks


Hardware security may therefore require physical protection
as well as logical protection.


============================================================
39.41 FAULT INJECTION
============================================================

Fault injection attempts to intentionally cause hardware
errors.

Possible techniques include:

    • Voltage manipulation
    • Clock manipulation
    • Electromagnetic interference
    • Laser-based techniques


Goal:

    Cause incorrect behavior that may reveal secrets or
    bypass security checks.


============================================================
39.42 POWER ANALYSIS
============================================================

Electronic circuits consume power.

Power consumption may vary according to operations and data.

An attacker may measure power consumption and attempt to
infer secret information.

Concept:

    Secret data
        ↓
    Computation
        ↓
    Power variation
        ↓
    Measurement
        ↓
    Possible information leakage


============================================================
39.43 DEFENCE AGAINST SIDE CHANNELS
============================================================

Possible defensive techniques include:

    • Constant-time algorithms
    • Cache isolation
    • Randomization
    • Hardware partitioning
    • Speculation controls
    • Memory access isolation
    • Cryptographic masking
    • Microcode/firmware updates


No single technique solves every side-channel problem.


============================================================
39.44 CONSTANT-TIME IDEA
============================================================

A constant-time algorithm attempts to avoid secret-dependent
timing differences.

BAD IDEA:

    if secret_bit == 1:
        perform extra operation


This may produce different timing.

BETTER IDEA:

    Structure computation so observable execution behavior
    does not depend directly on secret values.


Important:

    "Constant-time" does not mean literally identical
    hardware execution in every possible situation.

It is a security design goal.


============================================================
39.45 HARDWARE SECURITY LAYERS
============================================================

A secure computer can be viewed as multiple layers:

    +--------------------------------+
    | Applications                   |
    +--------------------------------+
    | Operating System               |
    +--------------------------------+
    | Hypervisor / Security Software |
    +--------------------------------+
    | CPU / Memory Protection        |
    +--------------------------------+
    | Secure Firmware                |
    +--------------------------------+
    | Hardware Root of Trust         |
    +--------------------------------+


Security should exist across layers.

39.46 COMPLETE SECURE BOOT EXAMPLE
============================================================

STEP 1:

    Power ON


STEP 2:

    Hardware starts trusted firmware


STEP 3:

    Firmware verifies bootloader


STEP 4:

    Bootloader verifies operating-system components


STEP 5:

    OS starts


STEP 6:

    OS enforces user/kernel isolation


STEP 7:

    Applications run with restricted privileges


Concept:

    Hardware Root of Trust
             ↓
         Firmware
             ↓
        Bootloader
             ↓
             OS
             ↓
       Applications

Virtualization allows multiple virtual machines to share

Concept:

       +-----------+
       | VM 1      |
       +-----------+
       | VM 2      |
       +-----------+
       | VM 3      |
       +-----------+

39.48 SECURITY AND DMA
============================================================

Without proper protection:

    Device
      |
      ↓
     DMA
      |
      ↓
    Arbitrary memory


With IOMMU:

    Device
      |
      ↓
     IOMMU
      |
      ↓
    Approved memory only


Therefore:

    IOMMU = important hardware mechanism for controlling
            device memory access.


============================================================
39.49 SECURITY AND MEMORY HIERARCHY
============================================================

COA memory hierarchy:

    Registers
        ↓
      Cache
        ↓
      RAM
        ↓
    Storage


Security must consider every level.

For example:

    Cache → side-channel risk
    RAM   → unauthorized access risk
    Storage → data-at-rest risk


============================================================
39.50 SECURITY AND CPU PIPELINE
============================================================

Pipeline:

    IF → ID → EX → MEM → WB


Security concerns may involve:

    • Speculative execution
    • Branch prediction
    • Pipeline state
    • Data dependencies
    • Side-channel effects


Thus:

    Pipeline optimization
          ↓
       Performance

but:

    Pipeline behavior
          ↓
       Security considerations


============================================================
39.51 SECURITY AND ISA
============================================================

ISA can provide architectural mechanisms for security.

Examples:

    • Privilege levels
    • Memory access controls
    • Special instructions
    • Virtualization support
    • Secure execution mechanisms


Therefore:

    ISA is not only about performance.

It also defines important security-related behavior.


============================================================
39.52 SECURITY PRINCIPLE — LEAST PRIVILEGE
============================================================

Principle of Least Privilege:

    Give a component only the permissions it needs.


Example:

    Calculator application

should NOT need:

    Full hardware control


Instead:

    Application
       ↓
    Limited permissions
       ↓
    OS-controlled resources


============================================================
39.53 SECURITY PRINCIPLE — DEFENSE IN DEPTH
============================================================

Do not depend on a single security mechanism.

Example:

    Secure Boot
        +
    Memory Protection
        +
    Privilege Separation
        +
    Encryption
        +
    TEE
        +
    Monitoring


If one mechanism fails, others may still provide protection.


============================================================
39.54 SECURITY PRINCIPLE — TRUST BOUNDARY
============================================================

A trust boundary separates:

    Trusted components
          |
          |
    ----------------
      Trust boundary
    ----------------
          |
    Untrusted components


Crossing the boundary should involve appropriate checks.


============================================================
39.55 IMPORTANT DEFINITIONS
============================================================

HARDWARE SECURITY:

    Protection of hardware, data and execution using
    hardware and architectural mechanisms.


SECURE BOOT:

    Verification-based startup process that helps ensure
    trusted software is executed.


TEE:

    Trusted Execution Environment for protected execution.


TPM:

    Hardware security component supporting platform
    integrity and cryptographic functions.


IOMMU:

    Hardware unit controlling device memory access.


SIDE CHANNEL:

    Information leakage through observable system behavior.


SPECTRE:

    Vulnerability class involving speculative execution,
    prediction and side-channel leakage.


MELTDOWN:

    Vulnerability class involving speculative execution and
    privilege-isolation issues in affected CPU implementations.


ROOT OF TRUST:

    Foundational trusted component from which trust is
    established.

    Protected execution environment.


TPM:

    Hardware-assisted platform security.


IOMMU:

    Controls device memory access.


SIDE CHANNEL:

    Leakage through observable behavior.


CACHE SIDE CHANNEL:

    Cache state → timing → possible information leak.


SPECTRE:

    Speculation/prediction + side channel.


MELTDOWN:

    Speculative execution + privilege-isolation leakage
    in affected implementations.


LEAST PRIVILEGE:

    Give only required permissions.


DEFENSE IN DEPTH:

    Multiple security layers.
