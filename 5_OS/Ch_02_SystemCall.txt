============================================================
1. WHAT IS A SYSTEM CALL?
============================================================

A System Call is a mechanism through which a user-level program
requests a service from the Operating System kernel.

Simple definition:

    System Call = Interface between User Program and OS Kernel

A normal application cannot directly perform certain privileged
operations.

For example, an application may need to:

    - Create a process
    - Open a file
    - Read data from a file
    - Write data to a file
    - Allocate certain resources
    - Communicate with another process
    - Create a socket
    - Change permissions

For these operations, the application requests the kernel through
system calls.


------------------------------------------------------------
REAL-WORLD ANALOGY
------------------------------------------------------------

Imagine a bank.

You are a customer.

You cannot directly enter the bank's secure vault and take money.

Instead:

    Customer
       |
       | Request
       v
    Bank Employee
       |
       | Authorized operation
       v
    Bank System
       |
       v
    Result

Similarly:

    User Application
          |
          | System Call
          v
       Kernel
          |
          | Hardware/resource operation
          v
       Hardware


============================================================
2. WHY DO WE NEED SYSTEM CALLS?
============================================================

Modern operating systems provide protection between applications
and hardware.

Suppose a program directly modifies disk hardware.

It could:

    - Corrupt files
    - Delete important data
    - Crash the system
    - Access another user's data
    - Damage OS structures

Therefore, applications normally run in:

    USER MODE

The kernel runs in:

    KERNEL MODE

Privileged operations are performed by the kernel.

System calls provide a controlled gateway from user mode to
kernel mode.


============================================================
3. USER MODE AND KERNEL MODE
============================================================

Modern CPUs generally provide different privilege levels.

The two important conceptual modes are:

    1. User Mode
    2. Kernel Mode


------------------------------------------------------------
USER MODE
------------------------------------------------------------

Applications normally execute in user mode.

Examples:

    - Chrome
    - VS Code
    - Text editor
    - Calculator
    - Python program

User-mode programs have restricted access.

They normally cannot directly:

    - Access arbitrary hardware
    - Execute privileged CPU instructions
    - Modify kernel memory
    - Control hardware directly


------------------------------------------------------------
KERNEL MODE
------------------------------------------------------------

The OS kernel executes in kernel mode.

Kernel mode has much greater privileges.

The kernel can:

    - Manage memory
    - Manage processes
    - Access devices
    - Manage filesystems
    - Schedule CPU
    - Handle interrupts
    - Manage networking
    - Control hardware

5. SYSTEM CALL INTERFACE
============================================================

The System Call Interface (SCI) is the mechanism that allows

Conceptually:

    User Space
    ---------------------
       Application
            |
       Library/API
            |
       System Call
    ---------------------
    Kernel Space
            |
       System Call Handler
            |
       Kernel Service
            |
       Hardware


The kernel maintains a collection of supported system calls.

Each system call generally has an identifier/number.

For example, conceptually:

    System Call Number
           |
           v
    +----------------+
    | System Call    |
    | Table          |
    +----------------+
       |     |     |

6. SYSTEM CALL NUMBER
============================================================

Operating systems internally identify system calls.

A system call number allows the kernel to determine which
operation the user process is requesting.

Conceptually:

    User Program
         |
         | System call number = X
         v
    Kernel
         |
         | Look up X
         v
    Corresponding system call handler


IMPORTANT:

Exact system call numbers depend on the operating system,
architecture, and ABI.

Therefore, do not memorize a system-call number universally.


============================================================
7. HOW A SYSTEM CALL WORKS
============================================================

Let's understand the process step by step.

Suppose a program wants to read a file.

Step 1:
    Application calls a library/API function.

Step 2:
    Parameters are prepared.

Step 3:
    System call identifier is prepared.

Step 4:
    A special CPU instruction causes a transition into kernel mode.

Step 5:
    Kernel identifies the requested system call.

Step 6:
    Kernel validates parameters and permissions.

Step 7:
    Kernel performs the requested operation.

Step 8:
    Kernel prepares the return value.

Step 9:
    CPU returns to user mode.

Step 10:
    Application continues execution.


FLOW:

    User Mode
       |
       v
    Application
       |
       v
    API / Library Wrapper
       |
       v
    System Call Instruction
       |
       v
    Kernel Mode
       |
       v
    System Call Handler
       |
       v
    Kernel Service
       |
       v
    Hardware / Driver
       |
       v
    Return Result
       |
       v
    User Mode


============================================================
8. SYSTEM CALL vs FUNCTION CALL
============================================================

This is extremely important for interviews and exams.


FUNCTION CALL
-------------

A function call usually transfers control from one function
to another within the same program/address space.

Example:

    result = add(a, b);


Conceptually:

    Function A
       |
       v
    Function B


SYSTEM CALL
------------

A system call requests a service from the operating system kernel.

Conceptually:

    User Program
         |
         v
    Kernel


Important difference:

    Function call:
        Program → Function

    System call:
        User Program → Kernel


System calls generally involve more overhead than ordinary
function calls because they may involve privilege transitions
and kernel-side work.


============================================================
9. SYSTEM CALL vs API
============================================================

These concepts are often confused.

API:

    Application Programming Interface

A system call:

    Kernel interface/mechanism for requesting OS services.

An API may internally use one or more system calls.

For example, a programming-language library function may provide
a convenient interface to an underlying OS service.

Conceptually:

    Application
         |
         v
        API
         |
         v
    Library Function
         |
         v
    System Call
         |
         v
       Kernel


IMPORTANT:

    API ≠ System Call

An API is a programming interface.

A system call is an OS/kernel entry mechanism.

11. PROCESS CONTROL SYSTEM CALLS
============================================================

Process control system calls deal with processes.

Typical operations:

    - Create process
    - Terminate process
    - Execute a program
    - Wait for a process
    - Signal a process
    - Get process information


Examples in Unix/Linux:

    fork()
    exec()
    wait()
    exit()
    _exit()
    kill()


------------------------------------------------------------
fork()
------------------------------------------------------------

fork() creates a new process.

The existing process is called:

    Parent process

The newly created process is called:

    Child process


Conceptually:

        Parent
          |
        fork()
          |
       +--+--+
       |     |
       v     v
    Parent  Child


IMPORTANT:

After fork(), both parent and child continue execution
from the point after fork(), subject to scheduling.


------------------------------------------------------------
exec()
------------------------------------------------------------

The exec family replaces the current process image with
another program.

Important distinction:

    fork() → creates a new process

    exec() → replaces the current process image


A common pattern is:

    fork()
       |
       +------ Child
                 |
                exec()
                 |
                 v
             New Program


------------------------------------------------------------
wait()
------------------------------------------------------------

wait() allows a parent process to wait for a child process
to change state, commonly to terminate.

Example:

    Parent
       |
       | wait()
       v
    waits for child


------------------------------------------------------------
exit()
------------------------------------------------------------

exit() terminates a process and performs process termination
activities.

Conceptually:

    Process
       |
      exit()
       |
       v
    Terminated

============================================================

File-related system calls allow programs to interact with files.

Common operations:

    - Close
    - Delete


Common Unix/Linux interfaces include:

    open()
    read()

------------------------------------------------------------
open()
------------------------------------------------------------

Used to open a file and obtain a file descriptor.

Conceptually:

    open("data.txt")
            |
            v
       File Descriptor


------------------------------------------------------------
FILE DESCRIPTOR
------------------------------------------------------------

A file descriptor is a small integer used by a process to
refer to an open file or another I/O object.

Common Unix conventions:

    0 → standard input
    1 → standard output
    2 → standard error


Example:

    fd = open(...)

Here:

    fd = file descriptor


------------------------------------------------------------
read()
------------------------------------------------------------

Reads data from an open file descriptor.

Conceptually:

    File
      |
      | read()
      v
    Process memory


------------------------------------------------------------
write()
------------------------------------------------------------

Writes data through a file descriptor.

Conceptually:

    Process memory
          |
        write()
          |
          v
        File


------------------------------------------------------------
close()
------------------------------------------------------------

Releases the file descriptor when the program is finished
using the corresponding open file.

19. TRAP / SYSCALL INSTRUCTION
============================================================

How does a user program enter the kernel?

A special mechanism/instruction is used.

Depending on architecture and OS, this may involve

    syscall
    sysenter
    trap mechanisms

The exact instruction is architecture-specific.

Conceptually:

    User Mode
        |
        | system-call instruction
        v
    Kernel Mode


This transition is controlled by the processor.


============================================================
20. SYSTEM CALL HANDLING
============================================================

When the system-call mechanism is invoked:

    1. CPU performs controlled privilege transition.
    2. Kernel entry point is reached.
    3. Kernel identifies the system call.
    4. Arguments are obtained safely.
    5. Kernel validates the request.
    6. Kernel performs the operation.
    7. Return value/error is prepared.
    8. Execution returns to user mode.


============================================================
21. SYSTEM CALL ARGUMENTS
============================================================

A system call may require arguments.

Example concept:

    read(fd, buffer, count)


Arguments:

    fd      → file descriptor
    buffer  → memory location for data
    count   → amount of data


The OS must carefully validate arguments.

Why?

Because user programs cannot be blindly trusted.

Potential problems:

    - Invalid pointer
    - Invalid memory address
    - Unauthorized access
    - Incorrect size
    - Malicious input


Therefore:

    User Input
        |
        v
    Validation
        |
        v
    Kernel Operation


============================================================
22. RETURN VALUES AND ERRORS
============================================================

System calls commonly return:

    - Success value
    - Failure indication
    - Data/result

For example:

    read()

may return the number of bytes successfully read,
or indicate an error.

The exact error-reporting mechanism depends on the OS/API.


Common Linux/POSIX concept:

    errno

When an operation fails, errno can provide information
about the error condition through the relevant library/API
conventions.


============================================================
23. BLOCKING SYSTEM CALL
============================================================

A system call can cause a process to wait.

Example:

    read()

If requested data is not currently available, the process
may block depending on the object and flags.

Meaning:

    Process
       |
       | read()
       v
    Waiting
       |
       v
    Data becomes available
       |
       v
    Process continues


This connects system calls with:

    - Process states
    - Scheduling
    - I/O
    - Context switching


============================================================
24. BLOCKING vs NON-BLOCKING
============================================================

BLOCKING:

    Process may wait until operation can proceed.


NON-BLOCKING:

    Operation returns without waiting for the resource/data
    to become available.


Example concept:

    Blocking read:
        "Wait until data is available."

    Non-blocking read:
        "Return now if data is not available."


This is very important in:

    - Network programming
    - Servers
    - Operating systems
    - Concurrent programming


============================================================
25. SYSTEM CALL OVERHEAD
============================================================

A system call generally has more overhead than a simple
function call.

Why?

Because it may involve:

    - User → kernel transition
    - Saving/restoring execution state
    - Argument validation
    - Kernel processing
    - Possible scheduling
    - Possible context switch
    - Device/I/O waiting


IMPORTANT:

    System call ≠ always context switch

A privilege transition into the kernel is not necessarily
the same thing as switching from one process to another.

This distinction is important for interviews.


============================================================
26. SYSTEM CALL vs CONTEXT SWITCH
============================================================

SYSTEM CALL:

    User program requests a kernel service.

CONTEXT SWITCH:

    CPU changes execution from one process/thread to another.


Example:

    Process A
       |
    system call
       |
       v
    Kernel
       |
       v
    Process A continues

No process switch necessarily occurred.


But:

    Process A
       |
    blocking system call
       |
       v
    Kernel
       |
       v
    Scheduler
       |
       v
    Process B

Here a context switch may occur.


============================================================
27. SYSTEM CALL vs INTERRUPT
============================================================

INTERRUPT:

    Usually an asynchronous event that requests CPU attention,
    commonly generated by hardware.

Examples:

    - Network packet arrival
    - Timer event
    - Keyboard input


SYSTEM CALL:

    A user program intentionally requests an OS service.


Conceptually:

    System Call:
        Program → Kernel

    Hardware Interrupt:
        Hardware → CPU/Kernel


Exceptions/traps are another category and can be synchronous
with the currently executing instruction.


============================================================
28. SYSTEM CALL vs TRAP
============================================================

A trap is a synchronous mechanism/event associated with
execution of an instruction.

Historically and conceptually, operating systems may use
trap mechanisms to enter the kernel.

Modern architectures can provide dedicated system-call
instructions.

Therefore:

    Trap = broader CPU exception/entry concept

    System call = intentional request for OS service

The exact terminology varies by architecture.

34. SYSTEM CALL SECURITY
============================================================

System calls are security-sensitive.

Suppose a malicious program requests:

    "Give me access to another user's private file."

The kernel checks:

    - Who is requesting?
    - What resource?
    - What permissions?
    - Is the operation allowed?
    - Are arguments valid?


Therefore:

    System Call
         |
         v
    Authentication / Credentials
         |
         v
    Authorization
         |
         v
    Resource Access


============================================================
35. WHY USER PROGRAMS CANNOT DIRECTLY ACCESS HARDWARE
============================================================

If every application had unrestricted hardware access:

    Application A
       |
       +---- Disk

    Application B
       |
       +---- Memory

    Application C
       |
       +---- Network card

There would be no central control.

Possible result:

    - Data corruption
    - Security vulnerabilities
    - Resource conflicts
    - System crashes


Instead:

    Applications
         |
      System Calls
         |
       Kernel
         |
      Drivers
         |
      Hardware


The kernel acts as the trusted control layer.

42. INTERVIEW QUESTIONS
============================================================

Q1. What is a system call?

Answer:
A system call is a controlled interface through which a
user-level program requests a service from the OS kernel.


Q2. Why are system calls required?

Answer:
Because user programs operate with restricted privileges and
cannot directly perform many privileged OS/hardware operations.


Q3. What is the difference between user mode and kernel mode?

Answer:

    User mode:
        Restricted privileges

    Kernel mode:
        Privileged access to OS resources and hardware


Q4. Is every function call a system call?

Answer:

    No.

A normal function call can occur entirely in user space.


Q5. Does every system call cause a context switch?

Answer:

    No.

A system call causes entry into kernel execution, but a
process context switch occurs only when the scheduler changes
the running process/thread.


Q6. What does fork() do?

Answer:

    Creates a new child process.


Q7. What does exec() do?

Answer:

    Replaces the current process image with a new program.


Q8. What is a file descriptor?

Answer:

    A small integer used by a process to refer to an open
    file or other I/O object in Unix-like systems.


Q9. What is strace?

Answer:

    A Linux tool that can trace system calls and signals
    made/received by a program.


Q10. What is the purpose of the system-call table?

Answer:

    Conceptually, it maps system-call identifiers to the
    corresponding kernel handlers.

MOST IMPORTANT INTERVIEW CONCEPT:

    System Call ≠ Context Switch

A system call transfers execution into the kernel to request
an OS service.

A context switch changes the CPU's execution from one
process/thread to another.
