Chapter 8 explains how the theoretical concepts from Chapters 4–7
are used to BUILD AN ACTUAL LEXICAL ANALYZER.

We will study:

    1. Input buffering
    2. Lookahead
    3. Sentinel technique
    4. Lexical errors
    5. Lexical error recovery
    6. Symbol-table interaction
    7. Lex / Flex
    8. Practical lexical analyzer construction


The overall idea:


                         SOURCE PROGRAM
                               │
                               ▼
                     ┌──────────────────┐
                     │ LEXICAL ANALYZER │
                     └────────┬─────────┘
                              │
                              ▼
                           TOKENS
                              │
                              ▼
                     SYNTAX ANALYZER
                           (PARSER)


Example source code:


        int sum = a + 25;


becomes:


        <KEYWORD, int>
        <ID, sum>
        <ASSIGN, =>
        <ID, a>
        <PLUS, +>
        <NUMBER, 25>
        <SEMICOLON, ;>


The lexical analyzer performs this transformation.


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
1. WHAT IS A LEXICAL ANALYZER?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

DEFINITION:

A lexical analyzer, also called a LEXER or SCANNER, is the compiler
phase that reads the source program as a sequence of characters and
groups those characters into meaningful units called TOKENS.


In simple words:


    CHARACTERS
        ↓
    LEXICAL ANALYZER
        ↓
    TOKENS


Example:


    Source:


        count = price + 100;


    Characters:


        c o u n t   =   p r i c e   +   1 0 0   ;


    Tokens:


        ID
        ASSIGN
        ID
        PLUS
        NUMBER
        SEMICOLON


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
2. POSITION OF LEXICAL ANALYZER IN A COMPILER
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━


                         SOURCE PROGRAM
                               │
                               ▼
                    ┌─────────────────────┐
                    │  LEXICAL ANALYZER   │
                    └──────────┬──────────┘
                               │
                               ▼
                             TOKENS
                               │
                               ▼
                    ┌─────────────────────┐
                    │   SYNTAX ANALYZER   │
                    │       PARSER        │

The lexical analyzer is therefore the FIRST major compiler phase
that processes the source program.


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
3. INPUT AND OUTPUT OF A LEXICAL ANALYZER
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

INPUT:


    Character stream


OUTPUT:


    Token stream


Diagram:


        ┌───────────────────────┐
        │    SOURCE PROGRAM     │
        │                       │
        │ int x = 25 + y;       │
        └───────────┬───────────┘
                    │

             LEXICAL ANALYZER
                    │

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
4. MAIN RESPONSIBILITIES OF A LEXICAL ANALYZER
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

A lexer generally performs the following jobs:


    • Read source characters
    • Group characters into lexemes
    • Recognize token patterns
    • Produce tokens
    • Ignore whitespace
    • Ignore comments
    • Recognize keywords
    • Recognize identifiers
    • Recognize literals
    • Recognize operators
    • Recognize separators
    • Report lexical errors
    • Maintain relevant symbol-table information
    • Track source positions


Therefore:


                    LEXICAL ANALYZER
                           │
          ┌────────────────┼────────────────┐
          ▼                ▼                ▼
       SCANNING         RECOGNITION      REPORTING
          │                │                │
          ▼                ▼                ▼
      Characters         Tokens           Errors


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
5. LEXEME, TOKEN AND PATTERN
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

These three terms are extremely important.


TOKEN:

A token is a category/type of lexical unit.


Examples:


        ID
        NUMBER
        IF
        PLUS
        ASSIGN


LEXEME:

A lexeme is the actual sequence of characters in the source program
that matches a token pattern.


Example:


        total


is a lexeme belonging to:


        ID


PATTERN:

A pattern is the rule describing which lexemes belong to a token.


Example:


        ID → letter(letter|digit)*


Therefore:


        PATTERN
           ↓
        recognizes
           ↓
        LEXEME
           ↓
        classified as
           ↓
        TOKEN


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
6. EXAMPLE — TOKEN, LEXEME AND PATTERN
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Source:


        int count = 25;


For:


        count


we have:


        TOKEN:


            ID


        LEXEME:


            count


        PATTERN:


            letter(letter|digit)*


For:


        25


we have:


        TOKEN:


            NUMBER


        LEXEME:


            25


        PATTERN:


            digit+


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
7. TOKEN ATTRIBUTES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

A token may contain additional information called an ATTRIBUTE.


General representation:


        <TOKEN-NAME, ATTRIBUTE>


Example:


        <ID, "count">


        <NUMBER, 250>


        <PLUS, +>


For identifiers, the attribute may point to an entry in the
symbol table.


Example:


        <ID, pointer-to-symbol-table-entry>


For numeric constants, the attribute may contain the numeric value.


Example:


        <NUM, 250>


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
8. BASIC LEXER ARCHITECTURE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━


                    SOURCE CHARACTER STREAM
                             │
                             ▼
                    ┌─────────────────┐
                    │ INPUT BUFFER     │
                    └────────┬────────┘
                             │
                             ▼
                    ┌─────────────────┐
                    │ LEXICAL         │
                    │ ANALYZER        │
                    └───────┬─────────┘
                            │
             ┌──────────────┼──────────────┐
             ▼              ▼              ▼
          TOKEN          ATTRIBUTE       ERROR
             │              │
             └───────┬──────┘
                     ▼
                SYMBOL TABLE
                     │
                     ▼
                TOKEN STREAM


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
9. WHY INPUT BUFFERING IS REQUIRED
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

A source program can contain thousands or millions of characters.

Reading one character at a time directly from disk can be expensive.


Therefore the lexer uses an INPUT BUFFER.


Instead of:


        disk → character → lexer
        disk → character → lexer
        disk → character → lexer


we use:


        disk
          │
          ▼
      ┌───────────────┐
      │ INPUT BUFFER  │
      │ a b c d e ... │
      └───────┬───────┘
              │
              ▼
           LEXER


The buffer reduces expensive I/O operations.


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
10. INPUT BUFFERING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Suppose the source contains:


        int total = price + tax;


The input buffer may contain:


        ┌───────────────────────────────────────────┐
        │ i n t   t o t a l   =   p r i c e   + ... │
        └───────────────────────────────────────────┘
          ↑
        current position


The lexical analyzer reads characters from memory instead of repeatedly
requesting them from the external input source.


Benefits:


    • Faster scanning
    • Fewer I/O operations
    • Easier lookahead
    • Efficient implementation


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
11. TWO-BUFFER SCHEME
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

A classic lexical analyzer implementation uses TWO BUFFERS.


Conceptually:


        ┌───────────────────────────────┐
        │          BUFFER 1             │
        │ a b c d e f g h ...           │
        ├───────────────────────────────┤
        │          BUFFER 2             │
        │ i j k l m n o p ...           │
        └───────────────────────────────┘


The lexer can process one buffer while the other can be refilled.


This avoids frequent interruption while scanning.


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
12. TWO-BUFFER SCHEME — POINTERS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Two important pointers are commonly used:


        lexemeBegin
        forward


Diagram:


        SOURCE BUFFER


        i n t   t o t a l   =   2 5   ;
        ↑                   ↑
        │                   │
    lexemeBegin          forward


lexemeBegin:


    Points to the beginning of the current lexeme.


forward:


    Moves ahead while searching for the end of the lexeme.


Example:


        total


During recognition:


        t o t a l
        ↑       ↑
        │       │
        begin   forward


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
13. LEXEME BEGIN AND FORWARD
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Consider:


        int count = 25;


Initially:


        lexemeBegin
        ↓
        i n t   c o u n t ...
        ↑
        forward


After recognizing "int":


        lexemeBegin
        ↓
        i n t   c o u n t
            ...
            ↑
          forward


Then lexemeBegin moves to the next nonprocessed character.


The basic relationship:


        lexemeBegin
              │
              ▼
        beginning of lexeme


        forward
              │
              ▼
        searches for lexeme end


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
14. LOOKAHEAD
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Sometimes the lexer must inspect one or more characters beyond the
current character to determine which token is being read.


This is called:


        LOOKAHEAD


Example:


        <
        <=


When the lexer sees:


        <


it cannot immediately know whether the token is:


        LESS


or:


        LESS_EQUAL


It must inspect the next character.


Diagram:


        Input:


            < =


            │
            ▼
          lexer
            │
            ▼
        inspect next char
            │
            ▼
            =
            │
            ▼
        token = <=


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
15. LOOKAHEAD EXAMPLE — = VS ==
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Suppose the language has:


        =    assignment
        ==   equality


Input:


        ==


Lexer reads first:


        =


It asks:


        "Is the next character also = ?"


If YES:


        ==


is recognized.


If NO:


        =


is recognized.


Therefore:


        LOOKAHEAD
            ↓
        DISAMBIGUATION
            ↓
        CORRECT TOKEN


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
16. RETRACTION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Sometimes the lexer reads one character too far.


Example:


        count;


The lexer reads:


        c o u n t ;


To recognize the identifier, it discovers that:


        ;


does not belong to the identifier.


Therefore it may need to:


        RETRACT


the forward pointer by one character.


Diagram:


        c o u n t ;
        ↑         ↑
        begin   forward
                  │
                  └── one character too far


Then:


        forward ← forward - 1


so that:


        ;


can be processed as the next token.


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
17. SENTINEL TECHNIQUE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

A SENTINEL is a special character placed at the end of a buffer to
indicate that the buffer has ended.


Instead of checking:


        "Have I reached the end of the buffer?"


after every character, the lexer encounters the sentinel.


Conceptually:


        ┌──────────────────────────────┐
        │ a b c d e f g h #            │
        └──────────────────────────────┘
                              ↑
                           SENTINEL


Here # is only an illustrative sentinel.


The actual sentinel must be a character that cannot be confused with
valid source input, or an equivalent end-of-input mechanism is used.


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
18. WHY SENTINELS IMPROVE SCANNING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Without sentinel:


        read character
             ↓
        check buffer end
             ↓
        process character
             ↓
        repeat


With sentinel:


        read character
             ↓
        process
             ↓
        if sentinel → refill/end
             ↓
        repeat


The sentinel reduces repeated boundary checks and makes the scanning
loop more efficient.


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
19. TWO-BUFFER + SENTINEL SCHEME
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━


        ┌──────────────────────────┐
        │        BUFFER 1          │
        │ a b c d e f g #          │
        └──────────────────────────┘
                          ↑
                       sentinel


        ┌──────────────────────────┐
        │        BUFFER 2          │
        │ h i j k l m n #          │
        └──────────────────────────┘
                          ↑
                       sentinel


When forward reaches the sentinel:


        BUFFER 1
            │
            ▼
        load BUFFER 2


When BUFFER 2 ends:


        BUFFER 2
            │
            ▼
        refill BUFFER 1


This gives continuous scanning.


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
20. TOKEN RECOGNITION USING FINITE AUTOMATA
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

From previous chapters:


        REGULAR EXPRESSION
                ↓
              ε-NFA
                ↓
               DFA


The lexer can use the DFA to recognize tokens.


Example identifier pattern:


        letter(letter|digit)*


Conceptual DFA:


                  letter
              ┌────────────┐
              │            ▼
            (START) ───► (ID)
                           ▲ │
                           │ │ letter/digit
                           └─┘


ID is accepting.


Therefore:


        abc
        x1
        total25


can be recognized as identifiers.


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
21. MAXIMAL MUNCH / LONGEST MATCH
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

A lexer commonly follows the:


        LONGEST MATCH


principle.


This is also called:


        MAXIMAL MUNCH


Example:


        >=


Suppose both are possible:


        >
        >=


The lexer should choose:


        >=


because it consumes the longest valid lexeme.


Similarly:


        ==


should not normally be tokenized as:


        =
        =


when:


        ==


is a valid token.


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
22. LONGEST MATCH EXAMPLE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Suppose tokens include:


        <
        <=
        <<


Input:


        <<


The lexer tries to consume the longest valid prefix.


Possible matches:


        <
        <<
       


Longest valid match:


        <<


Therefore:


        TOKEN = SHIFT_LEFT


This principle is central to practical lexical analysis.


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
23. KEYWORDS VS IDENTIFIERS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Consider:


        int


and:


        integer


Both may satisfy the identifier pattern.


But:


        int


is a keyword.


Therefore the lexer needs a mechanism to distinguish keywords from
ordinary identifiers.


Two common approaches:


    METHOD 1:
        Separate DFA/rules for keywords.


    METHOD 2:
        Recognize everything as ID, then search a keyword table.


Example:


        Input: int


        Recognize:
            ID


        Keyword table lookup:
            "int" → KEYWORD_INT


Therefore final token:


        <KEYWORD_INT, int>


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
24. SYMBOL TABLE INTERACTION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

The lexer often interacts with the SYMBOL TABLE.


Example:


        total


is recognized as an identifier.


The lexer may:


        1. Search symbol table.
        2. If found, use existing entry.
        3. If not found, create a new entry.
        4. Return token containing a reference to that entry.


Diagram:


        source
          │
          ▼
        "total"
          │
          ▼
       LEXER
          │
          ▼
     IDENTIFIER
          │
          ▼
     SYMBOL TABLE
          │
          ▼
     entry for total
          │
          ▼
       <ID, ptr>


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
25. WHAT CAN BE STORED IN SYMBOL TABLE?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

A symbol-table entry can contain:


    • Name
    • Token/category
    • Data type
    • Scope
    • Storage location
    • Memory address
    • Size
    • Parameter information
    • Return type
    • Line information
    • Link to scope information


Example:


        ┌────────────────────────────┐
        │ SYMBOL TABLE ENTRY         │
        ├────────────────────────────┤
        │ Name: total                │
        │ Kind: variable             │
        │ Type: int                  │
        │ Scope: main                │
        │ Address: 1004              │
        └────────────────────────────┘


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
26. WHITESPACE HANDLING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Whitespace generally includes:


        space
        tab
        newline
        carriage return


Example:


        int   x   =   10;


The lexer usually ignores whitespace because it normally does not
represent a token.


Thus:


        int x = 10;


and:


        int     x   =   10;


usually produce the same token sequence.


Exception:


Some languages use whitespace as syntactically significant.


Therefore the exact behavior depends on the language.


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
27. COMMENT HANDLING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Comments are usually removed or ignored by the lexer.


Example:


        int x = 10;   // initialize x


The lexer produces tokens for:


        int
        x
        =
        10
        ;


but ignores:


        // initialize x


Block comment:


        /*
           this is a comment
        */


is also generally skipped.


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
28. LEXICAL ERRORS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

A lexical error occurs when the input contains a sequence of
characters that cannot form a valid token according to the language's
lexical rules.


Examples:


        @@@


if @ is not a valid character.


Another example:


        12abc


if the language does not allow such a numeric format.


Another example:


        "hello


if a string literal is not properly terminated.


Therefore:


        INVALID CHARACTER / INVALID LEXEME
                    ↓
              LEXICAL ERROR


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
29. TYPES OF LEXICAL ERRORS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Common lexical errors include:


    • Illegal character
    • Invalid identifier
    • Invalid number
    • Unterminated string
    • Unterminated character literal
    • Unterminated comment
    • Invalid escape sequence
    • Malformed operator
    • Invalid numeric suffix


Example:


        "hello


Missing closing quote.


Result:


        LEXICAL ERROR:
        Unterminated string literal.


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
30. ERROR REPORTING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

A good lexer should report useful information.


Poor message:


        ERROR


Better message:


        Lexical Error:
        Invalid character '@'
        at line 5, column 12


Useful information includes:


        • Error type
        • Actual character/lexeme
        • Line number
        • Column number
        • Position
        • Possible correction


Good diagnostics make compiler errors much easier to understand.


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
31. LEXICAL ERROR RECOVERY
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

After finding an invalid lexeme, the lexer should ideally recover and
continue scanning instead of immediately stopping the entire compiler.


General idea:


        invalid input
              │
              ▼
        report error
              │
              ▼
        skip / modify input
              │
              ▼
        continue scanning


This allows multiple errors to be reported in one compilation.


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
32. ERROR RECOVERY STRATEGIES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Common simple strategies include:


    1. Delete an extraneous character.


    2. Insert a missing character.


    3. Replace an incorrect character.


    4. Transpose adjacent characters.


    5. Skip characters until a valid token boundary is found.


Example:


        fi!


If ! is invalid after identifier:


        fi!


Lexer can report:


        Invalid character !


and continue from the next character.


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
33. PANIC-MODE STYLE LEXICAL RECOVERY
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

A simple recovery strategy is to skip characters until a likely token
boundary is found.


For example:


        int x = @@@ + 10;


The lexer may:


        recognize int
        recognize x
        recognize =
        encounter @
        report error
        skip invalid characters
        recognize +
        recognize 10


This allows compilation to continue.


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
34. SOURCE POSITION TRACKING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

The lexer should normally maintain:


        line number
        column number


Example:


        int x = 10;
            ^
            column 5


If an error occurs:


        int x = @10;


the lexer can report:


        Line 1, Column 9:
        invalid character '@'


Position tracking is essential for useful diagnostics.


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
35. LEXICAL ANALYZER ALGORITHM
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

A simplified lexer algorithm:


    START


      ↓


    Read next character


      ↓


    Is it whitespace?


      ├── YES → skip → read next character
      │
      └── NO


      ↓


    Is it beginning of identifier?


      ├── YES → consume identifier
      │         ↓
      │      keyword lookup
      │         ↓
      │      return token
      │
      └── NO


      ↓


    Is it beginning of number?


      ├── YES → consume number
      │         ↓
      │      return NUMBER
      │
      └── NO


      ↓


    Is it operator/separator?


      ├── YES → use lookahead if necessary
      │         ↓
      │      return token
      │
      └── NO


      ↓


    Is it comment?


      ├── YES → skip comment
      │         ↓
      │      continue
      │
      └── NO


      ↓


    Report lexical error


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
36. ABSTRACT LEXER PSEUDOCODE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

    function getNextToken():

        while true:

            c = nextCharacter()

            if c is whitespace:
                continue

            if c begins comment:
                skipComment()
                continue

            if c begins identifier:
                lexeme = consumeIdentifier()

                if lexeme is keyword:
                    return KEYWORD(lexeme)
                else:
                    entry = symbolTable.lookupOrInsert(lexeme)
                    return ID(entry)

            if c begins number:
                lexeme = consumeNumber()
                return NUMBER(lexeme)

            if c begins operator:
                token = recognizeOperator()
                return token

            if c is separator:
                return SEPARATOR(c)

            if c is EOF:
                return EOF

            reportLexicalError(c)


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
37. DETERMINISTIC FINITE AUTOMATON INSIDE A LEXER
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

A lexer can be implemented as a collection of DFA-based recognizers.


Example identifier DFA:


                          letter/digit
                       ┌──────────────┐
                       │              │
                       ▼              │
                  ┌─────────┐         │
        letter →  │   ID    │─────────┘
                  └─────────┘
                     ▲
                     │
                  START


More accurately, the first character must satisfy the identifier
starting rule, while subsequent characters may include digits.


The DFA accepts the complete lexeme.


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
38. COMBINING TOKEN AUTOMATA
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

A practical lexer may combine multiple token recognizers into one
large DFA.


Conceptually:


                     ┌── Identifier DFA ──► ID
                     │
                     ├── Number DFA ──────► NUMBER
        START ───────┤
                     ├── Operator DFA ────► OPERATOR
                     │
                     ├── String DFA ──────► STRING
                     │
                     └── Comment DFA ─────► COMMENT


The combined machine recognizes many token classes.


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
39. LEX / FLEX
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

LEX and FLEX are tools for generating lexical analyzers.


LEX is a traditional lexical-analyzer generator.


FLEX means:


        Fast Lexical Analyzer Generator


A lexer generator allows us to specify:


        TOKEN PATTERN → ACTION


Example conceptual rules:


        [0-9]+
            → return NUMBER;


        [a-zA-Z_][a-zA-Z0-9_]*
            → return ID;


        "+"
            → return PLUS;


The tool generates scanner code.


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
40. FLEX ARCHITECTURE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━


        FLEX SPECIFICATION
                │
                ▼
        ┌─────────────────┐
        │      FLEX       │
        │   GENERATOR     │
        └────────┬────────┘
                 │
                 ▼
          GENERATED SCANNER
                 │
                 ▼
             COMPILER


The specification typically contains:


        definitions
        %%

        %%
        user code


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
41. FLEX RULE FORMAT
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

A simplified Flex rule looks like:


        PATTERN        ACTION


Example:


        [0-9]+         { return NUMBER; }


Meaning:


        If one or more digits are found,
        execute the action that returns NUMBER.


Another:


        "+"            { return PLUS; }


Another:


        [ \t\n]+       { /* ignore whitespace */ }


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
42. SIMPLE FLEX EXAMPLE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Conceptual Flex specification:


        %%

        [0-9]+
            { return NUMBER; }

        [a-zA-Z_][a-zA-Z0-9_]*
            { return ID; }

        "+"
            { return PLUS; }

        "="
            { return ASSIGN; }

        [ \t\n]+
            { /* ignore */ }

        .


The final "." rule can be used as a catch-all in many Flex
specifications, often for error handling.


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
43. HOW FLEX WORKS CONCEPTUALLY
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━


        REGULAR EXPRESSIONS
                │
                ▼
        AUTOMATA CONSTRUCTION
                │
                ▼
        DFA / OPTIMIZED SCANNER
                │
                ▼
        GENERATED LEXER
                │
                ▼
        TOKEN STREAM


Therefore:


        FLEX
          ↓
        REGEX
          ↓
        AUTOMATA
          ↓
        SCANNER


This directly connects Chapters 5–8.


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
44. LONGEST MATCH IN FLEX
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Flex generally chooses the rule that matches the longest input.


If two rules match the same longest lexeme, the rule appearing first
has priority.


Example:


        "="
        "=="


For input:


        ==


the longer match:


        ==


wins.


If two rules match exactly the same longest text, earlier rule order
determines the winner.


This is extremely important when designing lexer rules.


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
45. PRACTICAL LEXER — EXAMPLE PROGRAM
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Consider source:


        int sum = a + 25;


The lexer processes:


        i
        n
        t


Recognizes:


        int


Returns:


        <INT, int>


Then:


        sum


Returns:


        <ID, sum>


Then:


        =


Returns:


        <ASSIGN, =>


Then:


        a


Returns:


        <ID, a>


Then:


        +


Returns:


        <PLUS, +>


Then:


        25


Returns:


        <NUMBER, 25>


Then:


        ;


Returns:


        <SEMICOLON, ;>


Final token stream:


        <INT, int>
        <ID, sum>
        <ASSIGN, =>
        <ID, a>
        <PLUS, +>
        <NUMBER, 25>
        <SEMICOLON, ;>


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

47. LEXICAL ANALYZER VS PARSER
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

LEXER:


    Input:
        characters


    Output:
        tokens


    Uses:
        regular expressions
        finite automata


PARSER:


    Input:
        tokens


    Output:
        parse tree / AST


    Uses:
        context-free grammar
        parsing algorithms


Comparison:


        Characters
             │
             ▼
           LEXER
             │
             ▼
           Tokens
             │
             ▼
           PARSER
             │
             ▼
         Parse Tree


Therefore:


        LEXER = lexical structure


        PARSER = syntactic structure


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
48. LEXER AND SYMBOL TABLE — IMPORTANT DISTINCTION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

The lexer recognizes an identifier.


Example:


        total


The lexer knows:


        "total is syntactically an identifier"


But it generally does NOT determine:


        "total is an int variable declared at line 10"


That is mainly the job of later semantic analysis.


The symbol table, however, may be created or updated as identifiers
are encountered, depending on compiler design.


Therefore:


        LEXER
          ↓
        identifies NAME


        SEMANTIC ANALYZER
          ↓
        determines MEANING / TYPE / SCOPE


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
49. LEXICAL ANALYZER PERFORMANCE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Lexical analysis should be fast because it processes essentially every
source character.


Important optimization techniques:


    • Input buffering
    • Two-buffer scheme
    • Sentinels
    • Efficient DFA transition tables
    • Avoid unnecessary copying
    • Efficient symbol-table lookup
    • Longest-match scanning
    • Generated scanners


Goal:


        process source efficiently
        while producing correct tokens.

SCANNER:


    Another name for lexical analyzer.


LEXEME:


    Actual character sequence matched by a token pattern.


TOKEN:


    Category assigned to a lexeme.


PATTERN:


    Rule describing valid lexemes.


LOOKAHEAD:


    Examining future input characters.


RETRACTION:


    Moving the input pointer backward after reading too far.


SENTINEL:


    Special marker indicating buffer/end boundary.


INPUT BUFFER:


    Memory area containing source characters for efficient scanning.


MAXIMAL MUNCH:


    Choose the longest valid token.


SYMBOL TABLE:


    Data structure storing information about program names.

Remember:


    • Lexer works on characters.
    • Parser works on tokens.
    • Regular expressions describe token patterns.
    • DFA/NFA recognize token patterns.
    • Lexer usually uses DFA-style deterministic scanning.
    • Longest valid match is generally selected.
    • Keywords may be handled through a keyword table.
    • Input buffering improves performance.
    • Two-buffer scheme reduces I/O overhead.
    • Sentinel reduces repeated boundary checks.
    • Lookahead resolves ambiguous token prefixes.
    • Lexical errors occur before syntax analysis.
    • Symbol-table references can be included in token attributes.
