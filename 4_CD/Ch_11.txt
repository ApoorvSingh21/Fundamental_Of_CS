1. CHAPTER OVERVIEW
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Top-down parsing is a method of syntax analysis in which the parser
starts from the START SYMBOL of a grammar and tries to generate the
given input string.

Basic idea:

                Grammar
                   │
                   ▼
             Start Symbol
                   │
                   ▼
          Top-Down Parser
                   │
                   ▼
             Input String
                   │
                   ▼
              Parse Tree


Example grammar:

E → E + T | T

Input:

id + id

A top-down parser conceptually starts with:

E

and tries to derive:

E ⇒ T ⇒ id

or, for the complete input:

E ⇒ T + T ⇒ id + id


IMPORTANT:

Top-down parsing constructs the parse tree:

                from ROOT
                   ↓
                to LEAVES

Therefore:

TOP-DOWN = START SYMBOL → INPUT


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
2. WHERE TOP-DOWN PARSING FITS IN A COMPILER
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Compiler pipeline:

Source Program
      │
      ▼
Lexical Analyzer
      │
      ▼
Tokens
      │
      ▼
Syntax Analyzer / Parser
      │
      ├── Top-Down Parser
      │       ├── Recursive Descent
      │       └── Predictive Parser
      │
      └── Bottom-Up Parser
              ├── Shift-Reduce
              └── LR-family
      │
      ▼
Parse Tree / AST
      │
      ▼
Semantic Analysis
      │
      ▼
Intermediate Representation
      │
      ▼
Optimization
      │
      ▼
Code Generation


So:

TOP-DOWN PARSING is a technique used inside the
SYNTAX ANALYSIS phase of a compiler.


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
3. WHAT IS PARSING?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Parsing means checking whether a sequence of tokens can be generated
by a given Context-Free Grammar (CFG).

Example:

Grammar:

E → E + T | T
T → id

Input:

id + id

The parser checks whether:

id + id

belongs to the language generated by the grammar.


Three important inputs:

1. Grammar
2. Token stream
3. Parser


Output:

Usually a parse tree, AST, or syntax structure.


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
4. WHAT DOES "TOP-DOWN" MEAN?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Consider:

S → aA
A → b

Input:

ab

Start:

S

Derivation:

S
↓
aA
↓
ab

The derivation starts from the start symbol and moves toward
the terminals.

Therefore:

S
│
├── a
└── A
    │
    └── b

The parser expands non-terminals until terminals match the input.

This is called:

TOP-DOWN PARSING.


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
5. TOP-DOWN VS BOTTOM-UP PARSING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

TOP-DOWN:

Start Symbol
     ↓
Intermediate symbols
     ↓
Terminals
     ↓
Input

BOTTOM-UP:

Input
     ↓
Reduce substrings
     ↓
Intermediate symbols
     ↓
Start Symbol


Direction:

Top-down:
    Root → Leaves

Bottom-up:
    Leaves → Root


Top-down tries to find:

Leftmost derivation

Bottom-up parsing constructs:

Rightmost derivation in reverse


GATE IMPORTANT:

Top-down parsing is generally associated with
LEFTMOST DERIVATION.


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
6. TYPES OF TOP-DOWN PARSING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Major approaches:

                 TOP-DOWN PARSING
                       │
          ┌────────────┴────────────┐
          │                         │
          ▼                         ▼
   Recursive Descent          Predictive Parsing
          │                         │
          │                   ┌─────┴─────┐
          │                   │           │
          ▼                   ▼           ▼
   With Backtracking      Non-backtracking
                           Predictive Parser
                                 │
                                 ▼
                               LL(1)


Important:

Recursive descent MAY use backtracking.

Predictive parsing is designed to choose the correct production
without backtracking.

LL(1) is a very important predictive parsing technique.


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
7. RECURSIVE DESCENT PARSING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Recursive descent is a top-down parsing technique in which
each non-terminal is usually implemented as a procedure/function.

Example grammar:

S → aA
A → b

We can write conceptually:

parseS():
    match('a')
    parseA()

parseA():
    match('b')


Input:

ab


Execution:

parseS()
   │
   ├── match(a)
   │
   └── parseA()
          │
          └── match(b)


The function corresponding to S calls the function corresponding
to A.


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
8. WHY IS IT CALLED "RECURSIVE"?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Because grammar structures may cause parser functions to call
themselves directly or indirectly.

Example:

S → aS | b

Conceptually:

parseS():
    if input begins with 'a':
        match('a')
        parseS()
    else:
        match('b')


For input:

aaab

Execution:

parseS
  ↓
match a
  ↓
parseS
  ↓
match a
  ↓
parseS
  ↓
match a
  ↓
parseS
  ↓
match b


This recursive behavior gives recursive-descent parsing its name.


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
9. THE BIG PROBLEM: LEFT RECURSION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Consider:

E → E + T | T

This grammar is LEFT RECURSIVE because E appears as the first
symbol on the right-hand side:

E → E + T

If we directly create:

parseE():
    parseE()
    match('+')
    parseT()

then:

parseE()
   ↓
parseE()
   ↓
parseE()
   ↓
parseE()
   ↓
...

The parser enters INFINITE RECURSION.

Therefore:

DIRECT LEFT RECURSION IS NOT SUITABLE FOR
STANDARD RECURSIVE-DESCENT TOP-DOWN PARSING.


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
10. REMOVING LEFT RECURSION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

From Chapter 10:

Original:

E → E + T | T

Remove left recursion:

E  → T E'
E' → + T E' | ε


Now recursive descent can be written conceptually:

parseE():
    parseT()
    parseEPrime()

parseEPrime():
    if next token is '+':
        match('+')
        parseT()
        parseEPrime()
    else:
        return


This avoids infinite recursion.


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
11. RECURSIVE DESCENT WITH BACKTRACKING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Consider:

S → aA | aB
A → c
B → d

Input:

ad

The parser sees:

S → aA
or
S → aB

Both alternatives begin with:

a

The parser cannot immediately determine which production to use
using only the first input symbol.

A parser may try:

S → aA

Then:

a matches

but A expects:

c

Input has:

d

So it fails.

Then it backtracks and tries:

S → aB

which succeeds.


This is:

RECURSIVE DESCENT WITH BACKTRACKING.


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
12. PROBLEMS WITH BACKTRACKING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Backtracking can be expensive.

If many alternatives exist, the parser may repeatedly try
different possibilities.

For example:

S → A | B | C | D

The parser may try:

A → failure
B → failure
C → failure
D → success

For complicated grammars, this can cause substantial
extra work.

Therefore, we prefer:

PREDICTIVE PARSING


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
13. PREDICTIVE PARSING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Predictive parsing is a top-down parsing technique that chooses
the correct production by examining the upcoming input symbols.

The key objective:

NO BACKTRACKING


Example:

S → aA | bB

If next input symbol is:

a

choose:

S → aA

If next input symbol is:

b

choose:

S → bB


The parser predicts which production should be used.


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
14. WHY IS IT CALLED PREDICTIVE?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Because the parser predicts the production to use before
fully expanding the non-terminal.

The prediction is made using:

• Current non-terminal
• Lookahead input token
• FIRST
• FOLLOW
• Parsing table


For LL(1):

L = scan input Left-to-right
L = produce Leftmost derivation
1 = use one lookahead token


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
15. MEANING OF LL(1)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

LL(1) has three components:

First L:

Scan input from:

LEFT → RIGHT


Second L:

Construct a:

LEFTMOST DERIVATION


1:

Use:

ONE LOOKAHEAD SYMBOL


Therefore:

LL(1)

means:

"Scan the input from left to right, construct a leftmost
derivation, using one lookahead token."


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
16. LL(1) PARSER
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

An LL(1) parser:

• Reads input from left to right.
• Produces a leftmost derivation.
• Uses one lookahead token.
• Selects productions without backtracking.
• Uses a parsing table.

Typical architecture:

             Input Buffer
                  │
                  ▼
             Lookahead
                  │
                  ▼
        ┌──────────────────┐
        │   LL(1) Parser   │
        └──────────────────┘
                  │
                  ▼
           Parsing Stack
                  │
                  ▼
             Parse Tree


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
17. LL(1) GRAMMAR REQUIREMENTS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

A grammar suitable for LL(1) parsing must allow the parser to
uniquely choose the production using one lookahead token.

Problems that can prevent LL(1):

1. Left recursion
2. Common prefixes
3. Ambiguity
4. FIRST/FIRST conflicts
5. FIRST/FOLLOW conflicts


Important:

A grammar may be context-free but NOT LL(1).


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
18. FIRST SET
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

FIRST(X) is the set of terminals that can appear as the FIRST
symbol of strings derived from X.

In simple words:

FIRST(X) tells us:

"What can appear first when X is expanded?"


Example:

A → aB | cD

Then:

FIRST(A) = {a, c}


Because A can generate strings beginning with:

a

or:

c


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
19. FIRST OF A TERMINAL
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

For terminal a:

FIRST(a) = {a}


Example:

FIRST(+)
=
{+}


Similarly:

FIRST(id)
=
{id}


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
20. FIRST OF ε
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

ε means:

EMPTY STRING

Therefore:

FIRST(ε) = {ε}


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
21. FIRST OF A NON-TERMINAL
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Example:

A → aB | bC

Therefore:

FIRST(A) = {a,b}


Because every derivation from A starts with either:

a

or:

b


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
22. FIRST WITH ε
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Consider:

A → BC

B → ε
C → c

Because B can disappear:

B ⇒ ε

the first actual terminal may come from C.

Therefore:

FIRST(A) = {c, ε?}

Here B ⇒ ε, but C does not derive ε.

So:

FIRST(A) = {c}

Important rule:

If X₁ can derive ε, then FIRST(X₂) must also be considered.


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
23. GENERAL FIRST RULE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

For:

A → X₁X₂...Xₙ

Calculate:

FIRST(A)

by examining symbols from LEFT to RIGHT.

1. Add FIRST(X₁) except ε.
2. If X₁ can derive ε, examine X₂.
3. Continue.
4. If every Xᵢ can derive ε, add ε.


Example:

A → B C D

If:

FIRST(B) = {b, ε}
FIRST(C) = {c, ε}
FIRST(D) = {d}

Then:

FIRST(A) = {b,c,d}

ε is NOT included because D cannot derive ε.


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
24. FIRST EXAMPLE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Grammar:

E  → T E'
E' → + T E' | ε
T  → id

Calculate FIRST.

FIRST(T):

T → id

Therefore:

FIRST(T) = {id}


FIRST(E'):

E' → +TE' | ε

Therefore:

FIRST(E') = {+, ε}


FIRST(E):

E → TE'

FIRST(T) = {id}

T cannot derive ε.

Therefore:

FIRST(E) = {id}


Final:

FIRST(E)  = {id}
FIRST(E') = {+, ε}
FIRST(T)  = {id}


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
25. FOLLOW SET
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

FOLLOW(A) is the set of terminals that can appear immediately
after non-terminal A in some sentential form.

In simple words:

FOLLOW(A) tells us:

"What can come immediately after A?"


Example:

S → A b

Then:

b ∈ FOLLOW(A)


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
26. FOLLOW OF START SYMBOL
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

The end-of-input marker is usually written as:

$

For the grammar's start symbol S:

$ ∈ FOLLOW(S)


This represents:

"Input has ended."


GATE IMPORTANT:

FOLLOW(Start Symbol) ALWAYS contains $.


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
27. FOLLOW EXAMPLE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Grammar:

S → A b
A → a

Since:

S → A b

b comes immediately after A.

Therefore:

FOLLOW(A) = {b}


For S:

FOLLOW(S) = {$}


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
28. FOLLOW WHEN A IS AT THE END
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Consider:

S → A

Since A appears at the end of the production:

FOLLOW(A) includes FOLLOW(S).

If:

FOLLOW(S) = {$}

then:

FOLLOW(A) = {$}


General rule:

If:

A → αB

then:

FOLLOW(A) ⊆ FOLLOW(B)


More generally, if B is at the end or the symbols after B can
derive ε:

FOLLOW(A) ⊆ FOLLOW(B)


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
29. FOLLOW WITH ANOTHER NON-TERMINAL
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Consider:

S → A B

Suppose:

FIRST(B) = {b,c}

Then:

{b,c} ⊆ FOLLOW(A)

If:

B ⇒* ε

then:

FOLLOW(S) ⊆ FOLLOW(A)


So:

FOLLOW(A)
contains
FIRST(B) − {ε}

and if B can derive ε:

FOLLOW(S) is also propagated to FOLLOW(A).


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
30. FOLLOW EXAMPLE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Grammar:

S → A B
A → a
B → b | ε

Start:

FOLLOW(S) = {$}


For A:

B follows A.

FIRST(B) = {b, ε}

Therefore:

b ∈ FOLLOW(A)

Because B can derive ε:

FOLLOW(S) ⊆ FOLLOW(A)

Therefore:

FOLLOW(A) = {b,$}


For B:

B is at the end.

Therefore:

FOLLOW(S) ⊆ FOLLOW(B)

So:

FOLLOW(B) = {$}


Final:

FOLLOW(S) = {$}
FOLLOW(A) = {b,$}
FOLLOW(B) = {$}


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
31. FIRST vs FOLLOW
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

FIRST:

"What can begin a derivation?"


FOLLOW:

"What can occur immediately after a non-terminal?"


Example:

E' → + T E' | ε

FIRST(E'):

{+, ε}


FOLLOW(E') depends on where E' occurs.


MEMORY TRICK:

FIRST  → FRONT
FOLLOW → AFTER


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
32. WHY FIRST AND FOLLOW ARE IMPORTANT
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

FIRST and FOLLOW are used to construct:

LL(1) PARSING TABLE


They help determine:

"If the parser sees this lookahead token,
which production should it choose?"


Without FIRST/FOLLOW, constructing an LL(1) table is difficult.


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
33. LL(1) PARSING TABLE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

An LL(1) parsing table is usually written as:

              TERMINALS
             a   b   c   $
           ┌───┬───┬───┬───┐
       S   │   │   │   │   │
           ├───┼───┼───┼───┤
NON-   A   │   │   │   │   │
TERMINAL   ├───┼───┼───┼───┤
       B   │   │   │   │   │
           └───┴───┴───┴───┘


Rows:

Non-terminals

Columns:

Terminals + $


Each cell:

M[A,a]

means:

"What production should be used when the top of stack is A
and current input token is a?"


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
34. LL(1) TABLE CONSTRUCTION RULE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

For each production:

A → α


STEP 1:

For every terminal:

a ∈ FIRST(α)

put:

M[A,a] = A → α


STEP 2:

If:

ε ∈ FIRST(α)

then for every:

b ∈ FOLLOW(A)

put:

M[A,b] = A → ε


STEP 3:

If any table cell receives MORE THAN ONE production:

Grammar is NOT LL(1).


This is one of the most important rules in the chapter.


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
35. COMPLETE LL(1) EXAMPLE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Grammar:

E  → T E'
E' → + T E' | ε
T  → id


Terminals:

id, +, $


FIRST:

FIRST(E)  = {id}
FIRST(E') = {+, ε}
FIRST(T)  = {id}


FOLLOW:

FOLLOW(E)  = {$}
FOLLOW(E') = {$}
FOLLOW(T)  = {+, $}


Now construct table.


Production:

E → T E'

FIRST(TE') = {id}

Therefore:

M[E,id] = E → TE'


Production:

E' → +TE'

FIRST(+TE') = {+}

Therefore:

M[E',+] = E' → +TE'


Production:

E' → ε

Because ε is present:

use FOLLOW(E') = {$}

Therefore:

M[E',$] = E' → ε


Production:

T → id

FIRST(id) = {id}

Therefore:

M[T,id] = T → id


Table:

             id          +           $
         ┌──────────┬──────────┬──────────┐
E        │ E→TE'    │          │          │
         ├──────────┼──────────┼──────────┤
E'       │          │ E'→+TE'  │ E'→ε     │
         ├──────────┼──────────┼──────────┤
T        │ T→id     │          │          │
         └──────────┴──────────┴──────────┘


No cell contains multiple productions.

Therefore:

GRAMMAR IS LL(1).


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
36. PREDICTIVE PARSER USING A STACK
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

An LL(1) predictive parser commonly uses:

1. Input buffer
2. Stack
3. Parsing table


Initial stack:

$ E


Input:

id + id $


Conceptually:

Stack                 Input

$ E                   id + id $

Top of stack:

E

Lookahead:

id

Table:

M[E,id]

gives:

E → T E'


Replace E with:

T E'


Continue until:

$ matches $


If successful:

ACCEPT


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
37. PREDICTIVE PARSER ALGORITHM
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

INPUT:

String terminated by $

STACK:

$ StartSymbol


Algorithm:

1. Put $ and start symbol on stack.

2. Let X = top of stack.

3. Let a = current input token.

4. If X is a terminal:
       if X == a:
           pop X
           advance input
       else:
           ERROR

5. If X is a non-terminal:
       consult M[X,a]

       If M[X,a] = X → α:
           pop X
           push α in reverse order

       Else:
           ERROR

6. If stack top and input are both $:
       ACCEPT


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
38. WHY PUSH RHS IN REVERSE?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Suppose production:

E → T E'


Stack is LIFO:

LAST IN → FIRST OUT


We want:

T

to be processed before:

E'


Therefore push:

E'

then:

T


Stack receives:

E' T


so that T is on top.


Memory:

RHS:

T E'

Push:

E' T


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
39. LL(1) PARSER WORKED EXAMPLE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Grammar:

S → aA
A → b

Input:

ab$


Initial:

Stack = $S
Input = ab$


Step 1:

Top = S
Lookahead = a

Table gives:

S → aA


Replace S:

Step 2:

Lookahead = a

Actually, because the stack is LIFO, RHS aA is pushed as:

A then a

So the actual top becomes a.


Stack:

$Aa


Step 3:

Input = a

Match.

Pop a.

Input becomes:

b$


Stack:

Lookahead = b

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
40. RECURSIVE-DESCENT VS PREDICTIVE PARSER
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Recursive Descent:

• Top-down
• Usually one function per non-terminal
• Can use backtracking
• May be simple to implement
• Left recursion causes problems


Predictive Parser:

• Top-down
• No backtracking
• Uses lookahead
• Uses FIRST/FOLLOW
• Often uses parsing table
• LL(1) is a major example


IMPORTANT:

Every predictive parser is top-down.

But a general recursive-descent parser does not necessarily
have to be predictive.


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
41. LEFT FACTORING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Consider:

S → aA | aB


Both alternatives start with:

a


A predictive parser cannot distinguish them using one symbol
immediately.

Apply left factoring:

S → aS'
S' → A | B


Now after matching a, the parser can use additional information
to decide between A and B.


General form:

A → αβ₁ | αβ₂

becomes:

A → αA'
A' → β₁ | β₂


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
42. FIRST/FIRST CONFLICT
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Suppose:

A → α | β

If:

FIRST(α) ∩ FIRST(β) ≠ ∅

then the parser may not know which production to choose.

This is a:

FIRST/FIRST CONFLICT


For LL(1):

FIRST(α) ∩ FIRST(β) must be empty
for alternatives that do not derive ε.


Example:

A → aB | aC

FIRST(aB) = {a}
FIRST(aC) = {a}

Intersection:

{a} ∩ {a} = {a}

Not empty.

Therefore:

NOT LL(1).


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
43. FIRST/FOLLOW CONFLICT
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Consider:

A → α | ε


For LL(1):

FIRST(α) ∩ FOLLOW(A) must be empty.


Why?

If the lookahead belongs to both sets, the parser may be unable
to decide between:

A → α

and:

A → ε


Example:

A → a | ε

If:

FOLLOW(A) = {a}

then:

FIRST(a) = {a}

Intersection:

{a}

Therefore conflict exists.

Grammar is NOT LL(1).


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
44. LL(1) CONDITIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

For:

A → α₁ | α₂ | ... | αₙ

An LL(1) grammar requires that productions can be uniquely selected
using one lookahead token.

For distinct alternatives:

FIRST(αᵢ) ∩ FIRST(αⱼ) = ∅

for i ≠ j, with the necessary ε case handled through FOLLOW.


If:

ε ∈ FIRST(αᵢ)

then:

FIRST(αⱼ) ∩ FOLLOW(A) = ∅

for every j ≠ i.


Very important GATE concept.


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
45. CLASSIC EXPRESSION GRAMMAR
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Original grammar:

E → E + T | T
T → T * F | F
F → (E) | id


Problem:

E and T contain left recursion.

Transform:

E  → T E'
E' → + T E' | ε

T  → F T'
T' → * F T' | ε

F  → (E) | id


This transformed grammar is suitable for predictive parsing
and is the classic LL(1) expression grammar.


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
46. FIRST SETS FOR EXPRESSION GRAMMAR
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Grammar:

E  → TE'
E' → +TE' | ε
T  → FT'
T' → *FT' | ε
F  → (E) | id


FIRST(E):

FIRST(T) = {(, id}

Therefore:

FIRST(E) = {(, id}


FIRST(E'):

{+, ε}


FIRST(T):

{(, id}


FIRST(T'):

{*, ε}


FIRST(F):

{(, id}


Final:

FIRST(E)  = {(, id}
FIRST(E') = {+, ε}
FIRST(T)  = {(, id}
FIRST(T') = {*, ε}
FIRST(F)  = {(, id}


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
47. FOLLOW SETS FOR EXPRESSION GRAMMAR
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Grammar:

E  → TE'
E' → +TE' | ε
T  → FT'
T' → *FT' | ε
F  → (E) | id


Start symbol:

E

Therefore:

$ ∈ FOLLOW(E)


From:

F → (E)

')' follows E.

Therefore:

) ∈ FOLLOW(E)


Thus:

FOLLOW(E) = {), $}


E' appears at end of:

E → T E'

Therefore:

FOLLOW(E) ⊆ FOLLOW(E')

So:

FOLLOW(E') = {), $}


For T:

E → T E'

FIRST(E') = {+, ε}

Therefore:

+ ∈ FOLLOW(T)

Because E' can derive ε:

FOLLOW(E) ⊆ FOLLOW(T)

Thus:

FOLLOW(T) = {+, ), $}


For T':

T → F T'

T' is at the end.

Therefore:

FOLLOW(T) ⊆ FOLLOW(T')

So:

FOLLOW(T') = {+, ), $}


For F:

T → F T'

FIRST(T') = {*, ε}

Therefore:

* ∈ FOLLOW(F)

Because T' can derive ε:

FOLLOW(T) ⊆ FOLLOW(F)

Therefore:

FOLLOW(F) = {*, +, ), $}


Final:

FOLLOW(E)  = {), $}
FOLLOW(E') = {), $}
FOLLOW(T)  = {+, ), $}
FOLLOW(T') = {+, ), $}
FOLLOW(F)  = {*, +, ), $}


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
48. LL(1) TABLE FOR EXPRESSION GRAMMAR
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Grammar:

E  → TE'
E' → +TE' | ε
T  → FT'
T' → *FT' | ε
F  → (E) | id


Table:

              id          +          *          (          )          $
        ┌────────────┬──────────┬──────────┬────────────┬──────────┬──────────┐
E       │ E→TE'      │          │          │ E→TE'      │          │          │
        ├────────────┼──────────┼──────────┼────────────┼──────────┼──────────┤
E'      │            │ E'→+TE'  │          │            │ E'→ε     │ E'→ε     │
        ├────────────┼──────────┼──────────┼────────────┼──────────┼──────────┤
T       │ T→FT'      │          │          │ T→FT'      │          │          │
        ├────────────┼──────────┼──────────┼────────────┼──────────┼──────────┤
T'      │            │ T'→ε     │ T'→*FT'  │            │ T'→ε     │ T'→ε     │
        ├────────────┼──────────┼──────────┼────────────┼──────────┼──────────┤
F       │ F→id       │          │          │ F→(E)      │          │          │
        └────────────┴──────────┴──────────┴────────────┴──────────┴──────────┘


No conflicting entries.

Therefore:

GRAMMAR IS LL(1).


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
49. PARSING "id + id * id"
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Grammar:

E  → TE'
E' → +TE' | ε
T  → FT'
T' → *FT' | ε
F  → (E) | id


Input:

id + id * id $


The parser conceptually derives:

E
⇒ TE'
⇒ FT'E'
⇒ id T'E'
⇒ id E'
⇒ id + T E'
⇒ id + F T' E'
⇒ id + id T' E'
⇒ id + id * F T' E'
⇒ id + id * id T' E'
⇒ id + id * id E'
⇒ id + id * id


This demonstrates operator structure:

id + (id * id)


The grammar gives multiplication higher precedence than addition.


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
50. WHY DOES THIS GRAMMAR GIVE PRECEDENCE?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Structure:

E → T E'

E handles:

+

T handles:

*

Therefore:

E
 └── T
      └── multiplication


Since T is inside E:

multiplication is grouped more tightly than addition.


This is a very important compiler-design connection.


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
51. AMBIGUITY AND LL(1)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

An ambiguous grammar can have more than one parse tree for
the same input.

Example:

E → E + E
  | E * E
  | id


This grammar is ambiguous because precedence/associativity is
not properly encoded.

An ambiguous grammar cannot be LL(1).


Important:

LL(1) grammars are necessarily unambiguous.

But:

Not every unambiguous CFG is LL(1).


Therefore:

LL(1) ⊂ deterministic context-free grammars

and LL(1) is a restricted class of grammars.


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
52. LL(k)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

LL(1) uses:

1 lookahead symbol.


LL(k) uses:

k lookahead symbols.


For example:

LL(2)

means the parser may use up to two input symbols of lookahead.


General:

LL(k)

= Left-to-right scanning
+ Leftmost derivation
+ k lookahead symbols


As k increases, some grammars that are not LL(1) may become
predictable with more lookahead.

However, grammar transformation or another parsing method is
often preferred in practical compiler design.


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
53. LL(1) VS LL(k)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

LL(1):

• One lookahead
• Simple
• Efficient
• Common in teaching and parser construction
• Easy table-based implementation


LL(k):

• k lookahead tokens
• Can distinguish more situations
• Parsing decisions can be more complex
• Larger lookahead increases complexity


Memory:

LL(1) → one symbol
LL(2) → two symbols
LL(k) → k symbols


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
54. ADVANTAGES OF TOP-DOWN PARSING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. Conceptually simple.

2. Easy to understand.

3. Easy to implement for suitable grammars.

4. Recursive descent can be hand-written easily.

5. Predictive parsing avoids backtracking.

6. LL(1) parsing can be efficient.

7. Useful for educational and practical parser construction.

55. LIMITATIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. Left recursion must be removed.

2. Some grammars require left factoring.

3. Not every CFG is LL(1).

4. Backtracking can be expensive.

5. Some grammars are easier to handle with bottom-up LR parsing.

6. LL(1) has limited grammar coverage compared with more powerful
   parsing techniques.

56. TOP-DOWN PARSING ERROR CONDITIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

A parser can detect errors when:

1. Terminal on stack does not match input.

Example:

Stack top = id
Input = +

ERROR


2. Parsing table entry is empty.

Example:

M[A,+] = ERROR


3. Input finishes before stack becomes empty.


4. Stack finishes before input finishes.


At the end:

Stack = $
Input = $

means:

ACCEPT

57. ERROR RECOVERY CONNECTION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Top-down parsers can use error-recovery strategies.

Examples include:

• Panic-mode recovery
• Phrase-level recovery
• Synchronizing tokens

FOLLOW sets are particularly useful in panic-mode recovery.

For example, if:

FOLLOW(A) = {), $}

the parser may use these symbols as synchronization points.

58. RECURSIVE DESCENT VS LL(1) TABLE-DRIVEN PARSER
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Recursive Descent:

Grammar
  ↓
Functions
  ↓
Parser


Example:

parseE()
parseEPrime()
parseT()
parseTPrime()
parseF()


Table-driven LL(1):

Grammar
  ↓
FIRST/FOLLOW
  ↓
Parsing Table
  ↓
Stack + Input
  ↓
Parser


Both can implement top-down parsing.

59. IMPORTANT TERMINOLOGY
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

TERMINAL:

A symbol that appears in the input.

Example:

id, +, *, (, )


NON-TERMINAL:

A grammar variable that can be expanded.

Example:

E, T, F


START SYMBOL:

The symbol from which derivation begins.

Example:

E


LOOKAHEAD:

Upcoming input symbol(s) examined by parser.


LEFTMOST DERIVATION:

Always expand the leftmost non-terminal first.


PREDICTIVE PARSER:

Top-down parser that chooses production using lookahead
without backtracking.


LL(1):

Left-to-right scan + leftmost derivation + one lookahead.

60. HIGH-VALUE GATE FACTS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

FACT 1:

Top-down parsing constructs the parse tree from root toward leaves.


FACT 2:

Top-down parsing is associated with leftmost derivation.


FACT 3:

LL(1) uses one lookahead symbol.


FACT 4:

LL(1) means:

L = Left-to-right input scan
L = Leftmost derivation
1 = one lookahead


FACT 5:

Left recursion causes problems in recursive-descent parsing.


FACT 6:

Left factoring helps when alternatives have common prefixes.


FACT 7:

FIRST determines possible starting terminals.


FACT 8:

FOLLOW determines possible terminals after a non-terminal.


FACT 9:

$ belongs to FOLLOW(Start Symbol).


FACT 10:

If an LL(1) parsing-table cell has multiple productions,
the grammar is not LL(1).


FACT 11:

For A → α | β, conflicting FIRST sets can cause
FIRST/FIRST conflict.


FACT 12:

If A → α | ε, then FIRST(α) must not intersect FOLLOW(A)
for LL(1).


FACT 13:

LL(1) grammar is unambiguous.


FACT 14:

Not every CFG is LL(1).


FACT 15:

Predictive parsing does not require backtracking.

61. GATE TRAPS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

TRAP 1:

"Top-down parsing always uses backtracking."

FALSE.

Predictive top-down parsers do not use backtracking.


TRAP 2:

"Every CFG is LL(1)."

FALSE.


TRAP 3:

"FIRST tells what follows a non-terminal."

FALSE.

FIRST tells what can BEGIN a derived string.


TRAP 4:

"FOLLOW tells what can begin a derivation."

FALSE.

FOLLOW tells what can occur AFTER a non-terminal.


TRAP 5:

"Left factoring removes left recursion."

FALSE.

Left factoring handles COMMON PREFIXES.

Left recursion removal handles:

A → Aα


TRAP 6:

"LL means rightmost derivation."

FALSE.

LL uses LEFTMOST derivation.


TRAP 7:

"LR uses leftmost derivation."

FALSE.

LR parsing corresponds to a rightmost derivation in reverse.


TRAP 8:

"$ belongs to FIRST(start symbol)."

FALSE.

$ belongs to:

FOLLOW(start symbol).

64. INTERVIEW QUESTIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q1. What is top-down parsing?

Answer:

A syntax-analysis technique that starts from the grammar's start
symbol and constructs the parse tree toward the input terminals.


Q2. What is recursive descent parsing?

Answer:

A top-down parsing technique where grammar non-terminals are
implemented as procedures/functions.


Q3. What is predictive parsing?

Answer:

A top-down parsing method that predicts the production to use from
lookahead without backtracking.


Q4. What does LL(1) mean?

Answer:

Left-to-right scanning, leftmost derivation, and one lookahead
symbol.


Q5. Why must left recursion be removed?

Answer:

Because direct left recursion can cause infinite recursion in
recursive-descent top-down parsers.


Q6. Why is left factoring needed?

Answer:

To remove common prefixes so that a predictive parser can choose
a production using available lookahead.


Q7. What is FIRST?

Answer:

The set of terminals that can appear first in strings derived
from a grammar symbol or sequence.


Q8. What is FOLLOW?

Answer:

The set of terminals that can appear immediately after a
non-terminal in a sentential form.


Q9. What is the initial value of FOLLOW(Start)?

Answer:

{$}


Q10. What happens if an LL(1) parsing-table cell contains
two productions?

Answer:

The grammar is not LL(1).

67. CHAPTER 11 — MASTER SUMMARY
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Top-down parsing starts with the start symbol and attempts to
generate the input.

The two major ideas are:

1. Recursive descent
2. Predictive parsing


Recursive descent:

• Function-based
• One function per non-terminal
• Can use backtracking
• Left recursion causes infinite recursion


Predictive parsing:

• Uses lookahead
• Avoids backtracking
• Uses grammar information to select productions


LL(1):

L → Left-to-right
L → Leftmost derivation
1 → One lookahead


FIRST:

Possible beginning terminals.


FOLLOW:

Possible terminals after a non-terminal.


LL(1) table:

M[A,a]

Rows = non-terminals

Columns = terminals + $


For:

A → α

put production under:

FIRST(α)


If:

ε ∈ FIRST(α)

put A → ε under:

FOLLOW(A)


Conflict:

More than one production in a table cell

⇒ Grammar is NOT LL(1).


Main grammar transformations:

LEFT RECURSION REMOVAL
        +
LEFT FACTORING
        ↓
FIRST/FOLLOW
        ↓
LL(1) TABLE
        ↓
PREDICTIVE PARSER
