1. INTRODUCTION — STRUCTURE OF A COMPILER
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

A compiler is not a single operation.

It is a collection of logically organized phases that transform:

        SOURCE PROGRAM
              ↓
        Intermediate forms
              ↓
        TARGET PROGRAM

The major structure is:

    SOURCE PROGRAM
          │
          ▼
    ┌──────────────────┐
    │ Lexical Analysis │
    └────────┬─────────┘
             ↓
          TOKENS
             │
             ▼
    ┌──────────────────┐
    │ Syntax Analysis  │
    └────────┬─────────┘
             ↓
       PARSE TREE / AST
             │
             ▼
    ┌──────────────────┐
    │Semantic Analysis │
    └────────┬─────────┘
             ↓
       CHECKED PROGRAM
             │
             ▼
    ┌──────────────────┐
    │ Intermediate     │
    │ Code Generation  │
    └────────┬─────────┘
             ↓
             IR
             │
             ▼
    ┌──────────────────┐
    │ Code Optimization│
    └────────┬─────────┘
             ↓
        OPTIMIZED IR
             │
             ▼
    ┌──────────────────┐
    │ Code Generation  │
    └────────┬─────────┘
             ↓
        TARGET CODE


Two important supporting structures interact with these phases:

    SYMBOL TABLE
         ↕
    Multiple compiler phases

    ERROR HANDLING
         ↕
    Multiple compiler phases

2. LEXICAL ANALYSIS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

DEFINITION:
Lexical analysis is the compiler phase that reads the source
program as a sequence of characters and groups those characters
into meaningful units called TOKENS.

The component performing this work is called the:

    LEXICAL ANALYZER
    or
    SCANNER


Basic flow:

    Source Characters
          │
          ▼
    ┌──────────────────┐
    │ Lexical Analyzer │
    └────────┬─────────┘
             ↓
           TOKENS


Example:

    int sum = a + 10;

The lexical analyzer identifies approximately:

    int     → keyword
    sum     → identifier
    =       → operator
    a       → identifier
    +       → operator
    10      → integer literal
    ;       → separator


Character stream:

    i n t _ s u m _ = _ a _ + _ 1 0 _ ;

              ↓

Token stream:

    int | sum | = | a | + | 10 | ;


IMPORTANT TERMS:

    Lexeme
        Actual sequence of characters in the source.

    Token
        Category assigned to a lexeme.

    Pattern
        Rule describing the form of lexemes belonging to a token.


Example:

    age

Lexeme:
    "age"

Token:
    IDENTIFIER

Pattern:
    letter(letter|digit)*

3. SYNTAX ANALYSIS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

DEFINITION:
Syntax analysis checks whether the token sequence follows the
grammar of the programming language.

The component performing this operation is called:

    PARSER
    or
    SYNTAX ANALYZER


Flow:

    Tokens
      │
      ▼
    ┌─────────────────┐
    │ Syntax Analyzer │
    │    / Parser     │
    └────────┬────────┘
             ↓
      Parse Tree / AST


Example:

    a + b * c

The parser determines its grammatical structure.

Because multiplication has higher precedence, the structure is:

             +
            / \
           a   *
              / \
             b   c


The parser may detect an error such as:

    a + * b

because the token sequence does not conform to the grammar.


MAIN PURPOSES:

    • Check grammatical structure
    • Construct a parse tree
    • Construct or help construct an AST
    • Detect syntax errors

    Ambiguity
    FIRST
    FOLLOW

    Shift-reduce parsing
    LR(0)
    SLR
    CLR/LR(1)
    LALR

4. SEMANTIC ANALYSIS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

DEFINITION:
Semantic analysis checks whether a syntactically valid program
satisfies the language's semantic rules.

Important distinction:

    Syntax
       =
    Is the structure grammatically correct?

    Semantics
       =
    Does the program make sense according to language rules?


Example:

    int x;
    x = "hello";


The statement may have a grammatically valid structure, but assigning
a string to an integer variable may violate type rules.

Semantic analysis may check:

    • Type compatibility
    • Type checking
    • Variable declarations
    • Scope
    • Identifier usage
    • Other language-specific semantic rules


Flow:

    Parse Tree / AST
            │
            ▼
    ┌──────────────────┐
    │Semantic Analyzer  │
    └────────┬─────────┘
             ↓
       Checked AST / IR


Example:

    int a;
    float b;

    b = a + 2.5;


Semantic analyzer determines the types involved and checks whether
the expression and assignment are valid under the language's rules.

5. INTERMEDIATE CODE GENERATION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

DEFINITION:
Intermediate code generation converts the analyzed source program
into an intermediate representation (IR).

Why use IR?

Because directly translating every source-language construct to
every possible target machine can make compiler design complicated.

Instead:

    Source Language
          ↓
       Front End
          ↓
          IR
          ↓
       Back End
          ↓
      Target Machine


This allows the compiler to separate source-language processing
from target-machine processing.

Example:

    Source:

        a = b + c * d;


Possible three-address code:

        t1 = c * d
        t2 = b + t1
        a  = t2


Diagram:

             a = b + c*d
                    │
                    ▼
               IR Generator
                    │
                    ▼
              t1 = c*d
              t2 = b+t1
              a  = t2


IR will be studied in detail in:

    Chapter 19 — Intermediate Code / IR
    Chapter 20 — Three-Address Code
    Chapter 21 — Boolean Expressions & Control Flow

6. CODE OPTIMIZATION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

DEFINITION:
Code optimization transforms an intermediate representation into
a better representation while preserving the program's intended
behavior.

"Better" can mean:

    • Faster execution
    • Smaller code
    • Lower resource usage
    • Better use of machine resources


Example 1 — Constant Folding:

    x = 10 * 5;

can become:

    x = 50;


Example 2 — Algebraic Simplification:

    x = y + 0;

can become:

    x = y;


Example 3 — Dead Code:

    x = 10;
    x = 20;

If the first assignment is never used, an optimizer may be able
to eliminate it, depending on the surrounding program.


Basic flow:

    IR
     │
     ▼
    ┌──────────────────┐
    │    Optimizer     │
    └────────┬─────────┘
             ↓
       Optimized IR


Important:
Optimization must preserve the observable behavior required by
the language/program.

7. CODE GENERATION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

DEFINITION:
Code generation converts the intermediate representation into
target-machine code.

Flow:

    Optimized IR
         │
         ▼
    ┌─────────────────┐
    │ Code Generator  │
    └────────┬────────┘
             ↓
       Target Code


Example IR:

    t1 = b + c
    a = t1


A target machine might use instructions conceptually similar to:

    LOAD R1, b
    ADD  R1, c
    STORE a, R1


The exact instructions depend on the target architecture.


CODE GENERATION CONSIDERS:

    • Instruction selection
    • Register allocation
    • Register assignment
    • Addressing modes
    • Instruction ordering
    • Target-machine constraints

8. SYMBOL TABLE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

DEFINITION:
A symbol table is a data structure used by the compiler to store
information about identifiers appearing in the source program.

Typical entries may contain:

    • Name
    • Type
    • Scope
    • Storage information
    • Other language-specific attributes


Example program:

    int count;
    float total;


Symbol table:

    ┌──────────┬────────┬─────────┐
    │ Name     │ Type   │ Scope   │
    ├──────────┼────────┼─────────┤
    │ count    │ int    │ global  │
    │ total    │ float  │ global  │
    └──────────┴────────┴─────────┘


OPERATIONS:

    INSERT
       ↓
    Add identifier information

    LOOKUP
       ↓
    Find identifier information

    UPDATE
       ↓
    Modify relevant information

Symbol-table concept:

               Identifier
                    │
                    ▼
             ┌─────────────┐
             │Symbol Table │
             └──────┬──────┘
                    │
                    ▼
        Name / Type / Scope / etc.


A hash table is commonly useful for efficient lookup.

Symbol tables become especially important in:

    • Lexical analysis
    • Semantic analysis
    • Code generation
    • Scope management


Detailed study:
    Chapter 16 — Symbol Tables

9. ERROR HANDLING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

DEFINITION:
Error handling is the mechanism by which a compiler detects,
reports and, where possible, recovers from errors in the source
program.

Errors can occur at different stages.

--------------------------------------------------------------
9.1 LEXICAL ERROR
--------------------------------------------------------------

Occurs during lexical analysis.

Example:

    int x = 10 @ 20;

If '@' is not valid in that context according to the language,
the scanner may report a lexical error.

--------------------------------------------------------------
9.2 SYNTAX ERROR
--------------------------------------------------------------

Occurs when tokens do not follow the grammar.

Example:

    int x = ;

The structure is incomplete.

--------------------------------------------------------------
9.3 SEMANTIC ERROR
--------------------------------------------------------------

Occurs when the program violates semantic rules.

Example:

    int x;
    x = "hello";


--------------------------------------------------------------
9.4 RUNTIME ERROR
--------------------------------------------------------------

Occurs during program execution.

Examples can include:

    • Division by zero
    • Invalid memory access
    • Other execution-time failures

Not every runtime error is detectable by the compiler.


Error handling flow:

        Source
          │
          ▼
       Compiler
          │
      ┌───┴────┐
      │ Errors │
      └───┬────┘
          ↓
    Report / Recover

    Chapter 39 — Error Handling
    Chapter 40 — Error Recovery

10. INTERACTION BETWEEN COMPILER PHASES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

The phases are not isolated independent programs.

They communicate with each other.

Overall:

    SOURCE PROGRAM
          │
          ▼
       LEXER
          │
          │ Tokens
          ▼
       PARSER
          │
          │ Parse Tree / AST
          ▼
      SEMANTIC
       ANALYZER
          │
          │ Checked representation
          ▼
       IR GENERATOR
          │
          │ IR
          ▼
       OPTIMIZER
          │
          │ Optimized IR
          ▼
     CODE GENERATOR
          │
          ▼
      TARGET CODE


Supporting all these stages:

             ┌─────────────────┐
             │   SYMBOL TABLE  │
             └───────┬─────────┘
                     ↕
        ┌────────────┼────────────┐
        ↓            ↓            ↓
      Lexer        Parser      Semantic
                                   ↓
                                Code Gen.


And:

             ┌─────────────────┐
             │ ERROR HANDLING  │
             └───────┬─────────┘
                     ↕
        ┌────────────┼────────────┐
        ↓            ↓            ↓
      Lexer        Parser      Semantic
                     ↓            ↓
                  Optimizer   Code Gen.

11. EXAMPLE — HOW ALL PHASES WORK TOGETHER
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Consider:

    int x;
    int y;
    x = y + 10;


PHASE 1 — LEXICAL ANALYSIS
──────────────────────────────────────────────────────────────

Input characters:

    int x; int y; x = y + 10;

Output tokens:

    int
    x
    ;
    int
    y
    ;
    x
    =
    y
    +
    10
    ;


Symbol table information begins to be established for identifiers.


PHASE 2 — SYNTAX ANALYSIS
──────────────────────────────────────────────────────────────

The parser determines grammatical relationships.

For:

    x = y + 10

conceptual tree:

             =
            / \
           x   +
              / \
             y  10


PHASE 3 — SEMANTIC ANALYSIS
──────────────────────────────────────────────────────────────

Compiler checks:

    Is x declared?
    Is y declared?
    Are their types compatible?
    Is the assignment valid?

Suppose:

    x → int
    y → int

Then:

    y + 10 → int

and:

    x = int-expression

is valid.


PHASE 4 — IR GENERATION
──────────────────────────────────────────────────────────────

Possible TAC:

    t1 = y + 10
    x = t1


PHASE 5 — OPTIMIZATION
──────────────────────────────────────────────────────────────

If useful, the optimizer may transform the IR.

In this example, there may be little or nothing to optimize.


PHASE 6 — CODE GENERATION
──────────────────────────────────────────────────────────────

Conceptual target instructions:

    LOAD R1, y
    ADD  R1, 10
    STORE x, R1


COMPLETE:

    SOURCE
      │
      ▼
    LEXICAL
      │
      ▼
    TOKENS
      │
      ▼
    SYNTAX
      │
      ▼
    TREE / AST
      │
      ▼
    SEMANTIC
      │
      ▼
    CHECKED FORM
      │
      ▼
    IR
      │
      ▼
    OPTIMIZATION
      │
      ▼
    OPTIMIZED IR
      │
      ▼
    CODE GENERATION
      │
      ▼
    TARGET CODE

12. FRONT END, MIDDLE END AND BACK END
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Modern compiler architecture is often described using three
logical regions.

                    COMPILER
                       │
        ┌──────────────┼──────────────┐
        ↓              ↓              ↓
    FRONT END       MIDDLE END      BACK END
        │              │              │
        ↓              ↓              ↓
     Analysis      Optimization    Target Code
        │              │              │
        └───────→      IR      ←──────┘


FRONT END:

    • Lexical analysis
    • Syntax analysis
    • Semantic analysis
    • IR generation

MIDDLE END:

    • IR-level analysis
    • Machine-independent optimization
    • Data-flow analysis
    • Other IR transformations

BACK END:

    • Target-dependent optimization
    • Instruction selection
    • Register allocation
    • Code generation


Important:
The exact division can vary between compiler architectures.

13. PHASE vs PASS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

This is a very important exam/interview distinction.

PHASE:
A logical activity performed by the compiler.

Examples:

    Lexical analysis
    Syntax analysis
    Semantic analysis
    Optimization


PASS:
A complete traversal/processing stage over source or an intermediate
representation.

A compiler may implement several logical phases in one pass, or
one logical activity may involve multiple passes.


Example:

    Logical phases:

    Lexical
       ↓
    Syntax
       ↓
    Semantic
       ↓
    Optimization
       ↓
    Code Generation


Implementation could organize these activities into a different
number of actual passes.

Therefore:

    PHASE ≠ PASS

14. WHY COMPILER PHASES ARE SEPARATED
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Separation provides:

    1. Modularity
       Each component has a specific responsibility.

    2. Easier development
       Individual components can be designed separately.

    3. Easier debugging
       Errors can be isolated to a stage.

    4. Reusability
       Front ends and back ends can sometimes be reused.

    5. Portability
       A common IR can help support multiple target machines.

    6. Optimization
       Dedicated optimization stages can improve generated code.

Architecture idea:

    Language A ──┐
                 │
    Language B ──┼──→ Common IR ──→ Target A
                 │
    Language C ──┘              └──→ Target B


This separation is one of the most important ideas in compiler
architecture.

19. INTERVIEW RAPID-FIRE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q1. What is lexical analysis?
→ It converts source characters into tokens.

Q2. What does a parser do?
→ It checks token structure according to grammar and constructs a
  parse structure.

Q3. What does semantic analysis do?
→ It checks semantic rules such as types, declarations and scope.

Q4. Why do we need IR?
→ It separates source-language analysis from target-machine code
  generation and provides a useful form for optimization.

Q5. What is optimization?
→ Transformation of code into a better form while preserving
  required program behavior.

Q6. What does the symbol table store?
→ Information about identifiers and their attributes.

Q7. What is the front end?
→ The source-oriented analysis portion of the compiler.

Q8. What is the back end?
→ The target-oriented portion that transforms IR toward target code.

Q9. What is the middle end?
→ The part focused largely on IR analysis and optimization.

Q10. Are compiler phases and passes the same?
→ No. Phases are logical activities; passes are implementation
   processing stages/traversals.
