1. WHAT ARE ADVANCED LANGUAGE FEATURES?
══════════════════════════════════════════════════════════════════════════════

Modern programming languages provide features that are more
powerful than simple:

    variables
    loops
    if/else
    functions
    arrays

Examples:

    • Generics
    • Lambda expressions
    • Closures
    • Object-oriented programming
    • Inheritance
    • Polymorphism
    • Interfaces
    • Higher-order functions
    • Functional programming
    • Exceptions
    • Dynamic typing
    • Reflection
    • Coroutines
    • Pattern matching

These features are convenient for programmers, but they make
compiler design more complicated.

The compiler must translate high-level language concepts into
lower-level operations that the machine/runtime can execute.

2. BASIC IDEA — HIGH LEVEL → LOW LEVEL
══════════════════════════════════════════════════════════════════════════════

Programmer writes:

    list.map(x -> x * 2)

This looks simple.

But the compiler/runtime may need to deal with:

    • Lambda creation
    • Function objects
    • Captured variables
    • Function calls
    • Type checking
    • Memory allocation
    • Dispatch
    • Optimization

Therefore:

    High-level language feature
              ↓
        Compiler analysis
              ↓
        Intermediate form
              ↓
        Lowering
              ↓
        Runtime operations
              ↓
        Machine code

3. GENERIC PROGRAMMING
══════════════════════════════════════════════════════════════════════════════

Generic programming allows code to work with different types
while maintaining type safety.

Example concept:

    function identity<T>(T x) {
        return x;
    }

Here:

    T = type parameter

The same function can conceptually work with:

    identity<int>(10)

and:

    identity<string>("Hello")

Instead of writing:

    identityInt()
    identityString()
    identityFloat()

we can write one generic function.


══════════════════════════════════════════════════════════════════════════════
4. TYPE PARAMETER
══════════════════════════════════════════════════════════════════════════════

A type parameter is a placeholder for a type.

Example:

    List<T>

Here:

    T = type parameter

Possible instantiations:

    List<Integer>
    List<String>
    List<Float>

The compiler must determine:

    What is T?

and verify that operations involving T are valid.


══════════════════════════════════════════════════════════════════════════════
5. WHY GENERICS ARE IMPORTANT FOR COMPILERS
══════════════════════════════════════════════════════════════════════════════

Consider:

    function max<T>(T a, T b)

The compiler must understand:

    • What type is T?
    • Are a and b compatible?
    • Can a and b be compared?
    • What is the return type?
    • What code should eventually be generated?

Generic type checking therefore interacts with:

    • Symbol tables
    • Type systems
    • Semantic analysis
    • IR generation
    • Code generation


══════════════════════════════════════════════════════════════════════════════
6. TWO IMPORTANT GENERIC IMPLEMENTATION STRATEGIES
══════════════════════════════════════════════════════════════════════════════

Two major approaches are:

    1. Type erasure
    2. Specialization / monomorphization

──────────────────────────────────────────────────────────────────────────────
TYPE ERASURE
──────────────────────────────────────────────────────────────────────────────

Generic type information may be removed or represented in a
common runtime form.

Conceptually:

    List<String>
    List<Integer>
          │
          ▼
      Common representation

Advantage:

    Potentially less generated code.

Disadvantage:

    Some type-specific information may not be available at runtime.

──────────────────────────────────────────────────────────────────────────────
SPECIALIZATION
──────────────────────────────────────────────────────────────────────────────

The compiler generates specialized versions for particular types.

Example:

    max<T>()

may produce:

    max_int()
    max_float()
    max_string()

Conceptually:

    Generic function
          │
       ┌──┼───┐
       ▼  ▼   ▼
      int float string
      version version version

Advantage:

    Can enable type-specific optimization.

Disadvantage:

    May increase generated code size.


══════════════════════════════════════════════════════════════════════════════
7. TYPE ERASURE vs SPECIALIZATION
══════════════════════════════════════════════════════════════════════════════

    TYPE ERASURE
    ─────────────

    Generic code
         ↓
    Common representation
         ↓
    Runtime execution

    SPECIALIZATION
    ───────────────

    Generic code
         ↓
    Compile-time specialization
       /      |       \
     int    float    string
       ↓      ↓        ↓
     code   code      code

Remember:

    Erasure → reduce/remove some generic type information.

    Specialization → generate type-specific implementations.

8. LAMBDA EXPRESSIONS
══════════════════════════════════════════════════════════════════════════════

A lambda expression is an anonymous function.

Example:

    x -> x * 2

It has:

    • No traditional function name
    • Parameters
    • Function body

Equivalent conceptual function:

    function multiplyByTwo(x) {
        return x * 2;
    }

Lambda:

    x -> x * 2

9. WHY LAMBDAS MATTER TO COMPILERS
══════════════════════════════════════════════════════════════════════════════

The compiler must transform:

    x -> x * 2

into something executable.

Possible implementation:

    Lambda expression
          ↓
    Function representation
          ↓
    IR
          ↓
    Machine code

The language may represent the lambda as:

    • A function
    • A closure object
    • A method/function pointer
    • An internal compiler-generated function

10. CLOSURE
══════════════════════════════════════════════════════════════════════════════

A closure is a function together with the environment
needed to access variables captured from its surrounding scope.

Example:

    function outer() {
        int x = 10;

        function inner() {
            return x + 5;
        }

        return inner;
    }

The inner function uses:

    x

even though x was declared in outer().

The function:

    inner

and its captured environment together form a closure.


══════════════════════════════════════════════════════════════════════════════
11. CLOSURE — REAL-WORLD ANALOGY
══════════════════════════════════════════════════════════════════════════════

Imagine a worker carrying a backpack.

Worker:

    Function

Backpack:

    Captured variables

Together:

    Worker + Backpack = Closure

Example:

    x = 10

    function() {
        return x + 5;
    }

The function carries access to x.

This is why closure implementation often requires
environment management.


══════════════════════════════════════════════════════════════════════════════
12. CAPTURED VARIABLES
══════════════════════════════════════════════════════════════════════════════

Consider:

    function createCounter() {
        int count = 0;

        return function() {
            count++;
            return count;
        };
    }

The inner function captures:

    count

Normally, local variables are associated with an activation record.

But here:

    createCounter()
         ↓
    returns inner function
         ↓
    inner function still needs count

Therefore, the compiler/runtime may need to move the captured
variable into a heap-allocated environment or another structure
whose lifetime extends beyond the original call.


══════════════════════════════════════════════════════════════════════════════
13. CLOSURE IMPLEMENTATION
══════════════════════════════════════════════════════════════════════════════

A conceptual closure can contain:

    ┌─────────────────────────┐
    │ Closure                 │
    ├─────────────────────────┤
    │ Function code pointer   │
    │ Environment pointer     │
    └────────────┬────────────┘
                 │
                 ▼
        ┌───────────────────┐
        │ Environment       │
        ├───────────────────┤
        │ captured x        │
        │ captured y        │
        │ ...               │
        └───────────────────┘

Thus:

    Closure
       =
    Code + Environment


══════════════════════════════════════════════════════════════════════════════
14. LEXICAL SCOPE AND CLOSURES
══════════════════════════════════════════════════════════════════════════════

Lexical scope means that the meaning of a variable is determined
by where it appears in the source program.

Example:

    function outer() {
        x = 10;

        function inner() {
            return x;
        }
    }

The inner function can access x because of lexical nesting.

Closures preserve this relationship even when the function
is used later.


══════════════════════════════════════════════════════════════════════════════
15. CLOSURE AND HEAP ALLOCATION
══════════════════════════════════════════════════════════════════════════════

Suppose:

    function outer() {
        x = 10;

        return function() {
            return x;
        };
    }

If outer() returns, its normal stack frame may disappear.

But the returned function still needs x.

Therefore, a compiler/runtime may use:

    Heap environment
          ↓
    captured x

This connects Chapter 37 with:

    Chapter 22 → Runtime storage
    Chapter 23 → Activation records
    Chapter 25 → Recursion and scope
    Chapter 35 → Garbage collection

If the closure becomes unreachable, its environment can
eventually become garbage in a garbage-collected system.

══════════════════════════════════════════════════════════════════════════════

Inheritance allows one class to derive from another.

Example:

    Animal
       │
       ▼
      Dog

Dog inherits properties/methods from Animal.

    • Method lookup

══════════════════════════════════════════════════════════════════════════════
19. POLYMORPHISM
══════════════════════════════════════════════════════════════════════════════

Polymorphism means that the same interface or operation
can behave differently depending on the actual object/type.

Example:

    Animal a = new Dog();

    a.speak();

Although:

    static type of a = Animal

the actual object is:

    Dog

Therefore:

    Dog.speak()

may execute.

This is an important compiler/runtime problem.


══════════════════════════════════════════════════════════════════════════════
20. STATIC DISPATCH vs DYNAMIC DISPATCH
══════════════════════════════════════════════════════════════════════════════

STATIC DISPATCH:

    Target method can be determined at compile time.

Example:

    direct function call

Conceptually:

    call function_A

DYNAMIC DISPATCH:

    Target method depends on runtime object/type.

Conceptually:

    object.method()
          ↓
    determine actual method
          ↓
    call method


══════════════════════════════════════════════════════════════════════════════
21. VIRTUAL METHODS
══════════════════════════════════════════════════════════════════════════════

A virtual method can be overridden by subclasses and selected
dynamically.

A common implementation technique uses a:

        VTABLE

VTABLE = virtual method table.

Conceptually:

    Class Dog
        ↓
    VTable
    ┌─────────────────┐
    │ speak → Dog.speak│
    │ run   → Dog.run  │
    └─────────────────┘

Another class:

    Class Cat
        ↓
    VTable
    ┌─────────────────┐
    │ speak → Cat.speak│
    │ run   → Cat.run  │
    └─────────────────┘


══════════════════════════════════════════════════════════════════════════════
22. VTABLE DISPATCH
══════════════════════════════════════════════════════════════════════════════

Conceptually:

    object
      │
      ▼
    vtable pointer
      │
      ▼
    method entry
      │
      ▼
    actual method


For:

    animal.speak()

the runtime may perform:

    animal
      ↓
    vtable
      ↓
    speak entry
      ↓
    Dog.speak()


The exact implementation depends on language/runtime/compiler.

23. WHY DYNAMIC DISPATCH AFFECTS OPTIMIZATION
══════════════════════════════════════════════════════════════════════════════

Dynamic dispatch can make optimization harder.

Compiler may initially see:

    obj.method()

Possible targets:

    method_A
    method_B
    method_C

But if runtime information shows:

    99% of calls → method_A

a JIT compiler may optimize around that behavior.

This connects:

    Dynamic dispatch
          ↓
    Runtime profiling
          ↓
    JIT optimization
          ↓
    Speculative optimization

Functional programming treats functions as important values.

Important concepts:

    • First-class functions

    • Lambda expressions

25. HIGHER-ORDER FUNCTION
══════════════════════════════════════════════════════════════════════════════

A higher-order function is a function that:

    • takes another function as an argument
      OR
    • returns a function

Example:

    apply(f, x)

where:

    f = function

Conceptually:

    apply(double, 5)

If:

    double(x) = x * 2

then:

    apply(double, 5) = 10

26. MAP / FILTER / REDUCE
══════════════════════════════════════════════════════════════════════════════

Modern languages often provide:

    map
    filter
    reduce

Example:

    numbers = [1,2,3,4]

    map(x -> x*2)

Conceptually:

    [1,2,3,4]
         ↓
       map
         ↓
    [2,4,6,8]

Compiler may need to represent:

    • Function value
    • Lambda
    • Call
    • Collection operations

Optimizing compilers may sometimes eliminate abstraction overhead.

27. FUNCTION POINTERS
══════════════════════════════════════════════════════════════════════════════

A function pointer stores the address/reference of executable code.

Conceptually:

    function f()
       ↓
    code address

Then:

    p = address of f

    p()

The compiler must generate an indirect call.

Conceptually:

    load function address
          ↓
    indirect call


Dynamic dispatch and higher-order functions can similarly
require indirect calls.

28. EXCEPTION HANDLING
══════════════════════════════════════════════════════════════════════════════

Exception handling allows a program to handle abnormal conditions.

Example:

    try {
        riskyOperation();
    }
    catch (Exception e) {
        handle(e);
    }

Compiler/runtime must support:

    • Detecting exceptions
    • Throwing exceptions
    • Finding handlers
    • Unwinding stack frames
    • Transferring control
    • Cleaning resources


══════════════════════════════════════════════════════════════════════════════
29. THROWING AN EXCEPTION
══════════════════════════════════════════════════════════════════════════════

Conceptually:

    throw exception

causes control flow to change.

Instead of:

    normal next instruction

execution may become:

    throw
      ↓
    find handler
      ↓
    unwind stack if necessary
      ↓
    execute handler


══════════════════════════════════════════════════════════════════════════════
30. STACK UNWINDING
══════════════════════════════════════════════════════════════════════════════

Suppose:

    main()
      ↓
    A()
      ↓
    B()
      ↓
    C()
      ↓
    throw exception

If C has no handler:

    C frame
      ↓
    unwind
      ↓
    B frame
      ↓
    unwind
      ↓
    A frame
      ↓
    find suitable handler

This is called:

        Stack unwinding

Runtime support is often required.

33. DYNAMIC TYPING
══════════════════════════════════════════════════════════════════════════════

In a statically typed language:

    int x = 10;

The compiler knows the type of x.

In a dynamically typed language:

    x = 10

The runtime type of x can change.

Therefore, compiler/runtime may need:

    • Runtime type information
    • Dynamic dispatch
    • Type checks
    • Generic operations
    • Runtime object representation

34. DYNAMIC TYPE CHECKING
══════════════════════════════════════════════════════════════════════════════

Consider:

    x + y

In a dynamically typed language, x and y may be:

    integers
    floating-point values
    strings
    user-defined objects

Runtime may need to determine:

    What are the types?

Then:

    integer + integer
        ↓
    numeric addition

    string + string
        ↓

41. ADVANCED FEATURES AND IR

    • Inlining

43. DEVIRTUALIZATION
══════════════════════════════════════════════════════════════════════════════

Suppose:

    obj.method()

normally requires dynamic dispatch.

If the compiler can prove:

    obj is always class Dog

then it may transform:

    dynamic call

into:

    direct call to Dog.method

This is called:

        Devirtualization

Benefits:

    • Faster calls
    • Enables inlining
    • Enables further optimization


══════════════════════════════════════════════════════════════════════════════
44. ESCAPE ANALYSIS
══════════════════════════════════════════════════════════════════════════════

Escape analysis determines whether an object or value
escapes a particular scope.

Example:

    function f() {
        object x = new Object();
        use(x);
    }

If x never escapes f(), compiler may have opportunities
to optimize its allocation.

Possible result:

    Heap allocation
         ↓
    eliminated or transformed

This can reduce:

    • Allocation cost
    • Garbage collection pressure

45. PROFILE-GUIDED OPTIMIZATION
══════════════════════════════════════════════════════════════════════════════

PGO = Profile-Guided Optimization.

The compiler uses information about actual program execution.

Process:

    Program
      ↓
    Run / collect profile
      ↓
    Runtime behavior information
      ↓
    Compiler optimization
      ↓
    Better code

    • Frequently executed functions
    • Branch probabilities

    • Hot loops

46. ADVANCED LANGUAGE FEATURE — COMPLETE EXAMPLE
══════════════════════════════════════════════════════════════════════════════

Consider:

    function makeMultiplier(x) {
        return function(y) {
            return x * y;
        };
    }

    double = makeMultiplier(2);

    result = double(5);


Step 1:
    Compiler parses nested function.

Step 2:
    Semantic analysis identifies:

        y → local to inner function
        x → captured from outer function

Step 3:
    Compiler creates closure representation.

Conceptually:

    closure:
        code = inner_function
        environment:
            x = 2

Step 4:
    Calling:

        double(5)

causes:

        closure
          ↓
        code + environment
          ↓
        x = 2
        y = 5
          ↓
        2 * 5
          ↓
        10

50. STATIC vs DYNAMIC LANGUAGE — COMPILER VIEW
══════════════════════════════════════════════════════════════════════════════

STATICALLY TYPED:

    Type information known largely at compile time.

    Benefits:
        • Early error detection
        • More optimization opportunities
        • Potentially efficient generated code

DYNAMICALLY TYPED:

    More type decisions happen at runtime.

    Benefits:
        • Flexibility
        • Dynamic behavior

    Costs:
        • Runtime checks
        • More complex runtime
        • Potential optimization challenges

Modern JITs can reduce some dynamic-language overhead.

55. GATE TRAPS
══════════════════════════════════════════════════════════════════════════════

TRAP 1:

    "A lambda is always a closure."

    NOT NECESSARILY.

    A lambda becomes a closure when it needs to capture
    surrounding environment/state.

TRAP 2:

    "Closures contain only function code."

    WRONG.

    A closure generally includes the function/code reference
    plus its captured environment.

TRAP 3:

    "Dynamic dispatch is always determined at compile time."

    WRONG.

    Dynamic dispatch can depend on runtime type/object information.

TRAP 4:

    "Type erasure and specialization are identical."

    WRONG.

    They are different implementation strategies.

TRAP 5:

    "Exception handling is only a parser feature."

    WRONG.

    It can require compiler transformations, metadata,
    runtime support and stack unwinding.

TRAP 6:

    "Dynamic typing means no type checking occurs."

    WRONG.

    Type checks may occur at runtime.

TRAP 7:

    "Virtual function calls can never be optimized."

    WRONG.

    Devirtualization and profiling can sometimes convert
    them into direct calls.

TRAP 8:

    "Every dynamically allocated object must remain on the heap."

    Not necessarily.

    Escape analysis and other optimizations may eliminate
    or transform some allocations.

56. INTERVIEW QUESTIONS
══════════════════════════════════════════════════════════════════════════════

Q1. What are advanced language features?

Answer:
They are high-level programming constructs such as generics,
closures, lambdas, polymorphism, exceptions and dynamic features
that require additional compiler/runtime support.

Q2. What is a generic?

Answer:
A generic is code parameterized by one or more types so that
the same implementation can work with multiple types.

Q3. What is type erasure?

Answer:
Type erasure is an implementation technique in which generic
type information is removed or represented in a common form
for runtime execution.

Q4. What is specialization?

Answer:
Specialization generates type-specific versions of generic code.

Q5. What is a lambda?

Answer:
A lambda is an anonymous function expression.

Q6. What is a closure?

Answer:
A closure is a function together with the environment containing
captured variables needed by that function.

Q7. Why may closures require heap allocation?

Answer:
Because a captured variable may need to remain alive after the
activation record where it was originally declared has returned.

Q8. What is dynamic dispatch?

Answer:
Dynamic dispatch determines the method implementation to invoke
using runtime object/type information.

Q9. What is a vtable?

Answer:
A virtual method table is a data structure commonly used to
support dynamic dispatch for virtual methods.

Q10. What is devirtualization?

Answer:
It is the optimization of replacing a dynamic method call with
a more direct call when the target can be determined.

Q11. What is a higher-order function?

Answer:
A function that accepts another function as an argument and/or
returns a function.

Q12. What is stack unwinding?

Answer:
It is the process of moving back through activation records,
usually during exception handling, until an appropriate handler
is found.

Q13. What is dynamic typing?

Answer:
A typing approach where significant type information/checking
is determined at runtime rather than entirely at compile time.

Q14. What is escape analysis?

Answer:
An analysis that determines whether an object/value escapes a
particular scope or thread of execution, enabling optimizations
such as allocation elimination in suitable cases.
