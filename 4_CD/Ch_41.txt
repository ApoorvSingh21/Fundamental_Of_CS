============================================================
1. WHAT IS A MINI COMPILER?
============================================================

A mini compiler is a small compiler implementation designed
to demonstrate the fundamental concepts of compiler design.

It does not need to support a complete programming language.

We can design a tiny language containing:

    Variables
    Integer values
    Arithmetic expressions
    Assignment
    print statement
    Basic control flow

Example program:

    x = 10;
    y = 20;
    z = x + y * 2;
    print(z);

Our mini compiler converts this source program into an
intermediate or target representation.

============================================================
2. WHY BUILD A MINI COMPILER?
============================================================

Building a compiler helps you understand:

    • How source code becomes machine/executable code
    • How tokens are generated
    • How grammars are used
    • How ASTs represent programs
    • How symbol tables work
    • How type checking works
    • How IR is generated
    • How optimization works
    • How target code is produced
    • How errors are detected and recovered

This connects almost the entire Compiler Design syllabus.

4. OUR MINI LANGUAGE
============================================================

Let us design a tiny language.

We will call it:

    MiniLang

Example:

    x = 10;
    y = 20;

    print(z);

Supported features:

    • Integer literals
    • Variables
    • Assignment

    • Parentheses
    • print()

============================================================
5. MINI LANGUAGE SYNTAX
============================================================

Example:

    x = 10 + 20;
    y = x * 5;
    print(y);

We can define a simplified grammar.

------------------------------------------------------------
PROGRAM
------------------------------------------------------------

    program → statement_list

------------------------------------------------------------
STATEMENT LIST
------------------------------------------------------------

    statement_list
        → statement statement_list
        | ε

------------------------------------------------------------
STATEMENT
------------------------------------------------------------

    statement
        → assignment
        | print_statement

------------------------------------------------------------
ASSIGNMENT
------------------------------------------------------------

    assignment
        → ID = expression ;

------------------------------------------------------------
PRINT
------------------------------------------------------------

    print_statement
        → print ( expression ) ;

------------------------------------------------------------
EXPRESSION
------------------------------------------------------------

    expression
        → expression + term
        | expression - term
        | term

------------------------------------------------------------
TERM
------------------------------------------------------------

    term
        → term * factor
        | term / factor
        | factor

------------------------------------------------------------
FACTOR
------------------------------------------------------------

    factor
        → NUMBER
        | ID
        | ( expression )

============================================================
6. WHY THE GRAMMAR HAS expression / term / factor
============================================================

Consider:

    x + y * z

Multiplication has higher precedence than addition.

Therefore:

    x + (y * z)

not:

    (x + y) * z

The grammar structure:

    expression
        ↓
      term
        ↓
     factor

helps encode operator precedence.

7. LEXICAL ANALYZER
============================================================

The lexical analyzer converts characters into tokens.

Input:

    x = 10 + y;

Output:

    ID(x)
    ASSIGN
    NUMBER(10)
    PLUS
    ID(y)
    SEMICOLON

    ID("x")

============================================================
10. LEXER PSEUDOCODE
============================================================

    function nextToken():

        skip whitespace

        if current character is a letter:
            read identifier
            if identifier == "print":
                return PRINT
            else:
                return ID

        if current character is a digit:
            read number
            return NUMBER

        if current character == '+':
            return PLUS

        if current character == '-':
            return MINUS

        if current character == '*':
            return MULTIPLY

        if current character == '/':
            return DIVIDE

        if current character == '=':
            return ASSIGN

        if current character == '(':
            return LPAREN

        if current character == ')':
            return RPAREN

        if current character == ';':
            return SEMICOLON

        otherwise:
            report lexical error

============================================================
11. LEXICAL ERRORS
============================================================

Example:

    x = 10 @ 20;

If '@' is not supported:

    Lexical Error:
    Invalid character '@'

Possible recovery:

    Skip '@'

Then continue scanning.

============================================================
12. PARSER
============================================================

The parser receives tokens.

Input:

    ID = NUMBER + NUMBER ;

The parser checks whether the sequence follows the grammar.

Example:

    x = 10 + 20;

is valid.

But:

    x = + 20;

is invalid according to our grammar.

============================================================
13. PARSER RESPONSIBILITY
============================================================

The parser performs:

    Token validation
    Grammar checking
    Structure construction
    Syntax error detection

Output:

    Parse Tree
    or
    AST

============================================================
14. RECURSIVE-DESCENT PARSER
============================================================

For a small compiler, recursive descent is easy to understand.

We can create functions:

    parseProgram()
    parseStatement()
    parseAssignment()
    parsePrint()
    parseExpression()
    parseTerm()
    parseFactor()

Each function corresponds approximately to a grammar
construct.

============================================================
15. PARSER PSEUDOCODE
============================================================

    parseExpression():

        node = parseTerm()

        while current token is PLUS
              or MINUS:

            operator = current token
            consume(operator)

            right = parseTerm()

            node = BinaryNode(
                    operator,
                    node,
                    right
                   )

        return node

------------------------------------------------------------

    parseTerm():

        node = parseFactor()

        while current token is MULTIPLY
              or DIVIDE:

            operator = current token
            consume(operator)

            right = parseFactor()

            node = BinaryNode(
                    operator,
                    node,
                    right
                   )

        return node

------------------------------------------------------------

    parseFactor():

        if token == NUMBER:
            return NumberNode(value)

        if token == ID:
            return IdentifierNode(name)

        if token == '(':
            consume('(')
            node = parseExpression()
            consume(')')
            return node

        report syntax error

============================================================
16. AST — ABSTRACT SYNTAX TREE
============================================================

AST is a simplified tree representation of the program's
meaningful structure.

Example:

    x = 10 + 20 * 2;

AST:

              =
             / \
            x   +
               / \
             10   *
                 / \
                20  2

Notice:

    20 * 2

is deeper than:

    +

Therefore multiplication has higher precedence.

============================================================
17. WHY AST IS BETTER THAN A PARSE TREE
============================================================

A parse tree contains grammar details.

An AST removes unnecessary syntax details.

For example:

    Parentheses
    Some grammar helper nodes
    Redundant nonterminals

AST focuses on:

    Meaningful program structure.

Therefore compilers commonly use ASTs for later phases.

============================================================
18. AST NODE TYPES
============================================================

Possible node types:

    NumberNode
    IdentifierNode
    BinaryExpressionNode
    AssignmentNode
    PrintNode
    ProgramNode

Example:

    x = 10 + 20;

becomes:

    AssignmentNode
        |
        +-- IdentifierNode("x")
        |
        +-- BinaryExpressionNode("+")
                |
                +-- NumberNode(10)
                |
                +-- NumberNode(20)

============================================================
19. SYMBOL TABLE
============================================================

The symbol table stores information about identifiers.

Example:

    x = 10;
    y = 20;

Symbol table:

    +------+--------+
    | Name | Type   |
    +------+--------+
    | x    | int    |
    | y    | int    |
    +------+--------+

It may also store:

    Scope
    Memory location
    Size
    Storage class
    Declaration information

============================================================
20. SYMBOL TABLE OPERATIONS
============================================================

Main operations:

    INSERT
    LOOKUP
    UPDATE
    DELETE
    SCOPE MANAGEMENT

Example:

    x = 10;

If x is new:

    INSERT(x)

Later:

    y = x + 5;

Compiler performs:

    LOOKUP(x)

============================================================
21. SEMANTIC ANALYSIS
============================================================

After parsing, the compiler checks meaning.

Example:

    x = 10;

If x is undeclared and the language requires declaration:

    Semantic Error:
    variable 'x' is not declared

Our MiniLang can either:

    Automatically declare variables

or require:

    int x;

The design choice depends on the language.

============================================================
22. TYPE CHECKING
============================================================

Suppose MiniLang supports:

    int
    bool

Then:

    x = 10;

may be valid.

But:

    x = true;

could be invalid if x is int.

Semantic analyzer checks:

    Type(left) == Type(right)

according to the language's type rules.

============================================================
23. SEMANTIC CHECKS
============================================================

Our compiler can perform:

    • Variable declaration checking
    • Duplicate declaration checking
    • Type checking
    • Operator compatibility
    • Assignment compatibility
    • Function argument checking
    • Return-type checking
    • Scope checking

For a tiny compiler, only a subset may be implemented.

============================================================
24. INTERMEDIATE REPRESENTATION
============================================================

IR is an intermediate form between source code and target
machine code.

Why use IR?

    Source Language
          ↓
         IR
          ↓
    Target Machine

Advantages:

    • Easier optimization
    • Easier code generation
    • Separation of front end and back end
    • Portability

============================================================
25. THREE-ADDRESS CODE
============================================================

For:

    x = 10 + 20 * 2;

TAC:

    t1 = 20 * 2
    t2 = 10 + t1
    x = t2

Each instruction typically has at most three operands.

============================================================
26. TAC FOR A MORE COMPLEX EXPRESSION
============================================================

Source:

    z = a + b * c - d;

TAC:

    t1 = b * c
    t2 = a + t1
    t3 = t2 - d
    z = t3

============================================================
27. QUADRUPLE REPRESENTATION
============================================================

TAC can be represented as quadruples.

For:

    t1 = b * c

Quadruple:

    +-----------+
    | op   *    |
    | arg1 b    |
    | arg2 c    |
    | result t1 |
    +-----------+

For:

    z = t3

Conceptually:

    op      =
    arg1    t3
    arg2    -
    result  z

============================================================
28. CONTROL FLOW
============================================================

Our first compiler can support simple statements.

Later, we can support:

    if
    while
    for

Example:

    if (x > 10)
        print(x);

IR may contain:

    if x > 10 goto L1
    goto L2

L1:
    print x

L2:

This introduces labels and control flow.

============================================================
29. BASIC BLOCKS
============================================================

A basic block is a sequence of instructions with:

    One entry point
    One exit point

Example:

    t1 = a + b
    t2 = t1 * c
    x = t2

These can form a basic block.

Multiple basic blocks can form a:

    Control Flow Graph (CFG)

============================================================
30. OPTIMIZATION
============================================================

Optimization improves code while preserving program behavior.

Example:

    x = 10 + 20;

Compiler can calculate:

    10 + 20 = 30

So:

    x = 30;

This is:

    Constant folding

============================================================
31. CONSTANT FOLDING
============================================================

Input:

    x = 10 + 20 * 2;

Compiler evaluates:

    20 * 2 = 40
    10 + 40 = 50

Optimized:

    x = 50;

This can happen before final code generation.

============================================================
32. CONSTANT PROPAGATION
============================================================

Example:

    x = 10;
    y = x + 5;

Compiler may replace x with 10:

    y = 10 + 5;

Then constant folding gives:

    y = 15;

============================================================
33. DEAD CODE ELIMINATION
============================================================

Example:

    x = 10;
    x = 20;
    print(x);

The first assignment:

    x = 10;

may be dead because its value is overwritten before use.

Optimization can remove unnecessary computation where
semantically safe.

============================================================
34. COMMON SUBEXPRESSION ELIMINATION
============================================================

Example:

    a = b + c;
    d = b + c;

The expression:

    b + c

is computed twice.

Compiler can reuse the first result when safe:

    t1 = b + c
    a = t1
    d = t1

============================================================
35. CODE GENERATION
============================================================

Code generation converts IR into target instructions.

Suppose TAC:

    t1 = b * c
    t2 = a + t1
    x = t2

A simplified register-based target could be:

    LOAD R1, b
    MUL  R1, c
    LOAD R2, a
    ADD  R2, R1
    STORE x, R2

Actual instructions depend on the target architecture.

============================================================
36. TARGET MACHINE
============================================================

Our mini compiler can target:

    • A simple stack machine
    • A virtual machine
    • A simple register machine
    • LLVM IR
    • JVM bytecode
    • A real CPU architecture

For learning, a simple virtual machine is often easier.

37. STACK-MACHINE TARGET

    x = 10 + 20;

    PUSH 10

Execution:

    PUSH 10
        Stack: [10]

    PUSH 20
        Stack: [10,20]

    ADD

    STORE x

    +

    NUMBER
    ID
    (

============================================================

    x = 10;

============================================================
45. ERROR RECOVERY
============================================================

Our parser can synchronize at:

    ;

For example:

    x = 10 + ;
    y = 20;

After detecting the first error, the parser can skip until:

    ;

Then continue:

    y = 20;

This is panic-mode recovery.

47. COMPILER DRIVER
============================================================

The main compiler driver coordinates all phases.

Conceptual pseudocode:

    source = readFile()

    tokens = lexer(source)

    ast = parser(tokens)

    symbols = buildSymbolTable(ast)

    semanticCheck(ast, symbols)

    ir = generateIR(ast)

    optimizedIR = optimize(ir)

    target = generateCode(optimizedIR)

    writeOutput(target)

Pipeline:

    Source
      ↓
    Lexer
      ↓
    Parser
      ↓
    AST
      ↓
    Semantic Analysis
      ↓
    IR
      ↓
    Optimization
      ↓
    Code Generation
      ↓
    Target

============================================================
56. COMMON MINI COMPILER MISTAKES
============================================================

Mistake 1:

Trying to implement the complete C/C++ language.

Better:

    Start with a tiny language.

------------------------------------------------------------

Mistake 2:

Writing code before defining grammar.

Better:

    Define tokens + grammar first.

------------------------------------------------------------

Mistake 3:

Skipping AST design.

Better:

    Design clear AST node types.

------------------------------------------------------------

Mistake 4:

Mixing parsing and code generation.

Better:

    Keep phases separate.

------------------------------------------------------------

Mistake 5:

Ignoring error handling.

Better:

    Add diagnostics from the beginning.

------------------------------------------------------------

Mistake 6:

Optimizing before correctness.

Better:

    First make compiler correct.
    Then optimize.

58. WHY IR IS POWERFUL
============================================================

Suppose we support:

    Source Language A
    Source Language B

and:

    CPU 1
    CPU 2
    CPU 3

Without IR, we may need many direct translators.

With IR:

    Language A ──→ IR ──→ CPU 1
                 └──────→ CPU 2
                 └──────→ CPU 3

    Language B ──→ IR ──→ CPU 1
                 └──────→ CPU 2
                 └──────→ CPU 3

IR reduces coupling between front ends and back ends.

WHY USE IR?
============================================================

Answer:

IR separates the source-language front end from the
target-machine back end and provides a convenient form for
optimization.

============================================================
64. INTERVIEW QUESTION:
WHERE DOES THE SYMBOL TABLE FIT?
============================================================

The symbol table is used across compiler phases, especially:

    Lexical Analysis
    Syntax/Semantic Analysis
    Code Generation

It stores information about identifiers.

============================================================
65. GATE TRAPS
============================================================

TRAP 1:

"AST and parse tree are exactly the same."

FALSE.

AST is generally a simplified representation.

------------------------------------------------------------

TRAP 2:

"Optimization can change program semantics."

FALSE.

Correct optimization preserves required observable behavior.

------------------------------------------------------------

TRAP 3:

"IR is generated before parsing."

FALSE.

Normally the source must first be analyzed sufficiently to
construct a meaningful IR.

------------------------------------------------------------

TRAP 4:

"Symbol table is used only during lexical analysis."

FALSE.

It is used across multiple compiler phases.

------------------------------------------------------------

TRAP 5:

"Code generation should always happen before optimization."

Not generally.

A common pipeline is:

    IR
      ↓
    Optimization
      ↓
    Code Generation

------------------------------------------------------------

TRAP 6:

"Semantic analysis checks only syntax."

FALSE.

Syntax is handled primarily by parsing.

Semantic analysis checks meaning-related constraints.

73. CHAPTER 41 — GATE REVISION
============================================================

Remember this sequence:

    SOURCE
      ↓
    LEXER
      ↓
    TOKENS
      ↓
    PARSER
      ↓
    AST
      ↓
    SEMANTIC ANALYSIS
      ↓
    IR
      ↓
    OPTIMIZATION
      ↓
    CODE GENERATION
      ↓
    TARGET CODE

The most important practical relationships:

    Lexer      → Tokens

    Parser     → Structure

    AST        → Program representation

    Symbol Table → Identifier information

    Semantic Analyzer → Meaning/type checking

    IR Generator → Intermediate code

    Optimizer   → Improve code

    Code Generator → Target instructions

    Error Handler → Diagnostics/recovery

============================================================
74. FINAL INTERVIEW SUMMARY
============================================================

If an interviewer asks:

"Explain your mini compiler."

Answer:

    "I designed a small programming language and implemented
    its compiler as a pipeline. The lexer converts source
    characters into tokens. A parser validates the grammar
    and builds an AST. Semantic analysis uses a symbol table
    to perform checks such as identifier and type validation.
    The AST is translated into an intermediate representation,
    such as three-address code. Basic optimizations such as
    constant folding can then be applied. Finally, a code
    generator converts the optimized representation into
    instructions for a simple virtual machine or target
    architecture. Error detection, diagnostics, and recovery
    are integrated throughout the front end."
