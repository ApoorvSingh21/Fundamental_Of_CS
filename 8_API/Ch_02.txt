1. WHAT IS AN API?
====================================================================

API stands for:

    Application Programming Interface


An API is a defined interface through which one software component
can communicate with another software component.

Simple definition:

    API = A set of rules and interfaces that allows software
          systems to communicate and interact.


Example:

    Mobile App
        |
        | API Request
        ↓
    Backend Server
        |
        ↓
    Database


The mobile application does not need to know how the database
works internally.

It communicates with the backend through an API.


====================================================================
2. SIMPLE REAL-LIFE ANALOGY
====================================================================

Imagine a restaurant.

    Customer
        |
        ↓
      Menu
        |
        ↓
     Waiter
        |
        ↓
     Kitchen


Customer does not directly enter the kitchen.

The customer communicates through the waiter.

Similarly:

    Client Application
          |
          ↓
         API
          |
          ↓
       Backend


The API acts as an interface between software components.

IMPORTANT:

    API is NOT necessarily a server.

    API is NOT necessarily REST.

    REST is one architectural style used for APIs.

    API is a much broader concept.


====================================================================
3. WHY DO WE NEED APIs?
====================================================================

Imagine an e-commerce application.

It contains:

    User System
    Product System
    Order System
    Payment System
    Notification System


Without well-defined interfaces, components may become tightly
coupled.

With APIs:

    Mobile App
         |
         ↓
    User API
         |
         ↓
    User Service


    Mobile App
         |
         ↓
    Product API
         |
         ↓
    Product Service


    Mobile App
         |
         ↓
    Order API
         |
         ↓
    Order Service


APIs provide controlled communication.


====================================================================
4. PROBLEMS APIs SOLVE
====================================================================

APIs help solve several software engineering problems.

1. SYSTEM INTEGRATION

    System A
       |
       ↓
      API
       |
       ↓
    System B


2. ABSTRACTION

Client does not need to know internal implementation.

Example:

    Client:
        GET /users/10

The client does not need to know:

    Which database?
    Which SQL query?
    Which programming language?
    Which server?
    Which internal service?


3. REUSABILITY

One API can serve multiple clients.

             +--> Web Application
             |
    API -----+--> Mobile Application
             |
             +--> Partner Application


4. SEPARATION OF CONCERNS

Frontend and backend can evolve independently.


5. SECURITY

The backend can expose only controlled operations.

Instead of:

    Client → Direct Database


Use:

    Client → API → Database


6. SCALABILITY

APIs allow services to be deployed and scaled independently.


====================================================================
5. API AS AN INTERFACE
====================================================================

The word "interface" is extremely important.

Suppose you have:

    Payment System


The internal implementation may be complicated:

    Payment Gateway
         |
         ↓
    Fraud Detection
         |
         ↓
    Bank
         |
         ↓
    Transaction Database
         |
         ↓
    Ledger


The client might only see:

    POST /payments


The API hides internal complexity.

This is called:

    ABSTRACTION


The client cares about:

    What operation is available?
    What input is required?
    What response will I receive?
    What errors can occur?

The client does NOT need to know every internal implementation detail.

6. API CONSUMER
====================================================================

An API consumer is a software component that uses an API.

Examples:

    Web Browser
    Mobile App
    Frontend Application
    Backend Service
    Desktop Application
    Third-Party Application
    Postman
    Automated Test


Example:

    Mobile App
         |
         | Uses
         ↓
       API


Mobile App = API Consumer.

7. API PROVIDER
====================================================================

The API provider is the system that exposes the API.

Example:

    Mobile App
         |
         | Request
         ↓
    API Provider
         |
         ↓
    Database


The API provider is responsible for:

    Authentication
    Authorization
    Validation
    Business Logic
    Data Access
    Response Generation
    Error Handling
    Monitoring


====================================================================
8. API CONSUMER VS API PROVIDER
====================================================================

API CONSUMER:

    Uses the API.


API PROVIDER:

    Provides the API.


Example:

    E-commerce Mobile App
            |
            | Consumer
            ↓
       E-commerce API
            |
            | Provider
            ↓
       Backend Services


Another example:

    Your Application
          |
          | Consumer
          ↓
      Payment API
          |
          | Provider
          ↓
     Payment Company


One important concept:

    A system can be a consumer AND provider at the same time.


Example:

    Service A
       |
       | consumes API
       ↓
    Service B

    Service A may also expose an API
       |
       ↓
    Service C


====================================================================
9. API REQUEST
====================================================================

An API request is a message sent by an API consumer to an API
provider asking it to perform an operation or provide information.


Example:

    GET /api/users/10


Meaning:

    "Give me information about user 10."


A request may contain:

    HTTP Method
    URL
    Path
    Query Parameters
    Headers
    Body


Example:

    POST /api/users HTTP/1.1
    Host: api.example.com
    Content-Type: application/json

    {
        "name": "Apoorv",
        "email": "user@example.com"
    }


Breakdown:

    POST
        ↓
    Operation/method semantics

    /api/users
        ↓
    Endpoint path

    Content-Type
        ↓
    Header

    JSON
        ↓
    Request body


====================================================================
10. API RESPONSE
====================================================================

An API response is the result returned by the API provider.

Example:

    HTTP/1.1 201 Created
    Content-Type: application/json

    {
        "id": 101,
        "name": "Apoorv",
        "email": "user@example.com"
    }


A response can contain:

    Status Code
    Headers
    Body


The body may contain:

    JSON
    XML
    Text
    Binary Data
    File
    Empty Response

====================================================================
12. ENDPOINT
====================================================================

An endpoint is a specific network-accessible interface location
through which an API operation can be invoked.

Example:

    https://api.example.com/users


This may represent a users collection.


Another:

    https://api.example.com/users/10


This may represent user 10.


Typical REST API endpoints:

    GET    /users
    GET    /users/10
    POST   /users
    PUT    /users/10
    PATCH  /users/10
    DELETE /users/10


IMPORTANT:

An endpoint is not simply a URL in every possible API style.

In HTTP APIs, developers commonly describe the combination of
method + target path as an endpoint/operation.


For example:

    GET /users


and:

    POST /users


use the same path but represent different operations.


====================================================================
13. RESOURCE
====================================================================

A resource is a conceptual entity or piece of information exposed
through an API.

Examples:

    User
    Product
    Order
    Payment
    Employee
    Course
    Student


Example:

    /users


represents a collection of user resources.


    /users/10


represents a particular user resource.


Think:

    Resource = WHAT you are working with.

    Operation = WHAT you want to do with it.


====================================================================
14. RESOURCE VS ENDPOINT
====================================================================

RESOURCE:

    User


API path:

    /users


Individual resource:

    /users/10


Operations:

    GET /users/10
    PUT /users/10
    DELETE /users/10


The resource is the conceptual object.

The endpoint/operation is how the API exposes interaction with it.


====================================================================
15. OPERATION
====================================================================

An operation represents an action or interaction available through
an API.

For HTTP APIs, HTTP methods provide standardized semantics.

Examples:

    GET
        Retrieve representation/data.

    POST
        Submit data, often creating a resource or triggering
        processing.

    PUT
        Replace a resource representation.

    PATCH
        Partially modify a resource.

    DELETE
        Remove a resource.


Example:

    GET /users/10


Operation:

    Retrieve user 10.


Example:

    DELETE /users/10


Operation:

    Delete user 10.


====================================================================
16. API CONTRACT
====================================================================

This is one of the MOST IMPORTANT concepts in professional
API development.

An API contract defines how a consumer and provider communicate.

It specifies things such as:

    Available operations
    Request format
    Required parameters
    Authentication
    Response format
    Status codes
    Error format
    Data types
    Validation rules
    Compatibility expectations


Example contract:

    Endpoint:
        GET /users/{id}

    Input:
        id = integer

    Authentication:
        Bearer token

    Success:
        200 OK

    Response:
        JSON


Example:

    GET /users/10

    Response:

    {
        "id": 10,
        "name": "Apoorv"
    }


The client can be developed against this contract.


====================================================================
17. WHY API CONTRACT IS IMPORTANT
====================================================================

Suppose:

    Frontend Team
          |
          ↓
       API Contract
          |
          ↓
    Backend Team


Frontend developers can build the UI based on the expected API.

Backend developers can implement the API according to the same
contract.


Without a stable contract:

    Frontend expects:

    {
        "userName": "Apoorv"
    }


Backend returns:

    {
        "name": "Apoorv"
    }


The application may break.


Therefore:

    API Contract = Agreement between API consumer and provider.

18. API SCHEMA
====================================================================

A schema describes the structure of API data.

Example:

    User:

    {
        "id": integer,
        "name": string,
        "email": string
    }


Schema can define:

    Field names
    Data types
    Required fields
    Optional fields
    Constraints
    Nested objects
    Arrays


Example:

    {
        "id": 101,
        "name": "Apoorv",
        "email": "user@example.com"
    }


Possible schema:

    id:
        integer
        required

    name:
        string
        required

    email:
        string
        required


OpenAPI can be used to describe HTTP API schemas.

    Methods

====================================================================
20. BASE URL
====================================================================

A base URL is the common root used by an API.

Example:

    https://api.example.com


Endpoint:

    /users


Complete request:

    https://api.example.com/users


Another endpoint:

    /orders/100


Complete URL:

    https://api.example.com/orders/100


In API documentation, the base URL helps consumers understand
where requests should be sent.


====================================================================
21. API ROUTE
====================================================================

A route defines how an application maps an incoming request to
specific application logic.

Example:

    GET /users


could route to:

    UserController.getUsers()


Another:

    GET /users/10


could route to:

    UserController.getUserById(10)


Conceptually:

    HTTP Request
         |
         ↓
       Router
         |
         ↓
      Controller
         |
         ↓
       Service
         |
         ↓
      Repository
         |
         ↓
      Database


====================================================================
22. API CONTROLLER
====================================================================

A controller typically handles incoming API requests at the
application boundary.

Example:

    GET /users/10


Controller:

    getUser(10)


The controller may:

    Read parameters
    Validate request
    Call service
    Return response


Professional architecture often separates controller logic from
business logic.


Example:

    Controller
        ↓
    Service
        ↓
    Repository
        ↓
    Database


====================================================================
23. API SERVICE
====================================================================

The service layer usually contains business logic.

Example:

    OrderService.createOrder()


It may perform:

    Check inventory
    Calculate price
    Apply discount
    Create order
    Trigger payment
    Send notification


The controller should generally not contain all of this logic.


Better:

    Controller
        |
        ↓
    OrderService
        |
        ↓
    OrderRepository
        |
        ↓
    Database


====================================================================
24. API VS DATABASE
====================================================================

API:

    Interface for communication.


Database:

    System for storing/managing data.


Bad architecture:

    Mobile App
        |
        ↓
    Direct Database


Problems:

    Security
    Coupling
    Validation
    Business logic exposure
    Difficult maintenance


Better:

    Mobile App
        |
        ↓
       API
        |
        ↓
    Database


API acts as a controlled application boundary.


====================================================================
25. API VS USER INTERFACE
====================================================================

UI:

    Designed for humans.


API:

    Designed primarily for software-to-software interaction.


Example:

    Human
      |
      ↓
    Website UI
      |
      ↓
    API
      |
      ↓
    Backend


Another:

    Mobile App
       |
       ↓
      API
       |
       ↓
    Backend


Multiple interfaces can consume the same backend API.


====================================================================
26. API VS LIBRARY
====================================================================

A library API is different from a Web API.

Example:

    C++ Standard Library API


You call functions such as:

    std::vector
    std::sort


This is an API too.

But it may not involve HTTP or a network.


Web API:

    Client
       |
       | HTTP
       ↓
    Server


Library API:

    Program
       |
       | Function call
       ↓
    Library


Therefore:

    API ≠ HTTP

    API ≠ REST

    API ≠ Web API


API is a broader software engineering concept.

    User Service

29. EXTERNAL API

30. PUBLIC API
====================================================================

A public API is designed for broad external consumption.

Example:

    Developer
       |
       ↓
    Public API

====================================================================
31. API KEY
====================================================================

An API key is a credential used by some APIs to identify or
authorize clients.

Example:

    GET /weather

    X-API-Key: abc123...


The server checks the key.

Important:

    API keys should be treated as secrets when they provide access
    privileges.

Do not hard-code sensitive API keys into public source code.


API keys are NOT a universal replacement for stronger
authentication/authorization systems.


====================================================================
32. AUTHENTICATION VS AUTHORIZATION
====================================================================

AUTHENTICATION:

    "Who are you?"


AUTHORIZATION:

    "What are you allowed to do?"


Example:

    User logs in.

Authentication:

    Verify identity.


Authorization:

    Can this user delete this order?


Flow:

    Client
      |
      | Credentials
      ↓
    Authentication
      |
      ↓
    Identity
      |
      ↓
    Authorization
      |
      ↓
    API Operation


These concepts will be studied deeply in the API Security phase.

33. API GATEWAY RELATIONSHIP
====================================================================

In a microservices architecture, clients may not communicate
directly with every service.

Instead:

    Client
       |
       ↓
    API Gateway
       |
       +----→ User Service
       |
       +----→ Order Service
       |
       +----→ Payment Service
       |
       +----→ Product Service


API Gateway can provide:

    Routing
    Authentication
    Rate limiting
    TLS termination
    Logging
    Request transformation
    Aggregation


API Gateway is an infrastructure/architecture component.

It is NOT the same thing as an API itself.

34. API ABSTRACTION
====================================================================

Suppose a client calls:

    GET /products/10


Internally, the API might perform:

    API
     |
     +→ Redis
     |
     +→ Product Service
     |
     +→ PostgreSQL
     |
     +→ Inventory Service
     |
     +→ Pricing Service


The client only sees:

    GET /products/10


This is abstraction.

The API hides internal implementation details.

35. API COUPLING
====================================================================

Coupling means how strongly components depend on each other.

High coupling:

    Client
      |
      | Depends directly on database schema
      ↓
    Database


Low coupling:

    Client
      |
      ↓
    Stable API Contract
      |
      ↓
    Internal Implementation


The API contract acts as a boundary.


IMPORTANT:

Good API design aims for:

    Low unnecessary coupling
    Stable contracts
    Clear responsibilities

====================================================================
43. API VERSIONING
====================================================================

APIs evolve.

Suppose version 1 returns:

    {
        "name": "Apoorv"
    }


Later version 2 returns:

    {
        "firstName": "Apoorv",
        "lastName": "Singh"
    }


Changing the contract can break existing consumers.

Therefore APIs may use versioning.

Example:

    /api/v1/users

    /api/v2/users


Other versioning strategies also exist and will be studied later.


====================================================================
44. API DEPRECATION
====================================================================

Sometimes an API version becomes old.

Example:

    v1
       ↓
    deprecated
       ↓
    v2
       ↓
    v3


Deprecation means:

    "This API is still available for now, but consumers should
     migrate to the newer interface."


Eventually:

    Deprecated API
         ↓
    Retirement
         ↓
    Removed


Professional API providers communicate deprecation clearly.

45. REAL-WORLD EXAMPLE — LOGIN API
====================================================================

Suppose a mobile application has:

    Login Screen


User enters:

    Email
    Password


Mobile app sends:

    POST /api/login


Request:

    {
        "email": "user@example.com",
        "password": "********"
    }


Server:

    1. Validate input
    2. Find user
    3. Verify password
    4. Create authentication result
    5. Return response


Response may contain an access token:

    {
        "access_token": "eyJ...",
        "token_type": "Bearer"
    }


Flow:

    Mobile App
        |
        | POST /api/login
        ↓
    Authentication API
        |
        ↓
    User Database
        |
        ↓
    Authentication API
        |
        | Token
        ↓
    Mobile App


This token can then be used for authorized API requests.

    | Service     |
    +-------------+


Each service may expose APIs.

Communication can be:

    REST
    gRPC
    Messaging
    Events


API engineering therefore becomes a major part of microservices
engineering.


====================================================================
50. API AND DATABASE
====================================================================

Typical architecture:

    Client
       |
       ↓
      API
       |
       ↓
    Service
       |
       ↓
    Repository
       |
       ↓
    Database


The API should not blindly expose database structure.

For example, database table:

    users

might contain:

    id
    password_hash
    internal_flags
    created_at
    updated_at


The public API might return:

    id
    name
    email


Sensitive/internal fields should not automatically be exposed.


====================================================================
51. API DATA TRANSFER OBJECT
====================================================================

DTO = Data Transfer Object.

A DTO defines the data structure transferred between components,
especially across application boundaries.

Example internal database object:

    UserEntity:

    id
    name
    email
    password_hash
    internal_status


API response DTO:

    UserResponse:

    id
    name
    email


This prevents internal database representation from being directly
exposed as an external API contract.


====================================================================
52. API SECURITY BOUNDARY
====================================================================

An API is often a security boundary.

Example:

    Internet
       |
       ↓
    Authentication
       |
       ↓
    Authorization
       |
       ↓
    Validation
       |
       ↓
    Business Logic
       |
       ↓
    Database


Never assume:

    "The client will send correct data."


The server must validate and enforce rules.

The client is NOT trusted.

53. API CONTRACT-FIRST APPROACH
====================================================================

There are two common approaches.

CODE-FIRST:

    Write implementation
          ↓
    Generate/document contract


CONTRACT-FIRST:

    Design API contract
          ↓
    Review contract
          ↓
    Implement API


Contract-first development can improve communication between:

    Frontend
    Backend
    QA
    Product
    External Consumers


Tools:

    OpenAPI
    Swagger


====================================================================
54. API-FIRST ARCHITECTURE
====================================================================

API-first means treating APIs as first-class products/interfaces.

Instead of:

    Build backend
       ↓
    Add API later


Think:

    Define interface
       ↓
    Validate design
       ↓
    Implement
       ↓
    Test
       ↓
    Document
       ↓
    Deploy


This is especially useful for organizations with many API consumers.

55. API AS A PRODUCT
====================================================================

A mature organization may treat an API as a product.

An API product has:

    Users
    Documentation
    Versioning
    Support
    Monitoring
    Security

    Lifecycle
    Analytics


Example:

    Payment API

    E-commerce

    Partners


The API needs product-level quality.


====================================================================
56. API SLA / SLO CONCEPT
====================================================================

Production APIs may have reliability targets.

Example:

    Availability target:
        99.9%

    Latency target:
        95% requests under 200 ms


SLA:

    Service Level Agreement

SLO:

    Service Level Objective


These become important in production API engineering and
distributed systems.


====================================================================
57. API RATE LIMITING
====================================================================

A provider may limit how many requests a client can make.

Example:

    100 requests/minute


If the client exceeds the limit:

    HTTP 429 Too Many Requests


Purpose:

    Prevent abuse
    Protect resources
    Maintain fairness
    Control costs


Example:

    Client
      |
      | 1000 requests
      ↓
    API Gateway
      |
      X
    Rate Limit


Rate limiting will be studied deeply later.

58. API OBSERVABILITY
====================================================================

Production APIs should allow engineers to understand what is
happening.

Three major pillars:

    Logs
    Metrics
    Traces


Logs:

    What happened?

Traces:

    Where did the request travel?


Example:

Distributed tracing can show the entire request path.

62. MASTER-LEVEL MENTAL MODEL
====================================================================

Remember this:

    API = Interface

    Consumer = Caller/User of API

    Provider = System exposing API

    Request = What the consumer sends

    Response = What the provider returns

    Endpoint = Address/operation exposed by an API

    Resource = Thing/data represented by the API

    Operation = Interaction performed on a resource

    Contract = Agreement about how communication works

    Schema = Structure of exchanged data

    Documentation = Instructions for consumers

    Lifecycle = Plan → Design → Build → Test → Deploy →
                Monitor → Version → Deprecate → Retire

63. COMMON BEGINNER MISTAKES
====================================================================

MISTAKE 1:

    "API means REST API."

CORRECT:

    REST is one way of designing Web APIs.


MISTAKE 2:

    "API is a database."

CORRECT:

    API is an interface; database is a data storage system.


MISTAKE 3:

    "API means URL."

CORRECT:

    A Web API may expose URLs/endpoints, but an API is the complete
    interface/contract, not merely a URL.


MISTAKE 4:

    "HTTPS makes an API completely secure."

CORRECT:

    HTTPS protects communication, but application security still
    requires authentication, authorization, validation, etc.


MISTAKE 5:

    "The client can be trusted."

CORRECT:

    The server must validate and enforce security rules.


MISTAKE 6:

    "API only means communication between frontend and backend."

CORRECT:

    APIs can connect:

        Frontend ↔ Backend
        Service ↔ Service
        Company ↔ Partner
        Application ↔ Cloud Service
        Program ↔ Library
